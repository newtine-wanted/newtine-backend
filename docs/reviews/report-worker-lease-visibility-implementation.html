승인된 기준선

목표
최종 visibility 필터 결과를 저장 content에 반영하고, 만료 claim의 worker-owned write를 차단한다.
불변식
claim id·attempt·token이 맞고 lease가 유효할 때만 captureCandidates·heartbeat·complete·fail이 성공한다.
비목표
스키마·HTTP API·lease 기간·재시도 정책·provider 계약·DB clock 전면 통합은 변경하지 않는다.
승인 범위
설계 문서 D1 visibility 재할당, D2 captureCandidates 포함 fencing, D3 기존 now 계약 유지.

현재 구현

승인 범위의 구현을 완료했다. 스키마·API·lease 기간·재시도 정책은 변경하지 않았다.

  1. apps/batch/src/report/report.worker.ts:166에서 두 번째 filterVisibleCandidates 반환값을 candidates에 재할당했다.
  2. libs/core/src/report/mikroOrmReport.repository.ts의 heartbeat·captureCandidates·complete·fail에 lease_expires_at > now 조건을 추가했다. complete는 선행 select와 최종 update 모두 검사한다.
  3. visibility 변화 unit test와 만료 claim lifecycle integration test를 추가했다.
  4. 집중 테스트·전체 unit·typecheck·lint·format을 실행했다.
RUNNING + id/attempt/token + lease_expires_at > now
  → claim-bound write 허용
만료 또는 token 불일치
  → row count 0 / STALE_CLAIM
  → 기존 stale 처리와 다음 claim 회수

설계 delta

없음. 승인된 D1 재할당, D2 captureCandidates 포함 fencing, D3 기존 now 계약 유지가 그대로 구현됐다. 스키마·API·외부 효과·재시도 정책의 추가 변경은 없다.

잔여 위험과 운영 조건

현재 잔여 위험: 설계는 repository 메서드의 기존 now 계약을 유지한다. 배포 호스트 간 시계 오차가 실제로 관측되면 clock_timestamp() 기반의 별도 lease 시간 통합 설계를 다시 승인해야 한다.

운영에서 확인할 첫 증거는 report.run.stale_result, report.run.stale_failure 로그와 report의 attempt/token 상태다. 오래된 worker가 false를 받은 뒤 새 attempt가 claim되면 정상 회복 경로다.
