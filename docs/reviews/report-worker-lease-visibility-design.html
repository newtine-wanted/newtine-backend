목표와 경계

목표
최종 저장 직전의 현재 후보 상태를 실제 report content에 반영하고, lease가 만료된 워커가 후보·heartbeat·성공·실패 상태를 변경하지 못하게 한다.
성공 신호
두 번째 visibility 조회에서 제외된 추천 후보가 최종 content에 나타나지 않는다. 만료된 claim의 claim-bound write는 모두 실패하며, 다음 워커가 정상적으로 claim·재시도할 수 있다.
비목표
스키마·마이그레이션·HTTP API·lease 기간·재시도 정책·provider 프롬프트·운영 배포 설정은 변경하지 않는다.

확인된 근거

현재 코드에서 확인된 결함과 영향
영역근거영향
visibility apps/batch/src/report/report.worker.ts:152-166에서 첫 번째 결과는 재할당하지만, 두 번째 filterVisibleCandidates 반환값은 버린다. buildReportContent가 첫 번째 스냅샷의 추천 후보를 사용해 숨김·활동 후보를 저장할 수 있다.
lease lifecycle libs/core/src/report/mikroOrmReport.repository.ts:419-434, :709-814의 heartbeat·complete·fail 조건에 lease_expires_at 비교가 없다. id·attempt·token이 동일한 오래된 워커가 lease 만료 뒤에도 새 워커의 상태와 경쟁할 수 있다.
같은 경계의 추가 write captureCandidates도 claim triple로 후보 JSON을 저장하지만 만료 조건은 없다. 반면 usage 시작은 lease_expires_at > clock_timestamp()를 이미 검사한다. 동일한 fencing invariant를 lifecycle 일부에만 적용하면 claim-bound write 경계가 불균일해진다.

변경 모델

  1. 초기 후보 필터 결과는 기존처럼 provider 입력으로 사용한다.
  2. provider 처리 후 두 번째 필터의 반환값을 candidates에 다시 대입한다.
  3. buildReportContent는 재할당된 후보만 사용한다. 이때 relatedUnavailable도 최신 필터 결과에 맞게 유지된다.
  4. repository의 claim-bound SQL은 만료 조건까지 확인한다. 만료 claim은 complete/fail에서 false를 반환하고, worker는 기존 stale 로그 경로를 사용한다.

설계 결정과 불변식

구현 기준선
ID결정근거와 trade-off
D1 두 번째 filterVisibleCandidates 결과를 candidates에 재할당한다. 이미 존재하는 필터·상태 필드를 재사용하는 최소 수정이다. visibility 조회를 추가하지 않으며 provider 계약도 바꾸지 않는다.
D2 lease 만료 guard를 heartbeat·complete·fail뿐 아니라 captureCandidates에도 적용한다. 후보 JSON 저장도 claim-owned write이므로 같은 fencing invariant를 적용한다. 범위는 동일 repository 경계 안에 한정된다.
D3 이번 변경의 만료 비교는 각 repository 메서드가 받은 now를 사용한다. claim/reaper의 기존 시간 계약은 유지한다. 현재 claim·retry·테스트가 동일한 now 계약을 사용하므로 동작 변화가 작고 결정론적 테스트가 가능하다. 여러 호스트의 시계가 크게 어긋나는 문제는 별도 DB-clock 통합 hardening으로 미룬다.
핵심 위험: 만료 비교를 일부 SQL에만 넣으면 오래된 워커가 다른 경로로 상태를 바꿀 수 있다. 따라서 captureCandidates의 select/update, complete의 선행 select/final update, heartbeat/fail update 모두에 같은 조건을 둔다.

불변식

  • 현재 claim의 id + attempt + leaseToken이 맞고 lease_expires_at > now일 때만 claim-bound write가 성공한다.
  • 두 번째 visibility 결과에서 제외된 optional recommendation은 같은 실행의 최종 content에 들어가지 않는다.
  • source issue의 공개 상태에 대한 기존 complete 검사는 유지한다. optional recommendation의 이후 변화는 기존 read-time filtering 정책을 유지한다.
  • 만료 write 거부는 정상 stale 경로로 처리하며, 오래된 워커가 새 워커의 성공·재시도 상태를 덮어쓰지 않는다.

배포 설정, migration, DB schema 변경은 없다. 배포 시 새 batch 코드와 core 코드가 함께 배포되어야 하며, 롤링 중 구버전 워커가 잠시 남아도 token·expiry 조건으로 새 결과를 덮지 못하는 것이 목표다.

검증 계획

  1. 단위: visibility mock이 첫 번째 조회에서는 후보를 보이고 두 번째 조회에서는 숨기도록 만들어, 완료 content에서 해당 후보가 사라지는지 확인한다.
  2. DB lifecycle: 만료 claim 각각에 대해 heartbeat·complete·fail이 false/무변경인지 확인하고, claim 후 새 attempt가 처리되는지 확인한다.
  3. 후보 저장: 만료 claim의 captureCandidates가 STALE_CLAIM으로 거부되고 candidates JSON이 변하지 않는지 확인한다.
  4. 회귀: source issue 공개 상태 검사, 정상 heartbeat 연장, 정상 complete/fail, 기존 token fencing을 유지하는지 확인한다.
