# 3단계: 이슈 파생 데이터 생성

- 상태: `APPROVED` — 사용자 검토·승인 완료
- 작성: 2026-09-20

## 기존 구현 검토

- `apps/batch/src/pipeline/openAi.provider.ts`의 기존 생성기는 요약·요약 3줄·관점·용어·세대별 영향을 생성한다. 새 제목·사건 시각·분류·LLM 추정 중요도·후속 추적은 생성하지 않는다.
- 기존 관점은 nullable 배열이며 이해관계자 2개를 보장하지 않는다. 용어 설명도 기존 DB 조회 없이 생성한다.
- 기존 본문 수집기를 재사용할 수 있다. 기존 worker는 생성 후 검증·저장까지 연결되므로 새 3단계를 그 worker에 연결하지 않는다.
- DB에는 토픽·지역·entity와 4개 세대 코드가 있으나 독립된 세대 마스터와 용어 사전 테이블은 없다. 용어는 `issue_details.glossary` JSON에 이슈별로 저장된다.
- 중요도·최신성 저장 범위는 0~1이나 이번 방향에 해당하는 계산식은 정해져 있지 않다.

## 구현 범위 및 방법

1. 완료된 2단계 실행의 SELECTED 항목을 입력받아 선정 기사 최대 5개의 본문을 수집한다. 본문 확보가 2개 미만이면 보류하고 실패 원인을 남긴다.
2. 확보한 본문들을 한 번에 전달해 UX 라이팅 가이드에 따라 제목·사건 시각·요약·세대별 영향·관점·LLM 추정 중요도·후속 추적 설정을 생성한다. 시각 불명확 시 선정 기사 최초 보도 시각을 사용하고 대체 여부를 기록한다.
3. 분류는 DB 값의 명확한 이름·별칭을 먼저 규칙 매칭하고 애매한 항목만 LLM이 허용 목록에서 선택한다. 규칙 근거와 LLM 근거를 구분해 저장한다.
4. 사용자 요청에 따라 세대 테이블은 추가하지 않고 기존 4개 세대 코드를 그대로 사용한다. 용어 사전 테이블을 추가하고 기존 공개 이슈의 용어 설명을 초기 재사용 대상으로 삼는다. 상충 설명은 임의로 합치지 않는다. 새 용어 설명은 실행 결과에만 두고 검증 전 사전에 공개하지 않는다.
5. 생성 내용에서 용어를 추출한 후 정규화한 이름으로 DB를 조회하고, 없는 용어만 설명을 생성한다.
6. 서로 다른 이해관계자 관점을 반드시 2개 생성한다. 대치되는 입장일 필요는 없으며 직접 발언이 없는 대상은 기사에서 확인된 역할·적용 내용을 설명한다. 두 관점 모두 근거 기사 ID를 명시한다.
7. 중요도: `0.4 × min(기사수/50, 1) + 0.3 × min(언론사수/10, 1) + 0.3 × LLM 추정 중요도`. 기사수·언론사수는 2단계에서 저장한 시간·URL·제목 필터 후 검색 결과 기준이며 API 전체 검색 건수와 구분한다. LLM 추정 중요도는 LLM이 근거와 함께 0~1로 추정한다.
8. 최신성: `2^(-경과시간/72시간)`, 0~1 범위. 사건 시각과 계산 기준 시각을 함께 저장한다. 미래 예정 시각은 이미 일어난 사건 시각으로 사용하지 않는다.
9. 후속 추적 기간은 1~30일, 검색어 최대 3개로 제안한다. 실제 추적 등록은 5단계 공개 시 연결한다.
10. 독립 실행 테이블에 본문·생성 결과·분류 근거·계산 입력·사용량을 체크포인트로 저장한다. 중복 실행 방지·실패 후 재개·소유권 검증은 기존 단계 방식에 맞춘다.
