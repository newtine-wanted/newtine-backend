purpose · 목적
/api/feed의 동일 세션 직렬화와 긴 transaction 점유를 줄여 p95/p99 지연과 connection pool 압박을 완화한다.

R-01accepted · non-blocking riskissueFeed.service.ts:89-198에서 same session의 read·recommendation이 더 이상 process lock으로 합쳐지지 않는다.동시 요청이 늘면 중복 후보 조회·추천 계산이 CPU/DB read QPS를 키울 수 있다. 현재 승인 설계의 의도된 trade-off이며, 배포 후 p95/p99·pool wait·winner/loser를 보고 필요하면 bounded single-flight를 별도 설계한다.
R-02open · non-blocking verification gap단위 테스트는 in-memory winner와 transaction 경계를 확인하지만 실제 PostgreSQL의 두 transaction 간 PESSIMISTIC_WRITE 대기·EXISTING 경로는 실행하지 않았다.코드 경로와 schema 불변식은 일치하고 전체 unit은 통과했다. 배포 전 staging PostgreSQL에서 동일 sessionId + batchNo 동시 요청을 2개 instance/worker로 재현할 필요가 있다.

락 필요성 판정

현재 저장 구현에서는 필요하다. feed_batches의 primary key만으로는 동시 요청의 loser를 정상적인 EXISTING 결과로 만들 수 없고, feed_sessions.next_batch_no와 추천 상태 필드의 read-check-write도 보호해야 한다. 락을 없애려면 단순 삭제가 아니라 조건부 atomic claim과 INSERT ... ON CONFLICT 기반으로 저장 경계를 다시 설계해야 한다.

리뷰 판단: non-blocking risk만 있음. 승인 범위와 구현은 일치하고, 검증된 코드 오류·상태 손상·API 계약 위반은 발견하지 못했다. 이 판단은 production 배포 승인이나 실제 latency 개선 확정이 아니다.
