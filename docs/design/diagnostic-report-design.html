1. 목표와 범위

사용자가 신청하면 비동기로 생성하고, 완료된 보고서를 마이페이지에서 조회한다. 신청하지 않은 사용자에 대한 월요일 일괄 생성은 제외한다. 대기와 실패를 명시하며 완료 전에 결과가 있는 것처럼 응답하지 않는다.

성공 기준: 같은 사용자·기간 신청은 한 보고서로 수렴, 접수 이후 API 재시작에도 작업 유지, 본인 결과만 조회, 검증된 결과만 공개, 저표본·연결 없음도 정상 안내 결과 제공.

비범위: 정치 성향 추론, 이메일·푸시·SSE, PDF 내보내기, 일간 보고서, 성공 결과 재생성, 새로운 기사 수집, 전체 사용자 자동 생성. 알림 발송 시스템은 이번 요청에 명시되지 않아 추가하지 않는 제안이다.

3. 사용자 흐름 제안

  1. 보고서 화면 진입: 신청 가능한 기간, 현재 작업 상태, 최근 4개 주차의 결과를 조회한다. GET은 작업을 만들지 않는다.
  2. 사용자가 보고서 신청을 누르면 POST. 서버가 회원·기간을 검증하고 외부 호출 없이 입력 스냅샷과 QUEUED를 함께 저장한 뒤 응답한다.
  3. QUEUED/RUNNING 동안 생성 중 안내. 화면을 떠나도 생성은 계속된다. 기존 성공 보고서가 있으면 그 보고서의 실제 기간을 함께 표시한다.
  4. 화면이 활성일 때 3초 간격으로 상태를 조회하는 초기 제안. 백그라운드에서는 중지하고 복귀 시 갱신. 네트워크 실패 시 간격 증가. 추정 완료 시각·가짜 %는 제공하지 않는다.
  5. SUCCEEDED가 되면 해당 reportId의 결과를 읽고 새 보고서를 표시한다. 별도 푸시 없이도 재진입 시 완료 결과를 볼 수 있다.
  6. FAILED는 안전한 실패 안내와 재시도 가능 여부를 표시한다. 무제한 버튼 재시도는 허용하지 않는다.
문구 변경: “매주 월요일 자동 갱신 / 다음 생성 예정일” → “신청하면 생성됩니다 / 다음 신청 가능일”. 지난주 분석에 “이번 주 행동”이라는 문구를 붙이지 않는다.

4. 비동기 구조

신규 Redis/BullMQ 없이 PostgreSQL 대기열을 제안한다. 요청 저장과 메시지 발행의 이중 쓰기가 없으며, 기존 API/배치 경계를 유지한다. 워커는 별도 프로세스로 상시 polling하며 종료 신호에 신규 선점을 중단한다.

6. 기간·입력·출력 제안

기간 및 이슈 집계

G1 확정: 지난주 월요일 00:00 이상, 이번 주 월요일 00:00 미만(KST). 예: 2026-09-16 신청 → 09-07~09-14 미만. 마지막 행동이 LIKE이고 해당 LIKE가 기간 안에 있는 이슈만 한 번 집계한다. 주차 종료 뒤의 취소는 과거 입력을 바꾸지 않는다. 서버 수신 createdAt 기준이며 지연 도착을 과거로 소급하지 않는다.

신청 시 REPEATABLE READ의 짧은 DB 트랜잭션에서 현재 공개된 입력 이슈와 검증된 상세를 스냅샷으로 저장하고 QUEUED를 함께 commit한다. AI·벡터 후보 검색은 이 트랜잭션에 넣지 않는다. 요청 시각과 inputCapturedAt을 기록한다. 현재 상세 이력이 없으므로 이 고정 없이 신청 당시 내용을 나중에 재현할 수 없다. 표본 수와 분류 건수는 LLM이 계산하지 않는다. 추천 가중치로 비율을 만들지 않는다. 비공개·상세 누락 등 제외 건수도 기록한다.

보고서 본문

content: {
  schemaVersion: 1,
  analysisStatus: READY | INSUFFICIENT_DATA | NO_CONNECTION,
  issueCount, minimumIssueCount: 5, categoryCounts,
  connections: [{label, title, description, issueIds}],
  relatedIssues: [{issueId, reason}],
  majorIssueCategoryCodes,
  majorIssuesStatus: READY | NO_INTEREST | NO_CANDIDATES,
  majorIssues: [{issueId}],
  recommendationsStatus, recommendationCapturedAt
}
  • READY: 연결 1~3개. 설명 2~3문장, 서로 다른 입력 이슈 최소 2개 근거. 대표 근거 2개를 먼저 표시하고 전체 근거를 펼친다.
  • 5건 미만: INSUFFICIENT_DATA, 연결 생성 호출 생략. 0건이면 관심 분야를 정할 수 없으므로 관련 추천과 분야별 주요 이슈는 빈 배열 및 NO_INTEREST 안내를 제공한다. 보고서 페이지와 카드 탐색 진입은 유지한다.
  • 5건 이상이지만 연결 근거 없음: NO_CONNECTION. 형식·근거 검증 실패를 NO_CONNECTION으로 숨기지 않는다.
  • 조회 때 근거가 비공개로 바뀌었으면 해당 근거를 사용하는 연결 전체를 숨기고 contentAvailability 안내. 저장된 원본 분석 상태와 현재 노출 상태를 분리한다.

추천

Figma의 주간 스냅샷 요구에 맞춰 추천 ID·이유·표시용 요약도 성공 결과에 고정하는 제안. 재조회에서 새로운 후보로 바꾸지 않는다. 비공개 또는 이후 행동이 생긴 추천은 숨기며 개수가 줄 수 있다.

  • 함께 살펴볼 이슈: 공유 임베딩 재사용, 자기 자신·비공개·행동 이력·중복 제외, 최대 5개. 공유 임베딩의 모델·1536차원·inputVersion·현재 inputHash 일치를 확인한다. pgvector 정확 검색은 신규 구현이다. 입력 이슈별 후보 유사도를 계산하고 선정된 sourceIssueId를 보관해 추천 이유를 연결한다. 유사도를 “같은 사건” 또는 “반대 관점”의 근거로 단정하지 않는다. 이유 한 줄은 검증된 두 이슈의 주제·요약에서만 작성하고 근거가 불충분하면 후보 제외.
  • 관심 분야 주요 이슈 — G2 확정: 보고서 입력의 categoryCounts에서 건수가 가장 큰 분야를 선택한다. 추천 weight·온보딩 선호·누적 관심 수는 사용하지 않는다. 공동 1위면 모든 공동 1위 분야를 대상으로 하고 category displayOrder/code 순으로 번갈아 선택한다. 0건이면 NO_INTEREST, 해당 분야 후보가 없으면 NO_CANDIDATES 안내와 빈 배열을 반환하며 다른 분야로 자동 대체하지 않는다. 1~4건도 분야 선정·추천은 수행한다.
  • 별도 ReportMajorIssuePolicy에서 분석 대상 주간에 공개된 후보를 해당 최다 관심 분야로 필터링한다. 기존 feed의 MAJOR 자격인 importance 또는 freshness ≥ 0.7을 적용하고, importance 내림차순 → freshness 내림차순 → eventAt 내림차순 → id 내림차순으로 분야 내부 정렬한다. 공유 점수는 추천 입력을 고정하는 시점 값을 사용한다. 이미 행동한 이슈·비공개·분석 근거·관련 추천과 중복을 제외한다. 최대 5개, 3~5개 목표이며 부족하면 있는 만큼 제공한다. 이 규칙은 알고리즘 선정이며 기존 feed 개인화 순위는 변경하지 않는다.
  • 주간 좋아요 분포: Notion에 요구되므로 정수 categoryCounts 제공. 최종 화면에 넣을 위치는 프론트 구성 사항. 합계는 issueCount와 일치.
  • 임베딩 누락/추천 후보 부족은 빈 결과·부분 제공 상태로 명시. DB 장애는 정상 “후보 없음”으로 삼키지 않는다.

7. 불변식과 선점

  1. 동일 사용자·기간의 보고서는 DB UNIQUE로 하나만 존재. 성공 결과는 재신청·재시도로 덮어쓰지 않는다.
  2. 선점은 짧은 트랜잭션에서 대기 작업 하나를 선택·RUNNING 전환하고 새 lease_token을 발급한다. 여러 워커는 SKIP LOCKED 또는 동등한 원자 선점 사용.
  3. 외부 호출은 트랜잭션 밖. 완료 저장은 reportId + RUNNING + attempt_count + lease_token 조건의 conditional update가 성공할 때만 commit.
  4. 만료는 회수 가능 조건이다. 새 워커가 토큰을 바꾸기 전이면 기존 토큰의 완료를 허용하고, 먼저 commit한 전이만 유효하다. 회수로 lease_token을 잃은 워커는 결과·실패·heartbeat를 변경할 수 없다. 늦게 받은 결과는 폐기하되 외부 비용 발생 여부는 별도 기록.
  5. 입력 스냅샷은 접수 때 고정 후 재시도에서 재사용. 외부 호출 전과 결과 저장 직전 공개 상태를 재검증. 입력이 공개 중단되면 SOURCE_UNAVAILABLE로 종료하고 자동 재시도하지 않는 제안이며, 고정 입력을 조용히 바꾸지 않는다. 조회 시점에도 공개 여부를 다시 검사한다.
  6. AI에는 회원 식별자·인증정보를 보내지 않고 분석에 필요한 이슈 내용과 로컬 참조 키만 전달. 이슈 텍스트는 명령으로 취급하지 않는다.
  7. 검증은 구조·길이·근거 부분집합·건수·정치 성향 판정 금지·사실 근거를 포함한다. ID 검증만으로 설명의 사실성을 보증하지 않는다.
DB에 성공 결과를 한 번만 저장하는 것과 외부 AI가 한 번만 과금되는 것은 다르다. timeout/lease 만료 후 재실행은 외부 호출 중복 가능성이 있다. 이를 exactly-once 호출로 표현하지 않는다.

초기 설정 제안: 워커당 동시 1건, polling 1초, 외부 호출 timeout 60초, lease 180초·heartbeat 30초, 자동 3회/사용자 재시도 포함 총 5회, 수동 재시도 cooldown 60초. 이는 초기 구현 기본값이며 운영 성능 보장은 아니다. 실행 전체 제한 5분, 입력 이슈 최대 200건·스냅샷 UTF-8 최대 1MiB, LLM 입력 본문 최대 100,000자로 시작한다. 접수 상한 초과는 INPUT_LIMIT_EXCEEDED로 거절하고 일부를 전체처럼 분석하지 않는다. 공급자 컨텍스트/출력 한도와 맞지 않으면 설정 오류로 기동을 거절한다. 유사 후보는 입력별 상위 10개, 중복 제거 후 최대 50개로 제한하고 최종 5개만 선정한다. 총 시도 1~3은 일시 오류에 자동 실행하고 4~5는 사용자의 개별 재시도 요청에서만 실행한다. 영구 오류·SOURCE_UNAVAILABLE는 retryable=false이며 입력 변경 재생성은 지원하지 않는다.

관측: reportId/attempt/processExecutionId/단계/소요시간/안전한 오류 코드, 대기 최장 시간·RUNNING 만료 수·실패율·검증 탈락·사용량 불명 수. 원문 관심 내용·프롬프트·보고서 본문은 로그에서 제외한다. 보고서별 AI 사용량은 ai_usage_records에 nullable weekly_report_id를 추가하고 공유 AiUsageRepository로 추출하는 제안이다. 현재 runId 필수인 PipelineRunRepository를 보고서에서 호출하지 않는다. 보고서 행은 pipeline 소유 필드가 NULL이며, 기존 삭제 후 소유자 NULL 기록은 유지한다. 호출 전 RUNNING 기록이 실패하면 호출하지 않음, 호출 후 같은 usageId로 확정, 회수된 시도의 미완료 호출은 UNKNOWN. 소유권 종료 뒤 늦은 비용 정보가 도착하면 usage만 정정 가능하며 보고서 결과는 변경하지 않는다.

운영 실행: API와 별도 reportWorker 프로세스의 재시작 정책·환경변수·정상 종료를 배포 구성에 포함해야 비동기 기능이 완성된다. 새 worker 등록만으로 운영 기동이 되는 것은 아니다.

9. 제외한 대안

  • HTTP 요청 안에서 LLM 완료 대기: 요청 timeout과 사용자 대기를 키운다.
  • API에서 메모리 fire-and-forget: 재시작 시 접수 유실.
  • 새 메시지 브로커: 현재 단일 DB 구조에서는 운영 요소·이중 쓰기 대책이 늘어 우선 도입하지 않음.
  • 완료 후 동적으로 매번 추천 재계산: Figma 주간 스냅샷과 충돌.
  • 저표본일 때 보고서 전체 차단: Figma 저표본 스펙과 충돌.
