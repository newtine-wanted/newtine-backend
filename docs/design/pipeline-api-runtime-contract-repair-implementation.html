현재 구현과 변경 경계

현재 상태
구현·이미지 재빌드·정적/단위/통합/계약/Compose live 검증 완료. 실제 Naver/OpenAI 외부 호출까지 확인했고 테스트 fixture는 exact ID로 정리했다.
SQL
libs/core/src/common/database/postgresSql.ts가 실제 PostgreSQL에서는 executeQuery로 원래 $n placeholder와 transaction context를 보존한다. pipeline repository의 모든 raw query가 공통 helper를 사용하고, report helper도 이를 재사용한다. job claim은 ownership CTE의 중복 id를 alias하고 returning j.*를 사용해 실제 job ID를 보존한다.
HTTP query
apps/api/src/onboarding/onboarding.controller.ts, apps/api/src/issue/feed.controller.ts, apps/api/src/interest/interest.controller.ts의 TypedQuery validator를 typia.http.validateQuery로 전환했다.
운영 설정
compose.yaml의 batch.environment에 provider/config/worker env를 연결하고, batch가 migration 완료 뒤 시작되도록 dependency를 추가했다. 현재 env로 Naver 검색·OpenAI 후보/본문 생성/검증/embedding 호출까지 확인했다.
금지 범위
schema/migration, 의도된 API payload, provider secret 값, 외부 API 계약은 변경하지 않는다.

설계 delta와 결정 이력

현재 없음. 승인 baseline의 SQL helper·query decoder·batch env 범위를 그대로 구현한다. 구현 중 계약·상태·실패 처리·검증 전략이 바뀌면 설계 문서를 재승인 필요로 되돌리고 멈춘다.

  1. 원래 PostgreSQL positional query와 transaction context를 보존한다.
  2. raw request 수동 파싱 대신 typia HTTP decoder를 사용한다.
  3. provider env는 API가 아니라 worker인 batch에만 전달한다.

영향 경계와 상태 전이

HTTP create -- DB only --> QUEUED run
                              |
                              +-- batch worker -- NAVER/OpenAI --> SUCCEEDED or FAILED

URL query -- validateQuery --> typed DTO --> service limit/offset/cursor

create의 202 persistence 성공과 worker 외부 provider 성공은 별도 상태 경계다. query 실패는 service 진입 전 400이어야 한다.

이슈 레지스터

PIPE-001 · 해결됨
공통 raw PostgreSQL execution helper로 교체했다. live create/get/replay는 202/200/202, QUEUED 상태의 retry/interrupt는 409 도메인 응답으로 확인했다.
PIPE-002 · 해결됨
claimJob의 UPDATE ... FROM owner RETURNING *가 소유 run의 id로 target job ID를 덮어쓰던 문제를 확인했다. ownership alias와 returning j.*로 수정하고 job usage·stage·failure 전이를 live 재검증했다.
QUERY-001 · 해결됨
세 TypedQuery 사용처를 HTTP decoder로 전환했다. 유효 query는 200, limit=0, 비정수 limit, 빈 cursor는 400으로 확인했다.
ENV-001 · 해결됨
batch에 env 매핑과 migration dependency를 추가했고 현재 값으로 실제 Naver/OpenAI 호출을 완료했다.
