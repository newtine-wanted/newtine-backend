현재 구현

승인 범위의 기존 구현과 리뷰 후속 범위의 수정을 완료했다. 전체 점검에서 발견한 공통 예외·생성 계약·smoke 격리 결함도 보정했다. Nest CLI/Rspack 실행 경로와 class-validator·class-transformer 직접 의존성을 제거하고 Nestia·Typia 계약과 ttsc·ttsx 경로로 전환했다.

POST /issues/search 파일럿은 TypedBody·TypedRoute와 validateEquals를 사용한다. 유효 요청은 성공 data만 반환하고, 잘못된 요청은 GlobalExceptionFilter가 RFC 9457 application/problem+json으로 정규화한다. 4xx도 프레임워크의 원문 payload를 그대로 반사하지 않고 승인된 고정 detail을 사용하며, 5xx에서는 내부 payload를 버리고 INTERNAL_ERROR와 일반 detail만 반환한다. 5xx 로그는 예외 message 원문을 제외한 제한된 진단만 기록한다. generated/api, generated/e2e, generated/openapi.json은 공식 생성 명령으로 생성·검증한다. SDK·e2e는 Nestia를 직접 실행하고, scripts/openapi.mjs가 Swagger 생성 직후 ProblemDetails 실패 응답의 media type만 application/problem+json으로 이동한다. OpenAPI는 상대 서버 URL과 RFC 9457 실패 응답을 포함하고, 생성 TypeScript는 Bundler 해석 규칙으로 검사한다. smoke는 자식 API의 IPC 준비 신호와 실제 할당 포트를 확인한다.

IssueSearchService는 API request/response 타입을 직접 사용하지 않는다. type/issueSearch.mapper.ts가 IssueSearchRequest를 내부 IssueSearchInput으로 변환하고 service 결과를 IssueSearchResponse로 매핑한다. controller는 변환 함수를 호출해 HTTP 흐름만 조합한다. 내부 타입은 issueSearch.input.ts· issueSearch.output.ts에 두며, 현재 응답 JSON과 Nestia 생성 계약에는 변화가 없다. TypedException<ProblemDetails>가 API 예외 정의 객체로 상태 코드와 응답 schema를 Nestia에 선언한다. ApiException은 에러코드·HTTP 상태·title·기본 설명을 한 곳에서 관리하고, 글로벌 필터도 같은 정의를 사용한다. persistence가 연결되기 전까지 service는 가짜 업무 데이터를 만들지 않고 검색 결과를 빈 배열로 반환한다.

도메인 예외는 DomainException을 직접 생성하지 않는 추상 기반으로 바꾸고, 첫 업무 경계에 IssueException과 ISSUE_NOT_FOUND 코드를 추가했다. API adapter의 domainException.mapper.ts가 도메인 코드와 ApiException을 연결한다. 필터는 응답에 기존 네 필드만 남기고, exceptionName·domain·domainCode·apiCode· requestId를 구조화 로그로 기록한다. 매핑되지 않은 도메인 코드는 외부에 노출하지 않고 INTERNAL_ERROR로 처리한다.

typescript 6.0.3은 현재 ESLint 타입 분석기의 peer 범위를 유지하고, ttsc가 요구하는 TypeScript 7.0.2 실행 패키지는 지원 OS·아키텍처별 optional dependency로 lock했다. 현재 macOS arm64와 Linux x64 설치 계획을 확인했다.

설계 차이

리뷰 후 승인된 후속 설계는 세 가지다. G7-A는 생성 OpenAPI의 서버를 상대 경로 /로 고정해 호스트·포트를 노출하지 않는다. G8-B는 각 API operation에 RFC 9457 ProblemDetails 실패 schema와 400·404·409·500 응답을 생성하되, SDK의 기본 HttpError 예외 호출 방식은 유지한다. 생성물은 Nestia가 직접 만들고, source decorator와 SwaggerCustomizer가 실패 media type을 보정한다. G9-B는 Nestia가 생성하는 확장자 없는 상대 import를 후처리하지 않고 생성물 전용 Bundler typecheck로 검증한다. 전체 점검 보정은 이 기준선의 동작을 바꾸지 않고 세부 불변식을 보강했다. 5xx 응답은 내부 payload를 포함하지 않는다. smoke는 자식 프로세스의 준비 handshake와 실제 포트를 사용하고 각 요청에 timeout을 둔다. 이후 생성 단계 보완에서 route customizer는 제거하고 scripts/openapi.mjs가 최종 media type 보정을 담당하도록 변경했다.

후속 설계 승인 범위: 네 필드 실패 응답

기준선은 네 필드 실패 응답 설계다. 사용자가 구현을 승인한 범위는 title·status·detail·code만 반환하는 실패 계약이다. type·instance·errors와 별도 요청 경로 필드는 응답과 OpenAPI에서 제거한다. application/problem+json, 5xx 상세 은닉, x-request-id 헤더·로그 추적, 성공 응답의 data 형태는 유지한다.

소유 경계
GlobalExceptionFilter, ProblemDetails 타입, api.exception, unit·smoke·contract 테스트, 생성 산출물 및 관련 문서

G8 불변식

생성 SDK·e2e·OpenAPI 주변 TypeScript는 생성물 전용 Bundler module resolution에서 검사된다. API runtime build는 기존 ttsc NodeNext 경계를 유지한다.

5xx 응답 불변식
HttpException이 5xx이면 payload의 message·errors를 응답에 복사하지 않고 INTERNAL_ERROR와 일반 detail만 반환한다.
smoke 격리 불변식
API 자식이 IPC로 준비 신호를 보내고 알려준 실제 포트로 요청한다. 자식이 포트 충돌로 먼저 종료하면 smoke는 응답을 재사용하지 않고 실패한다.

첫 병렬 ttsc 실행에서는 Nestia source-plugin cache lock이 겹쳤다. 이후 ttsc 명령을 순차 실행해 stale lock을 회수하고 build를 통과시켰다. node --watch와 ttsc/register 조합은 파일 감시 한도(EMFILE)에 걸려 start:dev:api를 ttsx -P apps/api/tsconfig.app.json 일회성 실행으로 고정했다. 전체 점검에서 고정 포트의 기존 서버를 smoke가 검증할 수 있음을 확인해, API main의 IPC 준비 신호와 ephemeral port 기본값을 사용하도록 보정했다. 포트 충돌 재현 시 자식이 준비 전에 종료되고 smoke도 non-zero로 끝나는 것을 확인했다.

검증 공백과 잔여 위험

  • @newtine/api/*·@newtine/batch/*·@newtine/core/* path alias는 ttsc build output에서 상대 경로로 변환되고 API smoke에서 실제 모듈 로딩을 확인했다.
  • 생성 산출물은 현재 저장소에 남기며 contracts:check가 Nestia로 재생성한 뒤 계약 테스트와 생성 TypeScript Bundler typecheck를 실행한다. 생성 결과의 의미 기반 diff 정책은 CI 구성 시 추가한다.
  • TypeScript 타입 API(6.0.3)와 native compiler(7.0.2)는 별도 패키지다. 둘 중 하나를 업그레이드할 때 ttsc·Typia 변환과 ESLint peer 범위를 함께 재검증한다.
  • 초기 골격 리뷰에서 식별한 DB 자격증명 fallback은 development/test 외 환경의 명시적 필수값 검증으로 해결했다. API bootstrap graceful failure는 프로세스 종료 시 OS가 리소스를 회수하므로 초기 골격의 필수 조건이 아니며, 재시작·retry·테스트 재사용이 필요해질 때 운영 하드닝으로 추가한다.
  • 실제 PostgreSQL commit/rollback과 feature repository adapter의 DB 동작은 아직 확인하지 않았다. 현재 업무 entity/repository는 파일럿 범위 밖이다.
