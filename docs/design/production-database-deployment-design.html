운영 DB 스키마·기준 시드 배포 설계

운영 담당자가 SQL을 직접 실행해 PostgreSQL schema와 필수 reference data를 만들 수 있도록 production용 DDL·seed 쿼리와 사전 점검 계약을 정한다. 애플리케이션은 자동 migration을 수행하지 않는다.

목적
NEWTINE 운영 DB의 전체 스키마와 기준 시드를 버전 관리·배포하는 방식 확정
사용자
NEWTINE 백엔드 개발자와 배포 담당자
문제
현재 migration은 일부 기본 테이블을 저장소 밖의 선행 스키마로 가정하고 Compose SQL은 로컬 fixture라서 빈 운영 DB를 저장소만으로 재현할 수 없음
핵심 흐름
SQL 파일 검토 → 운영 DB 사전 점검 → DDL 실행 → 기준 시드 실행 → schema 검증 → API 롤아웃

이 설계의 성공 기준은 API나 Compose가 운영 DB를 몰래 바꾸지 않고, 운영 담당자가 검토 가능한 SQL을 순서대로 실행한 뒤 schema 계약을 확인하는 것이다.

제안 실행 모델

  1. production DDL과 seed는 사람이 검토·실행할 수 있는 별도 SQL 파일로 제공한다.
  2. 빈 DB와 기존 DB는 적용 대상이 다르므로, 운영 DB 상태를 먼저 확인하고 맞는 SQL만 실행한다.
  3. 기준 seed는 stable code/PK와 충돌 검사를 포함하며, 사용자·실제 entity master·기사 데이터는 별도 적재한다.
  4. npm run db:migrate, API startup, Compose init은 production DB 적용 경로가 아니다.

반드시 지킬 불변식

  • API startup은 schema sync나 자동 migration을 수행하지 않는다.
  • 동일 migration은 migration history와 DB lock으로 중복 실행되지 않는다.
  • seed는 stable code/PK와 ON CONFLICT 정책을 사용해 재실행해도 중복 행을 만들지 않는다.
  • 기존 운영 데이터가 있는 상태에서 destructive drop·무검증 타입 변경을 자동 수행하지 않는다.
  • migration 실패 시 API 롤아웃을 진행하지 않고, 실패 원인과 적용된 migration 상태를 확인할 수 있어야 한다.
  • 운영 entity master·publisher·article·admin 계정은 근거와 책임 주체가 정해지기 전까지 기준 seed에 포함하지 않는다.
  • 입력 범위·상태 enum·수치 범위 CHECK는 production DDL에서 제거하고, API·worker의 공통 validator가 저장 전에 책임진다.
  • PK는 유지한다. 애플리케이션의 ON CONFLICT가 직접 요구하는 unique key와 동시성 race를 막는 email·idempotency·주차 report unique도 유지한다.
  • FK는 account withdrawal의 사용자 cascade와 feed 자식 cascade, report usage의 SET NULL에 필요한 최소 집합만 유지한다. 나머지 issue/article/master 관계 FK는 앱 쓰기 경계에서 검증한다.
  • 인덱스는 실제 worker queue·lease·report 집계·개인화 lookup·account withdrawal 경로에만 둔다. 현재 코드에서 사용되지 않는 만료·catalog·중복 보조 인덱스는 제외한다.

아래는 기존 승인 baseline을 보완하는 후속 설계다. SQL 파일을 바로 덮어쓰지 않고, 이 정책 승인 뒤에만 001_schema.sql·003_verify.sql을 갱신한다.

보존·제거 기준
대상권고근거와 영향
CHECK 60개제거API·batch validator가 허용 상태·범위·상태 간 계약을 검사한다. summary JSON은 조회 시 사용하는 함수는 남기고, 저장 제약만 제거한다.
PK 29개유지식별자 조회, composite parent key, ON CONFLICT (id), 남겨둘 FK의 참조 대상에 필요하다.
UNIQUE필요한 것만 유지article URL, detail/task/embedding/impact upsert, preference upsert, pipeline idempotency, refresh token, 주차 report는 현재 SQL·동시성 계약이 직접 요구한다. feed session 내 issue 중복과 미사용 issue-entity 중복 방어는 앱 책임으로 옮긴다.
FK 40개12개 안팎으로 축소users의 member-owned cascade 9개, feed session→batch→item cascade 2개, ai_usage_records.weekly_report_id의 SET NULL 1개를 보존한다. 나머지를 제거하면 orphan 검증·삭제 순서를 앱이 맡는다.
인덱스 29개16개로 축소usage/run, job/run, embedding claim/pending, entity/relation lookup, interaction 최신·기간 조회, report claim/lease, user cascade 경로만 보존한다. feed guest/expiry, 작은 regions, 사용되지 않는 representative/category/region 보조 인덱스는 제외한다.
중요한 경계: unique key나 cascade FK를 삭제하면 단순히 “앱에서 한 번 더 체크”하는 수준이 아니다. 동시 요청에서 중복을 허용하거나, 탈퇴 시 자식 row 삭제를 앱 transaction으로 직접 구현해야 한다. 이 영향까지 승인 범위에 포함한다.

설계 승인 상태

승인됨 · 사용자가 2026-09-18 현재 대화에서 “ㄱㄱ”으로 G4-A·G5-A·G6-A를 명시적으로 승인했다.

구현 상태: 승인된 범위로 SQL 산출물과 검증 계약을 갱신 중이며, production DB에는 접속하지 않는다.
