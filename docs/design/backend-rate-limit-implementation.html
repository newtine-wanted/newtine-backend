승인된 baseline

백엔드 공통 Rate Limit 설계의 G1-A·G2-B·G3-A를 기준으로 한다. 사용자는 2026-09-17 KST “ㅇㅇ 해”로 구현을 승인했다.

G1-A
Cloud Run 인스턴스별 bounded in-memory token bucket. DB·Redis shared quota 없이 인스턴스별 best-effort로 동작하며 lifecycle 종료 시 상태 초기화.
G2-B
body parser 전 IP 전역 limiter와 auth·account·guest feed의 더 엄격한 override. raw forwarded header는 직접 파싱하지 않고 설정된 trust proxy hop만 반영.
G3-A
/health 명시적 예외. 초과 시 429 ProblemDetails와 Retry-After.

현재 구현

apps/api/src/common/middleware/rateLimit.middleware.ts에 Cloud Run 인스턴스별 bounded process-local token bucket과 공통 Express middleware를 구현하고, apps/api/src/main.ts에서 request context 다음·body parser 전에 등록했다. method와 canonical path(trailing slash 제거)로 endpoint override를 선택하며, body parser 뒤에는 login/signup의 canonical email SHA-256 account bucket을 추가했다. DB·Redis에는 rate limit 상태를 기록하지 않는다. 이번 구현은 승인된 G1-A·G2-B·G3-A 범위 안에서 확인된 경계 이슈를 보완했다.

  • 전역 기본값은 IP별 분당 120회이며, signup/login/logout 10회, refresh 20회, GET /feed 30회, POST /issues/search 60회로 더 엄격한 override를 둔다. 모든 수치는 환경 변수로 조정한다.
  • /health는 명시적으로 bypass한다. 제한 초과는 downstream parser·guard·controller·DB에 진입하지 않고 429 ProblemDetails, Retry-After, RateLimit-* 헤더를 반환한다.
  • Express의 request.ip를 사용한다. 기본 RATE_LIMIT_TRUST_PROXY_HOPS=0에서는 직접 peer IP만 사용하고, 설정된 hop 수가 있을 때만 Express trust proxy 결과를 반영한다. raw forwarded header는 직접 파싱하지 않는다. bucket map은 RATE_LIMIT_MAX_KEYS와 idle TTL로 bounded하며 eviction·429를 민감정보 없이 구조화해 기록한다.
  • scripts/rate-limit-smoke.mjs와 test:smoke:rate-limit로 실제 bootstrap의 parser 전 global/endpoint/account 429, trailing slash 경로, forwarded-header 우회 방지, health bypass를 회귀 검증한다.

영향 경계와 불변 조건

  • 제한된 요청은 body parsing, Argon2, JWT DB 조회, guest feed_sessions insert 전에 종료한다.
  • 인스턴스별로 Express가 계산한 정규화 IP를 key로 사용하며 raw forwarded header를 직접 신뢰하지 않는다. endpoint override는 trailing slash 변형에서도 동일하게 적용한다.
  • bounded in-memory 상태는 key 수·idle TTL을 넘어서 무한히 증가하지 않는다.
  • /health는 liveness probe를 위해 제한하지 않는다.
  • 429는 application/problem+json, RATE_LIMITED, Retry-After를 제공하고 downstream side effect를 만들지 않는다.
  • 다중 인스턴스 전역 shared quota와 DB·Redis 전환은 승인 범위 밖이다. Cloud Run scale-out에서는 인스턴스별 quota가 독립적으로 동작한다.

핵심 HTTP 증거
동일 email의 두 번째 auth 요청이 trailing slash 경로에서도 account 429가 되었고, malformed JSON 요청이 body parser 400보다 먼저 endpoint/global 429가 되었으며, 임의 X-Forwarded-For로 endpoint bucket을 우회하지 못했고, global quota 소진 뒤에도 GET /health는 200이었다.
현재 공백
실제 운영 트래픽 기반 quota tuning, 다중 API 인스턴스의 shared quota, Cloud Run ingress의 실제 proxy hop 수 검증과 운영 설정, Prometheus 같은 별도 metrics collector는 이번 범위에서 검증·추가하지 않았다.

잔여 위험

  • per-instance limiter는 lifecycle 종료 시 초기화되고 Cloud Run 다중 인스턴스에서 quota가 공유되지 않는다.
  • 정확한 quota 수치는 실제 트래픽·Argon2 비용·DB p95 측정 후 운영 조정이 필요하다.
  • 현재 구현 범위에서는 외부 gateway·WAF·Redis를 추가하지 않는다. rate-limit 429는 구조화 로그와 표준 응답 헤더로 관찰하며, 별도 metrics collector 연결은 후속 운영 항목이다.
