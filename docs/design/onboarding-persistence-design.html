온보딩 PostgreSQL 영속화

승인된 온보딩 API 설계와 현재 reference adapter를 실제 PostgreSQL 데이터 모델에 연결하기 위한 후속 설계다. 소셜 로그인·토큰 발급은 계속 제외하며, principal은 기존 seam을 사용한다.

목적
온보딩 API의 PostgreSQL 영속화 경계와 migration 계약 확정
사용자
NEWTINE 백엔드 개발자와 기획 결정자
문제
프로세스 재시작 시 사라지는 reference state를 기존 users·entities·선호 모델에 연결
핵심 흐름
기존 기준선 확인 → schema delta 결정 → ORM/migration 결정 → adapter 구현 → DB 검증

설계 시점 확인 상태

  • 현재 API 계약, 상태 전이, 가중치 규칙은 onboarding-api-design.html에 승인되어 있다.
  • CoreModule의 MikroORM 설정은 entities: [], ensureDatabase: false다.
  • migration 명령과 업무 ORM entity가 아직 없다.
  • 로컬 ERD에는 users, entities, issue_categories, user_category_preferences, user_entity_preferences가 있다.
  • 승인된 G9-B 지역 선호는 ERD에 없어서 새 master와 사용자 선호 관계가 필요하다.
이 문서는 기존 API의 재설계가 아니다. 영속화가 API 결과와 상태 불변식을 바꾸면 이 기준선을 폐기하고 API 설계 승인을 다시 받아야 한다.

구현 결과와 검증 공백은 온보딩 API 구현 제어에 기록한다. 현재 구현은 delta migration을 제공하지만 base migration과 실제 PostgreSQL 실행 환경이 없으므로 운영 활성화 상태로 해석하지 않는다.

제안하는 schema delta

기존 ERD와 승인된 온보딩 결정을 연결하는 변경
대상변경불변식
users age_group nullable, onboarding_status와 onboarding_completed_at는 기존 컬럼을 사용 PENDING만 최초 complete/skip 전이. 완료 시각은 complete에서만 기록.
issue_categories code unique와 display_order를 추가하고 승인된 12개 topic seed를 적재 API의 topic code를 UUID에 하드코딩하지 않는다. seed code가 계약의 기준이다.
user_category_preferences 기존 (user_id, category_id) unique를 사용해 topic +2 행이 있으면 weight에 2를 더하고, 재설문은 이번 범위에서 terminal 상태를 반환.
entities / user_entity_preferences 기존 active entity를 name prefix/type으로 조회하고 사용자 선호에 +2 비활성·없는 entity와 중복 선택은 전체 요청을 거절.
신규 regions / user_region_preferences 17개 시도 seed, 사용자별 region code + weight, (user_id, region_code) unique 최초 선택마다 +1. 빈 집합은 전국 이슈 선택으로 유지.

transaction과 adapter 경계

  1. API가 principal user id와 body를 검증한다. body/query의 user id는 사용하지 않는다.
  2. 한 PostgreSQL transaction에서 해당 users 행을 FOR UPDATE로 잠근다.
  3. 사용자가 없으면 401로 종료하고 새 users 행을 만들지 않는다.
  4. 상태가 COMPLETED/SKIPPED면 선호 조회·변경 없이 저장 snapshot을 반환한다.
  5. PENDING이면 topic/entity/region master를 확인하고 상태·나이·선호를 함께 저장한다.
  6. DB commit 뒤 기존 API output으로 변환한다. 피드 호출은 transaction 밖이다.

ORM adapter는 현재 OnboardingRepository port 뒤에 둔다. reference in-memory adapter는 테스트 fixture용으로 남기고, production provider는 PostgreSQL adapter로 교체한다. 실제 auth provider 연결은 이 단계에서도 하지 않는다.

권장 구현 선택

  • migration: @mikro-orm/migrations를 도입하고 versioned migration으로 schema와 seed를 관리한다.
  • ORM: users, entities, issue categories, preferences, regions를 MikroORM entity로 등록한다.
  • topic mapping: category UUID를 코드에 넣지 않고 issue_categories.code로 조회한다.
  • entity master: 운영 migration에는 임의 인물·정당·기관을 넣지 않는다. test fixture와 별도 운영 적재 절차를 둔다.
  • migration boundary: 기존 base tables가 이미 존재한다는 delta migration을 우선하고, 빈 DB 초기화 migration은 별도 baseline으로 분리한다.
마지막 항목은 특히 중요하다. 현재 저장소에는 업무 table을 생성하는 baseline migration이 없으므로, delta migration만 추가해도 빈 PostgreSQL에서 바로 부팅된다고 주장할 수 없다. 기존 issue category의 이름·참조가 승인된 12개 code로 정규화되지 않으면 migration은 taxonomy가 조용히 분리되지 않도록 실패한다. 그런 환경은 별도 legacy mapping migration을 먼저 적용해야 한다.

설계 질문

P1 — migration은 기존 base table을 전제로 할까?

A: 기존 users/entities 등 base migration이 선행된 환경에 onboarding delta만 추가(권장). B: 모든 ERD table을 이번에 baseline으로 생성. A는 범위를 통제하지만 현재 빈 DB 부팅에는 선행 작업이 필요하고, B는 unrelated schema까지 책임진다.

P2 — topic seed를 어떤 테이블 계약으로 둘까?

A: issue_categories에 stable code/display_order를 추가(권장). B: API 코드와 category UUID 매핑을 애플리케이션 상수로 고정. A는 DB seed와 API가 같은 계약을 공유하고, B는 migration과 코드가 쉽게 어긋난다.

P3 — age 컬럼 이름은?

A: ERD와 동일한 age_group(권장). B: onboarding_age_group로 온보딩 전용성을 표시. A는 기존 ERD와 후속 조회를 맞추고, B는 기존 문서·쿼리 변경이 늘어난다.

P4 — 운영 entity master seed를 포함할까?

A: 운영 migration에는 넣지 않고 fixture·적재 절차만 제공(권장). B: 임시 명단을 넣어 즉시 선택 가능하게 함. A는 근거 없는 운영 데이터를 만들지 않고, B는 명단 출처·관리 책임이 필요하다.

P5 — DB adapter 구현 방식은?

A: MikroORM entity + migrations + repository adapter(권장). B: raw SQL adapter와 SQL migration. A는 프로젝트 ORM 규칙과 transaction manager를 공유하고, B는 SQL 제어가 직접적이지만 mapping·test harness를 별도로 만든다.
