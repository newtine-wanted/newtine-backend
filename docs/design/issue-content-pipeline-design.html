재시도는 같은 실행 기록의 현재 상태를 갱신한다. 최초 시작 시각은 유지하고 finished_at은 재개 때 비운다. attempt/execution_id로 현재 시도를 구분하고 사용량은 시도별로 남긴다. 전체 단계별 스냅샷·과거 결과 버전은 도입하지 않는다. 자동 기간 삭제는 이번에 구현하지 않으며 보존 정책은 운영 검증 필요 항목이다.

워커·트랜잭션 제안

  1. 장기 실행되는 단일 배포 프로세스의 pipelineWorker 모드가 DB를 주기적으로 조회해 가장 오래된 대기 run을 선택하고 조건부 UPDATE로 QUEUED→RUNNING을 선점한다. 실행 환경은 프로세스당 고유 execution_id와 실제 PID/컨테이너 식별자를 로그로 대응한다. worker를 API 요청마다 새로 띄우지 않는다.
  2. 후보를 최대5개 순차 판정하고 직전 등록한 미공개 초안도 포함해 비교한다. 초안+seed 연결+job 등록은 한 짧은 트랜잭션이다. 이 초기 경로의 이슈 등록자는 단일 워커로 제한하며 다른 등록 경로 추가 시 동시성 설계를 다시 검토한다.
  3. job은 원자 선점 후 SEARCH/FETCH/GENERATE/VALIDATE를 같은 프로세스의 별도 단계로 수행한다. 외부 호출은 트랜잭션 밖에서 한다. 현재 run attempt/execution_id와 job 상태가 유효한 경우만 단계·결과를 채택한다.
  4. 공개는 상세·영향·근거·검증된 후속 관계와 job 성공을 원자 반영한다. WITHDRAWN은 공개하지 않는다. 현재 영향 집합의 교체도 같은 경계다.
  5. 모든 job 처리 종료 후 집계를 계산해 run을 종료한다. 한 job의 실패 때문에 다른 job을 자동 취소하지 않는다. 발견 실패는 FAILED, 콘텐츠가 모두 실패면 FAILED, 일부 실패면 PARTIALLY_SUCCEEDED, 모두 성공/정상 신규0이면 SUCCEEDED.
  6. 공개 후 임베딩은 파생 데이터 보완이다. 실패해도 콘텐츠 job 성공과 공개를 되돌리지 않고 경고/누락 상태를 조회 가능하게 한다. 누락·input_hash 불일치 벡터를 별도 수동 batch 명령으로 보완한다. 기존 내용 생성 job 재시도로 임베딩만 고치지 않는다.

중단 복구 제안

소유 프로세스가 살아 있는지 불명확한 RUNNING은 자동 회수하지 않는다. 운영자가 기존 execution_id의 실제 프로세스 종료를 확인하고 run과 미완료 job을 실패 상태로 정리한 뒤 재시도 API를 호출한다. 종료 확인은 서버가 임의 true로 추론하지 않는다. 전역 활성 제약은 고아 RUNNING에도 적용된다. 재시도 전 DB에서 성공 커밋 여부를 재조회하고 성공 결과를 보존한다.

CONTENT 재시도는 지정 실패 job의 seed 기사부터 문맥·본문을 재확보한다. DISCOVERY 재시도는 저장된 query/limits로 다시 발견하며 이미 생성한 초안을 재조회한다. 기존 child job이 있으면 성공 job은 유지하고 INTERRUPTED 또는 요청에서 명시 선택한 실패 job만 재개한다. 근거 부족·의미 실패 job을 발견 재시도에 편승해 자동 재개하지 않는다. 재시도마다 query를 바꾸지 않는다. 출처가 사라져 사건 범위를 확인할 수 없으면 FAILED 유지. 의미 검증 실패는 자동 재생성하지 않지만 운영자의 명시적 재시도는 새로운 시도로 허용한다.

결정 반영 · 두 번째 라운드

사용자: “현재 job을 보면 단계를 어느정도는 나누는걸 고려하고 있어… 한번에 모든게 되는구조는 아님.” SEARCH → FETCH → GENERATE → VALIDATE를 별도 단계로 설계한다. 한 함수·한 트랜잭션으로 묶는 것으로 해석하지 않는다. 단계마다 다른 프로세스가 맡아야 한다는 요구까지 확정된 것은 아니다.

G4 · 실행 소유권과 중단 복구 (확정)

근거: 현재 batch는 databaseCheck를 실행하는 일회성 CLI이며 실행 관리자·워커 소유자 컬럼이 없다. 시간 경과만으로 RUNNING을 재실행하면 기존 실행과 새 실행이 동시에 결과를 채택할 위험이 있다.

권고: MVP는 생성 워커 1개, 한 프로세스에서 단계별 실행. 비정상 종료 시 실행 관리자가 이전 프로세스 종료를 확인하고 운영자가 명시적으로 복구한다. 원자 선점과 결과 채택 조건은 별도로 유지한다. 동시에 두 워커가 뜨지 않는 배포·실행 계약을 확정해야 한다. 단일 워커라는 이름만으로 중복 방지가 보장되지는 않는다.

대안: 여러 워커·자동 인계를 지금 지원하려면 소유자·실행 세대와 늦은 결과 거부 조건 등 작업 소유권 모델을 추가한다. 자동 복구·처리량 이점 대신 스키마와 운영 복잡도가 증가한다. 결정: 사용자 “초기에는 단일 워커와 종료 확인 후 수동 재시도로 하시죠”. 여러 워커·자동 인계 대안은 초기 범위에서 제외한다. 이 결정은 등록 조정·선점·복구 절차를 연다.

이전 라운드 기록: 이후 G5~G17에서 문맥 복원 방향·공급자·의미 검증·실행량을 확정했다. 실제 수집·품질·비용은 검증 필요로 남는다.

의존 트리

  1. G1 저장·재현 보장 → 초안 문맥·중단 복구 → 단일/복수 워커·실행 소유권
  2. G2 공개 경계 + G3 연결 의미 → 생성 입력·검증 규칙 → 품질 평가·공개 중단 절차
  3. 실제 공급 경로·샘플 확보 → 독립 근거 확보율 → 수집량·호출 상한·모델 평가
  4. 처리 목표·동시성 → 예산 측정/예약 수준 → 운영 중단·재개 조건
  5. 모든 물질적 결정 종료 → 공유 이해 확인 → 별도 HTML 통제 점검 → 별도 구현 승인

현재 정책 분기는 G17까지 해결했다. 실측이 필요한 항목은 상단 검증 필요 목록으로 이관했고, 미실측을 성공으로 간주하지 않는다. 가정: 최신 ERD를 기본 권고로 삼되, 문서 충돌을 최신 날짜만으로 자동 확정하지 않는다.

G5 · 소스 기사 URL 기반 재확보 (방향 확인)
사용자 “소스 기사 url은 있을거 아닌가? 그거 기반으로”. 별도 범위 설명 저장 권고는 채택하지 않고 발견 당시 기사 URL·메타데이터를 출발점으로 재확보한다. 본문과 GENERATE 입력은 저장하지 않는다. articles.article_url은 있으나 초안/job과 발견 기사 사이의 명시적 연결은 현재 ERD에 없다. issue_articles는 G3에 따라 최종 근거 전용이다. 따라서 URL이 존재하는 것과 어느 초안의 출발 URL인지 아는 것은 별도다.
G5-L · 발견 기사 연결 (방향 확정)
사용자 동의: 발견 기사 ID 연결을 초안과 함께 저장한다. 구체 매핑 제안은 issue_seed_articles(issue_id, article_id)이며, 테이블명과 저장 형태는 최종 설계에서 확정한다. 여러 기사에서 후보가 나올 수 있어 복합 PK와 FK를 둔 다대다 참조를 제안한다. 발견 출처는 최종 근거로 자동 승격하지 않는다. 대안은 job에 발견 기사 ID 목록을 저장하고 서버 참조 검증을 수행하는 방식으로, 테이블은 줄지만 JSON 내부 FK 무결성은 별도 책임이다. 정확한 이름·DDL은 구현 승인 전 확정한다. 재실행은 저장된 기사 메타데이터와 재확보 본문으로 해당 사건을 재검증한다. 기사 삭제·내용 변경·한 기사 내 여러 사건으로 범위가 모호하면 FAILED 유지와 원인 기록, 임의 신규 의미 채택 금지. 출처 재확보는 동일 입력 복원을 보장하지 않는다.
G6 · 실제 네이버 뉴스 기반 (확정)
사용자 “우선은 실제 기사를 기반으로 해보자. 네이버 뉴스 기반으로”. 테스트 본문 우선 권고는 채택하지 않는다. 실제 검색·본문 확보·생성 평가를 이번 설계 범위에 포함한다. 외부 연동 구현·운영 공개 승인은 아직 없다.
공식 API 확인
네이버 뉴스 검색 API 공식 문서 확인 2026-09-13. originallink는 원문 URL, link는 네이버 뉴스 URL이며 네이버 미제공 기사는 원문 URL이다. description은 요약 패시지이며 전체 본문 필드는 없다. 검색 API는 Client ID/Secret 인증이 필요하다. API 샘플 호출·본문 추출 성공은 아직 검증하지 않았다. 검색 제공 시각과 언론사 최초 발행 시각을 동일하다고 가정하지 않는다.
G7 · 최초 본문 확보 대상 (확정)
사용자 동의: 네이버 검색 결과 중 네이버 뉴스에 본문이 제공되는 기사부터 확보 경로를 검증한다. 대상 구조를 좁혀 초기 실험을 할 수 있으나 원문 사이트에만 있는 기사는 빠져 기사·독립 근거 확보율이 줄어든다. 대안은 언론사 원문 사이트까지 처음부터 포함하여 개별 공급·추출 경로를 검증하는 것. 검색 응답의 link가 무조건 네이버 주소라고 믿지 않는다. 선택 뒤 실제 페이지 샘플·접근 가능성·본문 경계·리디렉션·실패 유형을 읽기 전용으로 검증하고, 요청 제한 및 접근 정책을 확인한다. 접근 차단은 우회하지 않으며 확보 실패로 처리한다.

G11 · 운영자 인증 (별도 설계·이번 범위 제외)

공식 Node SDK를 사용하는 어댑터에서 Responses API 호출. JSON Schema 기반 strict Structured Outputs를 사용하고 파싱 결과를 서버 도메인 규칙으로 다시 검증한다. refusal·incomplete·빈 출력·참조 오류는 성공 결과로 채택하지 않는다. 생성과 검증은 각각 독립 요청이며, 네이버 검색·본문 확보는 서버 어댑터의 책임이다.
상태와 보관
각 호출은 store:false, 대화 연결 없이 현재 입력만 전달하는 방향. 이는 Responses의 응답 저장 설정이며 공급자의 모든 로그 보존이 없어짐을 보장한다고 표현하지 않는다. 본문·전체 프롬프트·원시 응답은 서비스 DB/로그에 남기지 않는다. 모델·작업 종류·프롬프트 버전·사용량·요청 식별자 등 운영 메타데이터 저장 범위는 최종 스키마에서 확정한다.
재시도 책임
SDK 자동 재시도는 끄고 호출 래퍼 한 곳에서 추가 1회 상한을 관리하는 설계. 실제 재호출마다 별도 ai_usage_records를 기록한다. 인증·잘못된 요청·의미 검증 실패는 재시도하지 않는다. 일시적 전송/서버 오류만 제한적으로 재시도한다. 결과 불명 타임아웃은 UNKNOWN이며 재호출의 추가 비용 가능성을 유지한다. 시간 제한은 호출 운영값 초안을 따른다. backoff는 지수 대기와 jitter를 사용하되 1회 재시도/요청 시간 예산을 넘지 않게 최종 구현 계약에서 고정한다.
사용량과 오류의 분리
HTTP/API 호출 완료는 성공이어도 출력이 의미 검증에서 거절되면 job은 실패할 수 있다. 사용량을 0으로 덮지 않는다. 비용은 실제 반환 모델·입출력/캐시 토큰과 확인한 단가를 기준으로 추정하며, 미측정은 NULL이다. DB usage 기록 실패가 임의 외부 재호출로 이어지지 않게 한다.
남은 모델 계약
단계별 입력/출력 토큰 상한·reasoning effort·타임아웃은 초기 모델 결정 뒤 제안한다. 임베딩 모델·차원은 별도 명세로 닫는다. 최종 설계에서 요청·응답 스키마와 실패 유형별 테스트 명령을 명시한다.

공식 자료 확인 2026-09-13: GPT-5.4 Mini (Responses·Structured Outputs·snapshot 지원), Structured Outputs (거절/불완전 출력 처리), Responses API (store:false). 공식 문서가 한국어 뉴스 생성·검증 품질을 보증하는 것은 아니다.

G16 · 임베딩 모델·차원 (확정)

사용자 “ㅇㅇ”로 확정: OpenAI text-embedding-3-small, 1536차원으로 시작한다. 공식 임베딩 문서에서 기본 차원을 확인했다(2026-09-13). PostgreSQL의 issue_embeddings.embedding을 vector(1536)으로 설계한다. 생성용 Responses와 별도로 Embeddings API를 사용한다.

저장 입력은 기존 ERD대로 최종 제목+1줄 요약. 신규 후보 검색 입력은 후보 제목+메타데이터에서 추출한 범위 설명이며 메모리에서만 사용한다. 유사도는 기존 이슈 후보를 찾는 신호이며 동일성 확정이 아니다. 텍스트 검색과 벡터 없는 초안 조회를 함께 유지한다.

대안은 더 큰 임베딩 모델을 도입하는 것으로 비용·저장량·연산량이 증가하고 실제 한국어 사건 검색 평가로 이점을 확인해야 한다. 초기에는 작은 모델을 기준으로 누락·중복/후속 구분 사례를 평가하는 것을 권고한다. 모델·차원 변경은 단순 설정 교체만으로 처리하지 않고 전체 벡터 재생성과 전환을 함께 설계해야 한다. 다른 모델 벡터를 섞어 비교하지 않는다.

임베딩 생성 실패는 공개 성공을 되돌리지 않는다. 누락 벡터의 재생성은 공개 콘텐츠와 input_hash로 수행하고 텍스트/초안 조회는 계속 유지한다. 구체 수동 보완 명령과 실행 순서는 최종 명세에서 기록한다.

호출 운영값 초안 · 최종 설계에 포함해 검토

실측 전 제안이며 G13의 호출 횟수 상한을 늘리지 않는다. 후보 추출/비교/생성 요청 입력은 각각 최대 10,000토큰, 검증 입력은 본문과 생성 결과를 포함해 최대 16,000토큰을 제안한다. 출력 상한은 추출 3,000, 비교 2,000, 생성 4,000, 검증 4,000토큰으로 시작하고 평가한다. 지시문·스키마 등 전체 입력을 계산하며 무조건 앞부분을 잘라 조건·반론을 잃는 방식은 피한다. 상한 안에서 근거를 보존할 수 없으면 실패한다.

LLM 요청당 타임아웃 90초, 네이버 검색 10초·본문 확보 15초, 임베딩 30초를 초기 제안한다. 타임아웃은 워커 프로세스 종료 증거가 아니며 자동 RUNNING 회수에 사용하지 않는다. SDK 재시도를 끄고 일시적 실패 추가 1회만 공통 경계에서 수행한다. max_output_tokens 부족으로 잘린 응답을 성공 처리하거나 자동 한도 증액하지 않는다. 금액 기준 엄격한 일일 예산 예약은 현재 범위에 포함하지 않으며 호출별 실제 사용량으로 추정 비용을 기록한다.

G17 · 수동 재시도의 상한 범위 (확정)

사용자 “권고대로 하자”로 2026-09-13 확정. G13의 상한은 수동 재시도의 각 시도에 적용한다.

확정: 운영자가 명시적으로 재시도할 때 시도별 상한을 새로 적용한다. 저장된 effective limits는 그대로 유지하며 자동 증액하지 않는다. 같은 시도 안의 자동 재시도는 추가1회 상한에 포함된다. 성공 job은 재처리하지 않는다. run의 attempt와 누적 호출·토큰·비용을 계속 표시한다.

예: 실패 이슈의 본문 확보가 첫 시도에서 최대5개 URL을 모두 사용했어도, 운영자가 새 시도를 요청하면 다시 최대5개 URL을 시도할 수 있다. 비용은 누적된다. 대안은 run 전체 누적 상한 유지로, 한도를 소진한 run은 수동 재시도해도 처리 불가가 될 수 있다. 누적 상한 대안은 채택하지 않는다. 공유 이해 확인으로 진행한다.

의미 검증·복구 상세 보완

검증 응답은 PASS/FAIL/UNCERTAIN, 주장별 근거 article ID, 독립 근거 그룹과 짧은 판정 사유, 충돌 목록을 갖는 구조로 제안한다. 서버는 입력 기사 집합 내 참조, 서로 다른 기사 ID, 독립 그룹2개 이상과 근거 연결을 검사한다. 독립성은 URL·언론사 수만으로 자동 확정하지 않고 모델의 판정도 오판 가능성이 있으므로 실제 평가 대상으로 남긴다. UNCERTAIN은 FAILED·미공개다. 모든 채택된 요약·관점·용어·영향 참조의 합집합만 issue_articles에 반영한다. 임시 주장별 근거는 메모리 검증용이며 본문/입력 영속화 정책을 바꾸지 않는다.

발견 완료 전 중단으로 후보 상태를 잃으면 저장된 query/effective limits로 DISCOVERY를 재실행한다. 이미 있는 공개·미공개 이슈를 다시 비교하므로 성공 이슈를 재생성하지 않는다. 원래 후보 집합의 재현은 보장하지 않는다. 발견이 완료되고 콘텐츠만 실패했다면 지정한 실패 job만 SEARCH부터 재시도한다.

임베딩은 공개 성공 이후 보완이며 embeddingPendingCount를 별도로 노출한다. 모델 식별자·차원·입력 조합 버전은 input_version에 함께 고정하는 안으로 모델 혼합을 방지한다. 보완 실패가 job 또는 run을 실패로 뒤집지 않는다.

구현 오류 재분석 · 재승인 필요

상태: 재승인 필요. 구현 후 수직 경로를 다시 대조한 결과, 기존 승인 문서가 전제한 일부 불변식이 현재 코드에서 성립하지 않는 것을 확인했다. 아래는 “오류로 확정된 항목”과 “환경·운영 검증이 필요한 위험”을 분리한 보완 설계다. 기존 본문 미저장·자동 공개·단일 워커·JWT 범위 밖 결정은 유지한다.

재분석 결과와 보완 범위
항목재분석 결론보완 설계
R1 · transaction contextEntityManager.transactional callback 안의 em.getConnection().execute가 context 인자 없이 호출된다. MikroORM은 이 경우 pool client를 사용할 수 있어 FOR UPDATE와 다중 상태 변경의 원자성이 보장되지 않는다. 오류로 확정.raw SQL은 유지하되 transaction callback의 모든 쿼리를 공통 helper로 감싸 em.getTransactionContext()를 connection execute에 전달한다. 외부 호출은 계속 transaction 밖에 둔다.
R2 · Idempotency-Key headerTypedHeaders에 validateEquals를 전체 Express header 객체에 적용한다. 표준 host/content-type/content-length가 포함된 정상 요청이 400이 된다. 오류로 확정.필요한 idempotency-key만 projection한 뒤 일반 typia.validate로 검증한다. 필수 header 계약과 OpenAPI 문서는 유지하고 표준 헤더 회귀 테스트를 추가한다.
R3 · Naver article fetch초기 scheme만 검사하고 redirect를 따라가며 response.text()에 바이트 상한이 없다. 배포망에 따라 SSRF·메모리 고갈 위험이 실제로 열릴 수 있다.현재 범위는 Naver News 페이지다. redirect hop을 수동 처리해 허용된 Naver host만 따라가고, 그 외 redirect는 source unavailable로 종료한다. content-type과 최대 응답 바이트(서버 내부 상수)를 검사한다.
R4 · duplicate registrationLLM 비교 전 조회가 최근 100건으로 제한되고, 등록 transaction에서 최신 중복 재확인이 없다. 단일 워커에서도 오래된 이슈나 별도 등록 경로가 있으면 중복이 가능하다. 설계 계약 누락으로 확정.등록 transaction에서 정규화 제목을 다시 조회하고 duplicate 결과를 job 생성 없이 반환한다. 기존 후보 문맥 조회 100건 제한은 비용 제어로 남기되 최종 gate로 사용하지 않는다.
R5 · embedding pending텍스트 공개 commit과 embedding 호출이 분리되어 commit 직후 종료하면 누락이 pending count에 반영되지 않는다. 데이터 보완 위험이지 텍스트 공개 자체의 오류는 아니다.이번 blocker 수정과 분리된 후속 hardening으로 기록한다. 공개 transaction에서 pending을 먼저 기록하고 embedding 성공 시 해소하는 상태·repair 경계를 별도 설계한다.
