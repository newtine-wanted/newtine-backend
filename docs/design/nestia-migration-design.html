OpenAPI 생성 단계 보완 — 2026-09-12

설계 승인됨 · Compact. 이번 절은 기존 실패 응답 생성 방식에 대한 후속 보완안이다. 아래 과거 승인 기록은 기존 범위에만 적용한다. 사용자는 생성 단계 보정 방향과 설계 보완을 확인했고, 2026-09-12에 “설계대로 구현”으로 이 범위의 구현을 승인했다.

목적은 컨트롤러의 실패 명세 중복을 줄이면서 Nestia 타입 분석과 실제 HTTP 실패 계약을 일치시키는 것이다. 기존 Nestia 계약 전환 설계의 동일 목적 후속 변경으로 이 문서를 갱신한다. 의사결정 상태: 생성 단계 보정으로 합의, 추가 선택 질문 없음.

변경 모델

  • API 계층의 공통 예외 정의 객체에 code, status, title, description을 둔다. 글로벌 필터와 명세가 이를 재사용하고 core의 ErrorCode에는 HTTP 의존성을 추가하지 않는다. description은 기본 detail이며 기존 안전한 상세 메시지 정책을 유지한다.
  • 컨트롤러는 원본 Nestia 객체 overload를 사용한다: @TypedException<ProblemDetails>(ApiException.InvalidArgument). 변환 함수나 자체 TypedException 래퍼를 추가하지 않는다.
  • ProblemDetailsResponses 데코레이터와 공통 상태·설명 자동 추가를 제거한다. 각 route에 실제 발생 가능한 실패만 선언한다. 같은 HTTP 상태의 복수 업무 코드가 필요해지면 별도 examples 병합 설계를 추가한다.
  • scripts/openapi.mjs가 로컬 Nestia Swagger 생성 실행, JSON 읽기, media type 보정, 최종 저장을 순서대로 담당한다. 서버를 실행하거나 Swagger UI를 공개하지 않는다.

생성 명령

"contracts:swagger": "node scripts/openapi.mjs"
"contracts:all": "npm run contracts:sdk && npm run contracts:e2e && npm run contracts:swagger"
"contracts:check": "npm run contracts:all && npm run test:contracts && npm run typecheck:generated"

nestia swagger·nestia all 직접 실행 결과는 보정 전 원본이므로 최종 산출물로 사용하지 않는다. README의 공식 생성 안내와 package script도 구현 범위에 포함한다. 생성 스크립트 재도입은 승인된 변경 방향이며, 응답 schema를 수작업으로 재정의하는 과거 방식은 도입하지 않는다.

보정 불변식과 실패 처리

  • HTTP operation의 400–599 및 4XX·5XX 실패 응답 중 application/json schema가 #/components/schemas/ProblemDetails를 직접 참조하는 항목만 처리한다. 다른 schema, 성공 응답, default 응답은 변경하지 않는다.
  • 기존 media object 전체를 application/problem+json으로 이동한다. schema, example, examples, encoding 및 응답 description·headers 등 다른 속성은 보존한다. 상태 코드나 schema를 추가하지 않는다.
  • 이미 보정된 항목은 유지한다. 두 media type이 함께 있으면 동일한 내용일 때만 JSON 키를 제거하고, 서로 다르면 오류로 종료하여 충돌을 숨기지 않는다.
  • Nestia 실행 실패 시 이전 파일을 읽어 성공으로 처리하지 않는다. JSON 해석·보정·저장 실패도 비정상 종료한다. 실패한 생성 결과는 배포·공유하지 않고 원인을 수정한 뒤 공식 명령을 다시 실행한다.
  • 현재 직접 참조 형태를 지원 범위로 둔다. 향후 schema 이름이나 참조 구조가 바뀌어 보정이 누락되면 최종 계약 테스트가 실패해야 한다.

검증 계획

공식 생성 경로로 생성한 결과에서 route별 정확한 실패 상태, 예외 정의의 설명, 네 필드 schema와 application/problem+json을 확인한다. 선언하지 않은 상태의 자동 추가가 없어야 한다. fixture 기반 검사로 대상 외 응답·schema·예시 보존, 재보정의 동일 결과, 충돌 감지를 확인한다. 생성 실패가 성공으로 처리되지 않는지도 검증한다.

구현 후 실행: npm run contracts:check, npm run typecheck, npm run lint, npm run format:check, 글로벌 필터 단위 테스트, npm run build:api와 npm run test:smoke. 이 문서는 계획이며 통과 기록이 아니다.

도메인별 예외 분리 — 2026-09-12

설계 승인됨. DomainException 하나에 도메인 문자열만 추가하는 방식은 선택하지 않는다. DomainException은 직접 생성하지 않는 추상 기반 예외로 두고, 업무 경계마다 IssueException·UserException처럼 구체 타입을 만든다. 현재 구현에는 첫 업무 경계인 IssueException을 추가한다.

  • 도메인 예외 파일은 libs/core/src/<feature>/domain/<feature>.exception.ts에 둔다. 각 예외 타입은 도메인 코드와 도메인 이름을 소유하며 core는 HTTP를 모른다.
  • ApiException은 HTTP 상태·title·description·외부 응답 code만 관리한다. 도메인 예외와 API 정의를 연결하는 매핑은 apps/api의 adapter에 둔다.
  • GlobalExceptionFilter는 공통 기반 타입으로 도메인 예외를 받고 매핑된 ApiException으로 네 필드 응답을 만든다. 매핑되지 않은 도메인 코드는 INTERNAL_ERROR로 숨긴다.
  • 로그에는 exceptionName, domain, domainCode, apiCode, requestId, HTTP method·URL을 남긴다. 응답 계약에는 도메인 내부 코드를 추가하지 않는다.

목표와 범위

API의 request/response 타입을 apps/api의 기능별 type에 두고, 컨트롤러에서는 Nestia의 @TypedBody, @TypedQuery, @TypedParam, @TypedRoute를 사용한다. 성공 응답은 기존처럼 data 래퍼 없이 직접 반환하고, 실패 응답은 GlobalExceptionFilter가 RFC 9457 Problem Details로 변환한다.

사용자와 외부 시스템의 body·query·path·header·cookie·file·batch 인자는 입력 어댑터 경계에서 항상 Typia로 런타임 검증한다. TypeScript 타입이나 mapper만으로 검증을 대신하지 않으며, 검증 실패는 INVALID_ARGUMENT으로 정규화한다. 이번 전환의 산출물은 검증·직렬화 경로, 컴파일러 실행 경로, 오류 매핑, 마이그레이션 규칙이다. 실제 업무 라우트가 없으므로 첫 라우트에 대한 파일럿을 전환 검증으로 사용한다.

확인된 근거

아래 항목 중 검증 도구와 실행 경로는 전환 전 조사 기록이다. 현재 적용된 기준은 백엔드 구현 컨벤션과 이 문서의 확정 결정 및 연결된 구현 제어 문서를 따른다.

  • 전환 전 API는 전역 ValidationPipe({ transform: true, whitelist: true, forbidNonWhitelisted: true })를 사용했다. 현재 API는 Nestia·Typia의 입력 decorator 검증으로 전환했다.
  • 전환 전 빌드는 Nest CLI의 Rspack builder이며, TypeScript는 5.9.3이고 테스트 실행은 tsx였다. 현재 빌드·개발·타입 검증은 ttsc·ttsx, 테스트는 Jest를 사용한다.
  • Nestia는 Typia 위의 NestJS 통합 계층으로, TypeScript 인터페이스에서 요청 검증과 응답 직렬화 코드를 생성한다.
  • 최신 공식 설정 경로는 TypeScript 7과 ttsc이며, 일반 tsc/tsx는 Typia 변환을 실행하지 않는다. 현재는 ttsc·ttsx 경로를 사용하므로 별도 Rspack transformer를 추가하지 않는다.
  • @TypedBody 검증 실패는 BadRequestException으로 전달되고, errors: [{ path, expected, value }] 입력 payload가 오더라도 전역 필터가 응답에 복사하지 않는다.

전환 흐름

확정할 설계 규칙

레이어 경계
Nestia 데코레이터는 apps/api adapter에만 둔다. libs/core의 feature/domain/entity/vo와 feature/repository port는 Nestia·HTTP에 의존하지 않는다.
타입 소유권
request/response 타입은 기능별 API type에 두며 ORM entity를 직접 응답 계약으로 사용하지 않는다.
오류 계약
Nestia가 생성한 검증 오류를 원문으로 노출하지 않고 GlobalExceptionFilter에서 프로젝트의 INVALID_ARGUMENT와 일반 detail로 정규화한다. 프레임워크 4xx payload와 요청 URL도 고정 문구로 정규화하며, 현재 실패 본문은 title/status/detail/code 네 필드다.
Problem type 식별자 — 최신 보완에서 생략
현재 범용 실패에는 type을 보내지 않는다. RFC의 기본값은 about:blank이며, 세부 오류 구분은 프로젝트 확장 필드 code가 담당한다. 별도 업무 처리가 필요한 도메인 오류가 생기면 안정적인 type URI를 별도 설계한다.
스키마 도구
API의 request/response 검증과 직렬화는 Nestia·Typia를 단일 계약으로 사용한다. 같은 라우트에 Zod 스키마를 중복 적용하지 않는다. 다만 환경 변수·설정이나 외부 시스템의 동적 JSON처럼 API 타입 계약과 다른 경계에는 Zod를 선택적으로 사용할 수 있다.
추가 필드
현재의 whitelist + forbidNonWhitelisted 의미를 보존하기 위해 Nestia의 validateEquals를 기본 정책으로 사용한다. validatePrune는 제거 후 처리하므로 선택하지 않는다.
컴파일러·산출물
Nest CLI/Rspack 빌드 경로 대신 ttsc·ttsx 기반 실행 경로를 채택하고, @nestia/sdk의 SDK·Swagger·e2e 생성을 이번 전환 범위에 포함한다. 생성 파일의 소유 위치와 커밋 여부는 구현 계약에서 고정한다.
예외 라우트
health, stream, redirect, binary처럼 일반 JSON 계약이 아닌 라우트는 표준 Nest decorator를 유지할 수 있다.

설계 의사결정 질문(grilling)

진행 상태: 완료 · G10 후속 합의: 실패 본문은 title/status/detail/code 네 필드만 유지한다. 구현 승인 대기. 기존 G1–G9 기록은 유지한다.

결정 트리: G1이 전환 순서를 정하고, G2가 빌드 경로를 연다. G3가 컨트롤러 적용 범위를 정한 뒤 G4의 입력 필드 정책과 G5의 오류 매핑을 고정한다. G6은 SDK/Swagger/e2e 산출물 범위를 결정했다. 후속 리뷰에서 G7은 Swagger 서버 URL 노출 정책, G8은 RFC 9457 실패 계약의 생성 범위, G9는 생성 e2e의 module resolution과 검증 경계를 결정한다.

이미 확정된 경계: Nestia는 apps/api adapter에만 두고 core domain/repository port는 순수하게 유지한다. 해결된 결정: G1-A·G2-B·G3-A·G4-A·G5-A·G6-A·G7-A·G8-B·G9-B. 주요 가정: 현재 업무 라우트와 DTO 클래스가 없어 첫 기능 라우트가 파일럿 대상이 된다.

G9-B는 Nestia 생성물의 확장자 없는 상대 import를 후처리하지 않고 생성물 전용 Bundler typecheck로 검증한다. runtime API build의 ttsc NodeNext 경계와 생성물 검증 경계를 분리한다. 세 항목은 G7-A·G8-B·G9-B로 결정되었고, 사용자 승인 후 구현 단계로 전환했다.

type, instance, errors를 본문과 선언·생성 계약에서 제거한다. requestPath나 다른 본문 필드는 추가하지 않는다. 검증 실패도 같은 네 필드로 반환하며 필드별 오류 목록은 제공하지 않는다. application/problem+json, HTTP 상태와 title/code 매핑, 5xx 상세 은닉은 유지한다. type 생략은 RFC에서 about:blank로 해석되며 code는 프로젝트 확장 계약이다. 알 수 없는 code는 HTTP 상태로 처리하고 detail을 파싱하지 않는다.

확인된 운영 경계: HttpRequestContextMiddleware는 서버에서 UUID를 만들고 x-request-id 응답 헤더를 설정한다. 본문 instance 삭제와 무관하게 이 헤더와 로그의 요청 ID 연결은 유지한다. core 예외와 트랜잭션, 성공 응답, DB 동작은 변경하지 않는다.

구현 범위와 검증

GlobalExceptionFilter, ProblemDetails, exceptionDefinition의 URI 매핑을 정리하고 사용되지 않는 검증 상세 변환을 제거한다. 단, 검증 예외의 code/status 판정은 유지한다. 단위·smoke·계약 테스트는 네 필드의 정확한 키 집합, 5xx 은닉, x-request-id와 로그 연결을 검사한다. Nestia로 SDK/OpenAPI/e2e를 재생성하고 관련 README·설계 및 구현 기록을 맞춘다.

검증 계획: npm run test:unit, npm run contracts:check, npm run typecheck, npm run lint, npm run format:check, npm run build:api, npm run test:smoke. 필수 type/instance 또는 errors에 의존하는 기존 소비자에는 호환성 영향이 있다. 외부 소비자 배포 여부는 미확인으로 남기며 이번 작업에 배포는 포함하지 않는다.

이전 type 단독 생략 제안 이력 — 최신 결정으로 대체됨

목적: 현재 오류 계약을 간소화하면서 RFC 해석과 클라이언트 동작을 명시한다. 사용자: 백엔드 개발자와 API 소비자. 문제: 범용 코드마다 URI를 중복 관리하고 있다. 핵심 흐름: 예외 → 전역 필터 → 오류 본문 → 클라이언트 처리. 기존 실패 계약의 보완으로 이 문서를 갱신한다.

확인된 코드: ProblemDetails.type은 필수 string이고, api.exception.ts는 네 코드의 URI를 별도 매핑한다. 필터의 세 응답 경로와 unit·smoke가 이 URI에 의존한다. 현재 구현은 변경하지 않았다. 외부 소비자의 배포·사용 여부는 이 저장소만으로 확인되지 않았다.

RFC 9457 §3.1.1에 따라 type 생략은 about:blank으로 해석된다. §4.2.1의 의미는 HTTP 상태 이상의 별도 문제 타입 의미가 없다는 것이다. 문서가 없다는 뜻이 아니다.

G10 — 현재 오류 응답에 type을 보낼 것인가
안 효과 비용과 제한
A 생략 — 권고 기본 타입 해석을 사용하고 URI 매핑을 제거 범용 RFC 소비자는 프로젝트 code의 의미를 알지 못함
B about:blank 명시 A와 같은 RFC 의미를 본문에 명시 고정 필드를 계속 전송하고 관리
C 에러별 URI 유지 RFC type으로 종류를 구분 안정적인 식별자·의미·문서를 정하고 변경 호환성을 관리

권고 A의 적용 범위는 현재 범용 오류다. HTTP 상태를 기본 처리 기준으로 사용하고, code·errors는 우리 클라이언트가 이해하는 문서화된 확장으로 유지한다. code가 RFC의 주 식별자인 type을 대체한다고 설명하지 않는다. 알 수 없는 code는 HTTP 상태에 따라 일반 오류로 처리하고 detail 문구를 파싱해서 분기하지 않는다. 

{
  "title": "Bad Request",
  "status": 400,
  "detail": "요청 값이 올바르지 않습니다.",
  "instance": "urn:uuid:8f75c728-6591-4370-9aec-75813f5158ca",
  "code": "INVALID_ARGUMENT"
}

검증 상세가 있으면 errors를 추가한다. Content-Type은 application/problem+json을 유지한다. 요청 endpoint를 담으려는 요구는 type과 별개이며 이번 범위에 응답 필드를 추가하지 않는다.

승인 후 변경 범위와 불변식

  1. 필터의 모든 응답에서 type을 생략하고 ProblemDetails 선언에서도 제거한다.
  2. PROBLEM_TYPE_BY_CODE, problemTypeForCode, 예외 정의의 type만 제거한다. HTTP 상태·title 매핑은 유지한다.
  3. Nestia로 재생성해 OpenAPI의 type 속성과 required 항목을 함께 제거한다. 생성 파일은 직접 수정하지 않는다.
  4. unit·smoke에서 type이 실제로 없음을 검사한다. status/code, 5xx 상세 은닉, instance, media type은 유지한다.

검증 명령: npm run test:unit, npm run contracts:check, npm run typecheck, npm run lint, npm run format:check, npm run build:api, npm run test:smoke. 현재 계약 테스트는 type 필수 여부를 검사하지 않으므로 해당 회귀 검사를 보강한다.

호환성과 재검토 조건

현재 required 필드의 삭제는 기존 클라이언트에 영향을 줄 수 있다. 배포된 소비자가 있다면 먼저 type 누락을 허용하도록 소비자를 전환한 후 서버를 변경한다. 아직 내부 골격이면 서버·SDK·테스트를 함께 갱신한다.

나중에 같은 HTTP 상태라도 서로 다른 업무 처리가 필요한 도메인 오류를 외부 계약으로 제공하거나, RFC type을 사용하는 도구와 연동한다면 구체적인 type을 다시 설계한다. 도메인이 생겼다는 이유만으로 자동 전환하지 않는다. about:blank에서 구체적인 URI로 바꾸는 것은 문제 식별자의 변경이며, 단순 필드 추가처럼 무조건 호환된다고 보지 않는다.

결정 트리: G10 표현 선택 → 소비자 호환성 확인 → 필터·타입·생성 계약 동시 변경. 현재 G10은 제안 상태다. URI 도메인·문서 서버는 보류하며 이번 범위에 만들지 않는다.

이해 점검: 미실시. G10 결정과 공유 이해 확인 후, type 누락의 RFC 의미와 알 수 없는 code의 처리, 기존 소비자의 required 필드 삭제 영향을 별도 점검한다. 설계 선택은 구현 승인이 아니다.
