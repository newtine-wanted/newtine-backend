Pipeline API 런타임 계약 복구

목적 (purpose)
현재 Compose 환경에서 pipeline API 등록·조회·재시도 계약과 query 입력 파싱을 복구하고 worker 환경 주입을 명시적으로 보장
사용자 (audience)
NEWTINE 백엔드 개발자와 로컬·배포 환경 운영자
문제 (problem)
MikroORM raw SQL placeholder 경계가 PostgreSQL positional placeholder를 처리하지 못해 pipeline API가 500을 반환하고, TypedQuery 검증기가 URL query를 디코딩하지 않으며, Compose batch에 pipeline provider 환경변수가 전달되지 않음
핵심 흐름 (core-flow)
HTTP 입력 디코딩·검증 → pipeline persistence transaction → batch worker 설정 주입 → API·DB·worker 경계 검증

추적 메모: 현재 실행 중인 Compose API의 live API 점검에서 확인한 런타임 결함을 다룬다. 기존 뉴스 공급자 연동 설계·이슈 생성 정책 설계와 목적·문제·핵심 흐름이 달라 새 동료 문서로 기록한다.

범위구조결정실패·복구검증이해 점검승인

목표와 범위

pipeline API의 DB persistence 경계가 실제 PostgreSQL driver를 통해 positional placeholder를 실행하도록 고친다. onboarding/entities, feed, me/liked-issues의 TypedQuery는 URL query를 숫자·문자열 DTO로 디코딩하고 검증하도록 고친다. Compose의 batch service에는 pipeline worker가 읽는 provider·AI config 환경변수를 전달한다.

성공 신호는 pipeline 등록·조회·retry·interrupt가 의도한 HTTP/DB 계약으로 응답하고, limit=1 같은 query 값이 실제 service 입력에 반영되며, invalid query가 400으로 거절되는 것이다.

이번 변경에 포함하지 않는 것

  • NAVER API HUB·OpenAI의 실제 credential 발급, 외부 quota, 실제 provider 인증 성공
  • pipeline 상태 머신·DB schema·migration·공개 API payload의 의도된 필드 변경
  • API 컨테이너에 worker 전용 provider secret을 복사하거나 저장소에 secret 값을 기록하는 것

확인된 현재 구조와 경계

확인된 환경
API 컨테이너의 NODE_ENV=production, DB_HOST=db, DB/JWT 값은 주입됨. OPENAI_API_KEY, NAVER_CLIENT_ID, NAVER_CLIENT_SECRET는 API에 없어도 등록 API의 선행조건이 아니다.
확인된 결함
MikroOrmPipelineRepository.enqueue()가 select ... $1를 ORM connection에 전달해 there is no parameter $1를 반환한다. 같은 repository의 transaction query도 같은 경계를 사용한다.
설정 결함
.env의 provider 값은 비어 있고, Compose batch.environment에는 해당 키 매핑 자체가 없다. AI 설정 파일은 이미지에 복사되어 기본 경로에서 읽을 수 있다.

설계 결정

  1. SQL 실행 경계: libs/core/src/common/database/postgresSql.ts에 PostgreSQL raw execution helper를 두고 pipeline repository가 이를 사용한다. helper는 EntityManager.getTransactionContext()를 우선하고, PostgreSQL driver의 executeQuery에 원래 $n query와 params를 전달한다. 이미 report repository에서 사용하는 경계와 같은 방식이다.
  2. query 디코딩: 세 TypedQuery 사용처의 validator를 typia.http.validateQuery<T>로 바꾼다. feed의 cursor ownership·unknown-query 수동 검증은 유지한다.
  3. Compose 환경: provider·AI config 키는 batch에만 ${...:-} 형태로 연결하고, batch가 migration 완료 후 시작하도록 dependency를 명시한다. 빈 secret은 빈 값으로 유지하며 fake key를 넣지 않는다.
  4. 검증 수준: unit/type/lint/contract gate와 live Compose HTTP smoke를 재실행한다. 실제 NAVER/OpenAI credential이 없으므로 provider 인증은 미검증으로 남기고 worker가 필요 환경을 읽는 설정 경계만 확인한다.

거부한 대안

  • 모든 SQL의 $n을 ?로 일괄 치환: 같은 query에서 positional parameter를 재사용하는 구문이 있어 params를 함께 재배열해야 하며 누락 위험이 더 크다.
  • API에 provider secret 주입: enqueue 단계는 provider 호출을 하지 않으며 secret 노출 범위를 불필요하게 넓힌다.
  • query를 controller에서 raw Request.query로만 수동 파싱: DTO 계약과 Nestia/typia의 공통 query decoder를 우회한다.

불변 조건과 상태 경계

  • pipeline create는 provider credential 유무와 무관하게 persistence가 가능하면 202와 run snapshot을 반환하고, worker 외부 실행은 별도 단계다.
  • idempotency key replay는 동일 request hash에 대해 같은 run을 반환하고, 다른 hash는 conflict로 남는다.
  • transaction query는 같은 transaction context에서 실행되어 retry·interrupt·issue registration의 lock/조건부 update 경계를 보존한다.
  • query DTO의 숫자는 문자열이 아닌 number로 service에 전달되며, limit=0, 비숫자 값, 범위 밖 값은 400이다.
  • provider secret과 OPENAI_API_KEY의 원문은 소스·설계·검증 출력에 기록하지 않는다.

실패·복구·운영

API persistence failure
HTTP 500과 구조화 로그에서 SQL/driver 원인을 확인한다. 수정 후 enqueue → get → retry/interrupt 경로를 DB fixture로 재검증한다.
worker provider key 누락
Compose가 빈 값을 worker에 전달하더라도 실제 provider 호출 전 명시된 외부 오류로 run이 실패한다. 이 변경은 키를 생성하거나 외부 호출을 우회하지 않는다. 운영자는 .env/secret store에 실제 값을 넣고 worker를 재시작한다.
AI config 누락·오류
batch bootstrap에서 config/pipeline-ai.yml 읽기 실패가 드러난다. 이미지 포함 여부와 PIPELINE_AI_CONFIG_PATH를 먼저 확인하고, 수정 후 worker를 재시작한다.
검증 fixture
live 테스트가 만든 user/run/issue/report fixture는 exact id·prefix로 정리하고 기존 feed session 등 사전 데이터는 삭제하지 않는다.

검증 계획

  1. focused source/build: npm run typecheck, npm run lint, pipeline/query 관련 unit test
  2. contract/build: npm run test:contracts, API·batch build 및 Compose image 재생성
  3. live HTTP: health, onboarding query valid/invalid, feed cursor, liked-issues pagination, admin pipeline create/get/retry/interrupt
  4. configuration: docker compose config와 batch container env key presence를 secret 원문 없이 확인
  5. external boundary gap: NAVER/OpenAI 실제 credential이 비어 있으므로 provider 인증 성공은 잔여 검증 항목으로 보고

설계 의사결정 상태 (grilling)

완료. 로컬 코드·컨테이너·로그가 원인을 분리했으며, SQL 경계·query decoder·Compose env 범위의 material frontier를 닫았다. 사용자가 소유해야 할 별도 정책 선택은 없고, 실제 provider credential 인증은 외부 상태 때문에 검증 필요로 설계 범위 밖에 남긴다.

G1 · SQL 방식
raw PostgreSQL helper 권고를 선택. positional parameter 재사용을 보존하고 transaction context를 잃지 않는다.
G2 · query 방식
typia HTTP decoder를 선택. 세 사용처를 동일하게 고쳐 계약 불일치를 막는다.
G3 · env 범위
worker 전용 env만 batch에 전달. API enqueue와 외부 provider 실행을 분리한다.
