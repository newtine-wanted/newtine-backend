현재 흐름과 목표 흐름

BuildKit의 registry cache는 Docker layer 공유에는 유효하지만 RUN --mount=type=cache의 디렉터리를 Cloud Build worker 사이에 보존하는 수단으로 전제하지 않는다. Cloud Build가 제공하는 GCS directory cache 방식으로 ttsc의 compiled plugin cache를 직접 복원·저장한다. 현재 저장소에는 cloudbuild.yaml이 없으므로 새 설정 파일을 추가해 trigger가 이를 사용하도록 연결하는 안을 우선 권고한다.

현재 권고 결정

  1. 빌드와 image 조립을 분리한다. Cloud Build의 Node step이 npm ci와 npm run build를 실행하고, Dockerfile은 이미 생성된 dist를 runtime image에 복사하는 역할만 맡는다.
  2. GCS에는 우선 ttsc/plugins만 저장한다. 현재 로컬 관찰값은 약 93MB이며, 3.1GB인 go-build 전체를 매 build 전송하지 않는다.
  3. cache key는 Linux·Node 24·lockfile hash를 포함한다. ttsc/Typia·TypeScript 버전 변경도 새 namespace로 분리하고, cache miss는 정상 cold build로 fallback한다.
  4. 빌드 성공 후에만 plugin cache를 GCS에 업로드한다. cache 복원·저장은 성능 최적화이므로 GCS 장애가 배포 자체를 막지 않게 한다.
  5. cache object는 lockfile hash별 경로를 유지하고, 저장 직후 최신 3개의 plugins.tgz만 남긴다. bucket lifecycle의 30일 삭제 규칙은 cleanup 실패를 위한 안전망이며, 정확한 개수 보존은 Cloud Build prune step이 담당한다.
  6. 이미지는 명시적인 docker push 한 경로만 남기고, 같은 image를 다시 push하는 images: 자동 push는 제거한다. 기본 worker와 GOMAXPROCS=1 GOGC=50, API·batch 순차 빌드는 유지한다.
Dockerfile
FROM node:24-bookworm-slim AS runtime
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev --omit=optional && npm cache clean --force
COPY dist ./dist
COPY config ./config
COPY scripts/migrate.mjs ./scripts/migrate.mjs

Cloud Build
restore GCS: ttsc/plugins/<platform>/<lock-hash>
TTSC_CACHE_DIR=/workspace/.cache/ttsc npm ci && npm run build
save GCS:  ttsc/plugins/<platform>/<lock-hash>  # build 성공 뒤
docker build -t <image>:$COMMIT_SHA .
docker push <image>:$COMMIT_SHA

RUN --mount=type=cache는 로컬·동일 builder 반복에는 유효하지만, 현재처럼 worker가 매번 바뀌는 Cloud Build에서 remote ttsc cache의 저장 경계로 사용하지 않는다.

불변식·실패 복구

  • runtime image의 실행 명령·환경·포트는 유지하고, Docker는 이미 생성된 dist만 조립한다.
  • Docker context에는 node_modules가 계속 포함되지 않으며, 빌드 산출물 dist는 runtime image 조립을 위해 context에 허용한다.
  • GCS cache가 없거나 손상되어도 npm run build가 plugin을 다시 컴파일하는 fallback이 남는다.
  • cache 복원은 best-effort이고, cache 저장은 build 성공 뒤에만 수행한다. cache 저장 실패가 image push·deploy 실패로 번지지 않도록 한다.
  • cache prune도 best-effort이다. 목록 조회·삭제 실패는 배포를 막지 않으며, 30일 lifecycle이 오래된 cache namespace를 최종 정리한다. 동시 build 중에는 prune 사이에 일시적으로 3개를 초과할 수 있다.
  • 다른 OS·CPU 아키텍처·Node·ttsc·Typia·TypeScript·lockfile 조합은 cache namespace를 분리한다.
  • cache object에는 build 산출물이나 비밀값을 넣지 않고 compiled plugin cache만 저장한다. bucket lifecycle로 오래된 namespace를 정리한다.

가장 큰 잔여 위험: GCS plugin cache가 실제로 ttsc: building source plugin 로그를 없애는지 2회 연속 build로 입증해야 한다. hit가 되지 않으면 그때만 go-build cache 추가 또는 별도 BuildKit cache-dance를 검토한다.

검증은 같은 trigger에서 (1) cache miss, (2) 동일 lockfile의 소스만 변경한 cache hit, (3) lockfile 변경으로 의도적인 miss를 각각 실행한다. hit 케이스에서 ttsc: building source plugin 로그가 사라지고, cache restore/save 실패가 배포 실패로 이어지지 않는지 확인한다.
