Docker ttsc 빌드 캐시 개선 설계

목적 · 결정 · 불변식·위험 · 설계 이해 점검

목적과 범위

목표
Docker 소스 변경 때 반복되는 ttsc 네이티브 플러그인 cold build를 줄인다.
범위
Dockerfile의 BuildKit cache mount와 중첩 node_modules를 제외하는 .dockerignore 보완을 적용한다.
비범위
ttsc/Typia 교체, GOMAXPROCS·GOGC 변경, 런타임 이미지 구조 변경, 애플리케이션 코드 변경.

확정 결정

  1. 중첩 dependency cache가 Docker context에 들어오지 않도록 .dockerignore에 중첩 node_modules 패턴을 명시한다.
  2. /app/node_modules/.cache/ttsc를 BuildKit cache mount로 보존한다.
  3. 캐시 id는 newtine-backend-ttsc로 고정하고 sharing=locked로 동시 plugin build 경합을 피한다.
  4. 기존 저메모리 설정은 유지하고, 컨텍스트 크기·연속 Docker build·산출물을 검증한다.
.dockerignore
**/node_modules/

Dockerfile
RUN --mount=type=cache,id=newtine-backend-ttsc,target=/app/node_modules/.cache/ttsc,sharing=locked \
    npm run build

호스트에서 확인된 약 3.2GB의 ttsc cache는 Docker context에 복사하지 않고 BuildKit builder가 별도로 보존한다.

불변식·실패 복구

  • runtime stage와 애플리케이션 실행 동작은 변경하지 않는다.
  • Docker context에는 dependency directory가 포함되지 않으며, context transfer가 수 MB 수준으로 줄어야 한다.
  • 캐시가 없거나 손상되어도 npm run build가 다시 plugin을 컴파일하는 fallback이 남는다.
  • sharing=locked는 같은 builder의 동시 빌드 일부를 직렬화할 수 있다.
  • 다른 아키텍처·컴파일러 버전으로 전환할 때는 캐시 id를 분리하거나 clean build를 수행한다.

가장 큰 잔여 위험: BuildKit cache mount를 지원하지 않는 CI builder에서는 문법 또는 캐시 동작이 달라질 수 있다. 그런 환경은 clean build로도 검증해야 한다.
