## 유지할 결정

| 항목             | 결정                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| 서비스 중심 단위 | 기사와 이슈를 구분한다. 카드는 이슈를 표현한다.                                                |
| 이슈 발견        | 제목·description으로 후보를 추출한 뒤 기존 이슈와 비교한다. 신규 확정 후 관련 기사를 수집한다. |
| 동일 이슈        | 단순 재보도는 새 이슈·생성 job을 만들지 않는다.                                                |
| 후속 전개        | 새 issue_id로 생성하고 검증된 FOLLOW_UP 관계로 연결한다.                                       |
| 기사 연결        | issue_articles는 근거 기사 전용이다.                                                           |
| 가공 결과        | issue_details에 현재 상세 1벌을 둔다. 전체 버전 스냅샷은 누적하지 않는다.                      |
| 본문             | 본문 영구 저장 테이블은 두지 않는다. 재시작 시 입력을 다시 확보할 수 있다.                     |
| 분류             | issue_categories 값 테이블과 대표 category_id를 사용한다.                                      |
| 행동             | LIKE / SKIP / PASS만 기록한다. dwell_time은 밀리초다.                                          |
| 보고서           | 마이페이지에서 지난주 보고서를 제공한다. weekly_reports에 상태·결과를 저장한다.                |
| 공개             | 검증을 통과한 초기 생성 결과는 자동 공개한다.                                                  |
| 개발 입력        | 실제 본문 공급 경로 미확정. 테스트용 본문으로 계약부터 검증한다.                               |
| 저장소           | PostgreSQL 사용. 임베딩은 pgvector 활용 방향이며 모델·차원은 미정이다.                         |

## 현재 구조의 한계

- 행동 없이 열람만 한 이슈까지는 정확하게 추적하지 못한다.
- stage만으로 검색 결과·본문·생성 중간값을 복구할 수 없다.
- 주간 분석의 최초 성공 결과는 고정하지만, 실패 후 재생성 입력 전체의 동일성은 보장하지 않는다.
- 사용자별 추천 결과와 주차별 주요 이슈 목록을 고정 저장하는 구조는 아직 없다.
- AI 사용량 기록만으로 엄격한 동시 예산 예약이나 보고서별 비용 추적을 보장하지 않는다.
- 본문 공급, 추천 점수, 워커 종료 확인, 보존 기간은 구현 단계별로 먼저 결정해야 한다.

새 테이블을 자동으로 추가하지 않고 [구현 계획의 미결정 목록](implementation-plan.md#미결정-사항)을 통해 닫는다.
