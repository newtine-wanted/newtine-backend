NestJS 기본 틀과 구현 전 점검

공유 이해 확인 및 feature별 repository 보완을 마쳤고, 사용자가 승인하여 구현을 시작한다.

API 계약·컴파일러 전환에 관한 최신 기준은 Nestia 마이그레이션 설계와 구현 제어 문서에서 관리한다. 이 문서는 초기 api·batch·core 경계의 기준선이다.

범위: 초기 api·batch·core 실행 골격 · 작성일: 2026-09-12 · 갱신일: 2026-09-12 · 작업 참조: 구현 연속 대화

폴더 구조경계오류 계약실행 계약구현 전 점검승인

목표와 범위

Nest CLI 모노레포의 api·batch 실행 앱과 core 라이브러리를 구성한다. MikroORM/PostgreSQL을 사용하며 domain·repository·transaction 경계를 분리한다. 성공 기준은 각 앱의 빌드·실행, DB 연결, 오류 계약, 컨텍스트 및 종료 처리의 검증이다.

제외 및 후속 범위

19개 테이블 전체 구현, 실제 업무 entity/repository, 뉴스·LLM 연동, 마이그레이션 실행, 배포, 데이터 변경, 큐·스케줄러·업무 재시도는 포함하지 않는다. 업무별 오류 문서와 도메인 코드, 실제 저장 원자성, batch 멱등성·동시 실행 방지는 해당 업무 구현 전에 확정한다.

변경 모델과 확인 근거

기존 설계 문서만 있는 저장소에 초기 실행 골격을 추가하는 설계다. 이번 턴은 이 HTML만 보완한다. Node v24.18.0, npm 11.16.0을 확인했다. Docker CLI는 있으나 현재 샌드박스에서 daemon socket 접근이 거부되어 DB 환경은 미확인이다. 실행 테스트 성공으로 기록하지 않는다.

UUIDv7 생성기는 값 객체가 아니라 서버 식별자 발급 책임을 가지므로 common/id에 둔다. issue/article 경로는 미래 기능의 배치 규칙이며 이번 구현에서 빈 업무 클래스를 생성하지 않는다. 폴더·자체 소스 파일은 역할 접미사를 점으로 분리한 camelCase, 클래스는 PascalCase. 자체 이름에 하이픈을 쓰지 않는다. 외부 패키지명과 Nest CLI가 요구하는 nest-cli.json 같은 도구 고유 이름은 변경하지 않는다. 기존 설계 HTML 경로는 링크 보존을 위해 유지한다.

소스 import는 @newtine/api/* → apps/api/src/*, @newtine/batch/* → apps/batch/src/*, @newtine/core/* → libs/core/src/* alias를 사용한다. 앱 root barrel alias는 만들지 않아 api와 batch를 서로 패키지처럼 참조하지 않도록 한다.

포트와 어댑터

유지할 경계

  • core → 앱 참조와 api ↔ batch 참조 금지. 앱 service의 MikroORM 및 구체 어댑터 직접 import 금지. DI 조립부와 core adapter에는 필요한 참조 허용.
  • core/application 없음. 유즈케이스는 앱별이다. 업무 도메인 규칙은 각 <feature>/domain 아래에 두고, 공유 도메인 기반 타입만 common에 둔다. entity는 MikroORM 엔티티를 겸하므로 완전한 ORM 독립성은 목표가 아니다.
  • repository는 feature별. 테이블과 일대일로 만들지 않고 일관성·저장 책임을 기준으로 나눈다. feature 간 계약 참조는 필요한 경우만 명시하며 구체 adapter끼리 결합하지 않는다.
  • request/response와 서비스 입출력은 feature의 type에 두고, 조회 계약은 해당 feature의 repository/type에 둔다. controller의 mapper가 API 계약과 서비스 타입을 변환하며 ORM entity를 HTTP 응답으로 직접 반환하지 않는다.
  • 사용자·외부 시스템 입력은 body·query·path·header·cookie·file·batch 인자를 포함해 항상 입력 어댑터 경계에서 런타임 검증한다. Nestia의 TypedBody· TypedQuery·TypedParam에 Typia 검증을 연결하고, TypeScript 타입이나 mapper만으로 검증을 대신하지 않는다.
  • TransactionManager 계약의 execute 콜백이 트랜잭션 경계. 성공 시 flush/commit, 실패 시 rollback. repository의 독립 flush/commit 금지. 모든 참여 adapter가 해당 컨텍스트의 EntityManager를 사용한다.
  • 요청/작업별 컨텍스트. 초기 계약은 중첩 트랜잭션을 지원 범위로 삼지 않고 명시적으로 거부해 모호한 부분 커밋을 피한다. 이 제한은 구현 승인 대상 세부 계약이다.

핵심 위험

DI 토큰만 분리하고 실제 구현이 다른 EntityManager를 쓰면 트랜잭션 경계가 깨진다. 컨텍스트 참여 검증이 필요하다. 연결 확인만으로 실제 feature repository의 저장 원자성을 보장하지 않는다.

응답 계약

이 절의 오류 식별자 설계는 초기 기준선이다. 최신 네 필드 실패 응답은 Nestia 마이그레이션 보완 설계와 구현 제어 기록이 기준이다.

성공: 결과 자체(application/json), data envelope 없음. 실패: RFC 9457(application/problem+json), code 확장. 현재 외부 실패 본문은 title/status/detail/code 네 필드만 사용한다. type과 instance는 응답 계약에 넣지 않으며, request ID는 응답 헤더와 서버 로그에서만 추적한다.

알려진 프로젝트 오류는 API 계층의 ApiException에서 외부 code·HTTP status· title·description을 관리한다. code는 INVALID_ARGUMENT·NOT_FOUND·CONFLICT·INTERNAL_ERROR를 유지하며, 매핑되지 않은 상태는 HTTP_<status>를 fallback으로 사용한다. 검증 실패는 400/INVALID_ARGUMENT으로 정규화하고 원본 입력값과 검증 상세를 응답에 포함하지 않는다.

DomainException은 직접 생성하지 않는 추상 기반이고, 도메인마다 IssueException·UserException 같은 구체 타입과 내부 코드를 소유한다. API adapter의 도메인 예외 매핑이 이를 ApiException으로 변환한다. 로그에는 예외 이름·도메인·도메인 코드·API 코드·requestId를 남긴다. 예상 밖 오류는 고정된 안전한 설명을 반환하고 SQL·스택은 응답에서 숨긴다. core는 HTTP를 모른다.

실행·실패·복구

API는 환경 설정만으로 기동하고 요청을 받는다. DB 연결 확인은 batch의 databaseCheck 작업에서 별도로 수행한다. 기동 실패는 자원을 정리하고 실패 종료한다. GET /health는 프로세스 생존 확인이며 지속적인 DB readiness 보장은 아니다. 성공 본문은 {status:"ok"}다.

batch는 명시적인 databaseCheck 작업만 실행하고 별도 ORM 컨텍스트에서 SELECT 1 확인 후 종료한다. 정상 및 정리 성공은 0, 잘못된 작업명·연결/작업/정리 실패는 1. 자동 재시도 없음. 강제 process.exit로 정리를 생략하지 않는다. API 종료 신호와 batch 정상·예외 경로에서 연결을 닫는다.

실제 업무 데이터 쓰기와 기동 시 스키마 자동 변경 없음. 실제 배치 중복 실행 방지와 장애 복구는 후속 업무 계약이다.

설계 의사결정 기록

진행 상태: 완료. 공유 이해는 사용자의 “맞아” 및 후속 구조 보완 요청으로 확인. 남은 업무 전용 분기는 현재 범위에서 보류 수용. 이번 점검은 별도 design-control이다.

G1-A CLI 모노레포 / G2-A ORM 엔티티 겸용 / G3-B 앱별 유즈케이스 / G4-A 일회성 batch / G5-A repository 계약·구현 / G6-A 타입 분리 / G7-A HTTP 독립 오류 / G8-A 실행 골격 / G9-A 트랜잭션 계약 / G10 RFC 9457+code 및 성공 직접 반환 / G11-A 최소 batch.

후속 확정: unit of work 대신 transaction 및 TransactionManager. 하이픈 없는 자체 이름. repository와 domain은 feature 최상위 아래에서 함께 관리한다. 출력 포트·어댑터 역할은 유지하며 불필요한 port/adapter 폴더는 생략한다.

세부 기본값과 근거

환경에 있는 npm과 단일 package.json을 사용한다. Node 24 계열, NestJS 12 계열, MikroORM 7 계열을 후보로 공식 문서의 런타임 요구와 대조했다. 실제 설치 전 peerDependencies를 재확인하고 호환되는 정확한 패치 버전을 lockfile로 고정한다. peer 충돌을 무시하는 설치 옵션은 쓰지 않는다. ESM 기준 빌드로 정리하며 Nest CLI 빌드의 alias 처리와 실행 산출물을 함께 검증한다.

DB 자격증명은 환경변수로만 받으며 문서·로그에 노출하지 않는다. DB 통합 검증은 격리된 로컬 테스트 DB가 확보된 뒤 실행한다. 운영 DB나 기존 테이블을 변경하지 않는다.

채택하지 않은 대안

개별 workspace 의존성, 순수 도메인/ORM 이중 모델, core/application, 상주 batch·큐, repository 구현만 직접 주입, 입력 포트 인터페이스, port/adapter 중첩 폴더, 성공 data envelope를 채택하지 않았다.

검증 계획과 현재 상태

다음은 구현할 npm script 계약이며 아직 명령은 저장소에 존재하지 않고 실행되지 않았다. 

npm run format:check
npm run lint
npm run typecheck
npm run build:api
npm run build:batch
npm run test:unit
npm run test:integration
npm run test:smoke

unit: TransactionManager 예외/컨텍스트와 Filter 매핑. integration: 격리 DB에서 컨텍스트·transaction adapter 경로. smoke: API 성공/404/검증/예상 밖 실패, batch 정상/잘못된 작업명/DB 실패·종료. 테스트 전용 경로를 운영 API에 추가하지 않는다.

사전 점검: 실행 코드 없음, Node/npm 확인, Docker daemon 접근 제한. npm registry 조회는 DNS ENOTFOUND로 실패해 정확한 패치 및 peerDependencies 확인이 남아 있다. DB 실동작 검증도 설치·실행 단계에 남음. HTML 구조 검사(중복 ID 없음, 20개 입력 label, 10개 결과 카드 초기 숨김, figure 캡션) 및 JavaScript 구문 검사는 통과했다. 실제 브라우저 동작·시각 검증은 미실시다. 빌드 통과만으로 통합 검증 성공을 주장하지 않는다.
