Cloud Build ttsc 캐시·단일 push 구현 제어

운영 제어 보류 · 기준 설계: 설계 문서

기준 설계

승인 범위
기본 worker 유지, GCS ttsc/plugins cache, Node build step 분리, runtime-only image, cache miss fallback, 명시적 단일 push, 최신 cache 3개 prune, 30일 lifecycle 안전망, 새 cloudbuild.yaml 버전 관리.
불변식
API·batch의 순차 빌드와 production runtime 계약을 유지하고, GCS cache 장애·cache miss는 cold plugin build로 복구된다.

현재 구현

  • Dockerfile을 runtime-only image로 변경했다. Cloud Build가 먼저 dist를 만들고 Docker는 production dependency와 산출물만 조립한다.
  • .dockerignore는 node_modules, GCS archive, workspace cache를 제외하고 dist는 image context에 허용한다.
  • cloudbuild.yaml에 GCS cache 복원 → Node 24 build → plugin cache 저장 → 최신 3개 prune → Docker build → 명시적 push 1회 → Cloud Run deploy를 추가했다.
  • cache key는 Linux amd64·Node 24·package-lock.json hash로 분리하고, cache read/write 실패는 배포를 막지 않는다.
  • plugin archive는 임시 파일에 먼저 생성하고 성공 시에만 최종 경로로 rename한다. packaging 실패 시 stale·partial archive를 제거해 업로드하지 않는다.
  • trigger가 사용자 지정 서비스 계정을 사용하므로 options.logging: CLOUD_LOGGING_ONLY를 지정해 Google Cloud Logging으로 build log를 보낸다. 서비스 계정에는 roles/logging.logWriter가 필요하다.
  • build-application step은 Go 기반 ttsc plugin compile 전에 ca-certificates를 설치해 proxy.golang.org TLS 검증을 보장한다.
  • ttsc-cache-lifecycle.json은 newtine-backend/ prefix의 30일 안전망으로 유지한다. 정확한 최신 3개 보존은 prune-ttsc-cache 단계가 담당한다.
  • cache write는 trusted main/deployment trigger 전용으로 운영한다. cache 전용 bucket은 soft delete를 비활성화하고 lifecycle을 적용해야 한다.

구현 상태

로컬 구현과 설정 검증은 완료했다. 실제 Cloud Build trigger가 새 설정을 사용하고, bucket/IAM이 준비된 상태에서 두 번째 build가 plugin cache hit가 되는지는 운영 검증 대기다.

검증 증거와 계획

  1. 완료: YAML parser로 7개 step, save-ttsc-cache → prune-ttsc-cache → build-image 순서와 images: 부재를 확인했다.
  2. 완료: prune step의 Bash 문법과 설계 문서의 JavaScript 문법을 확인했다.
  3. 완료: cloudbuild.yaml·ttsc-cache-lifecycle.json 포맷, 기존 npm run format, 기존 애플리케이션 npm run build가 통과했다.
  4. 완료: git diff --check 통과.
  5. 완료: archive packaging을 임시 파일 → 성공 시 rename 경로로 변경하고 Bash 문법을 재검증했다.
  6. 완료: 로컬 npm run build 성공. 기존 local ttsc cache hit 경로에서 API·batch 산출물이 생성됐다.
  7. 완료: docker build -t newtine-backend:cloudbuild-layout-test . 성공. context 3.17MB, runtime dependency 설치 4초, dist 조립 확인.
  8. 대기: 실제 trigger에서 cache miss build 후 소스만 변경한 warm build를 실행해 ttsc: building source plugin 부재와 build elapsed를 비교한다.
  9. 대기: cache archive 복원 실패, 저장·prune 실패, lockfile 변경 시 cold fallback과 배포 성공을 확인한다.

검증 공백과 잔여 위험

  • bucket이 없거나 Cloud Build service account에 object read/write 권한이 없으면 모든 build가 cold path로 실행된다.
  • 외부 PR 또는 신뢰할 수 없는 build에 cache write 권한을 주지 않아야 한다.
  • 현재 cache scope는 93MB 수준의 plugin archive만 대상으로 하며, 3.1GB Go object cache는 의도적으로 전송하지 않는다.
  • 동시 Cloud Build가 여러 개 실행되면 최신 3개 보존은 eventual 상태가 되며, 필요하면 trigger 동시 실행 제한을 별도로 검토해야 한다.
  • soft delete가 기본 7일로 활성화된 bucket에서는 prune된 객체가 물리적으로 즉시 사라지지 않을 수 있다. 캐시 비용과 복구 필요성을 보고 bucket 생성 시 soft delete 정책을 결정해야 한다.
  • 실제 Cloud Run deploy flags와 기존 trigger substitution이 저장소에 없으므로, 운영 연결 후 image URI·service·region을 확인해야 한다.

설정 리뷰

리뷰 범위는 cloudbuild.yaml, ttsc-cache-lifecycle.json, Docker build 경계와 GCS 운영 연결이다. 리뷰에서 확인된 archive 저장 위험은 atomic save로 반영했다. GCP bucket·trigger 자체는 외부 리소스라 이 저장소에서 변경하지 않았다.

ID판정·심각도근거·영향최소 조치
R-SEC-1 논의 필요 · P1 cloudbuild.yaml:38-43,95-96에서 archive를 복원하고 같은 bucket에 저장한다. 외부 PR이나 신뢰하지 않는 trigger가 이 설정을 사용하면 cache poisoning과 빌드 입력 오염 경계가 생긴다. 배포용 trusted main trigger에만 read/write 권한을 부여하고, PR build는 cache write를 끄거나 별도 bucket·service account를 사용한다. 실제 trigger 범위를 확인하기 전에는 운영 안전성 확정 불가.
R-CACHE-1 해결됨 · P2 cloudbuild.yaml:66-76에서 tar와 rename을 한 조건으로 묶었다. 실패 시 임시·최종 archive를 제거하므로 partial archive를 저장 단계가 업로드하지 않는다. 로컬 Bash 문법 검증 완료. 실제 Cloud Build에서 packaging 실패를 주입하는 검증은 선택적으로 남아 있다.
R-COST-1 논의 필요 · P2 prune은 live object를 3개로 줄이지만, GCS soft delete가 켜져 있으면 삭제 객체가 기본 7일간 복구 보존되어 실제 저장 비용은 3개보다 커질 수 있다. lifecycle 30일은 이 동작을 즉시 해결하지 않는다. 폐기 가능한 cache bucket이면 soft delete 비활성화를 명시하고, 복구 보존이 필요하면 비용을 “live 3개 + soft-deleted 보존분”으로 산정한다.
R-RET-1 논의 필요 · P2 cloudbuild.yaml:30-32,106-125의 prune은 서로 다른 cache key 객체를 updateTime 기준으로 3개 남긴다. 같은 lockfile hash로 반복 빌드하면 같은 객체를 갱신하므로 “최근 3회 빌드” 또는 “동일 객체의 세대 3개”를 보장하지 않는다. 목표가 최근 3개 cache key면 현재 정책을 유지한다. 최근 3회/세대가 목표면 object versioning·generation 보존 또는 run-id 기반 key와 별도 prune 설계를 선택한다.
R-OPS-1 non-blocking risk · P2 cloudbuild.yaml:95-119의 best-effort prune은 동시 build와 경합한다. 일시적으로 3개를 초과하거나 다른 build가 막 저장한 cache를 삭제해 다음 build가 cold path가 될 수 있다. 정확한 상한이 필수가 아니면 현재 eventual 정책을 수용하고 모니터링한다. 필수라면 trigger 동시 실행 제한 또는 별도 직렬화가 필요하다.

리뷰 판정

논의 필요. 로컬 문법·빌드 검증은 통과했지만, 실제 trigger가 trusted main 전용인지, bucket soft delete 정책과 “3개”의 의미가 확정되지 않았다. 따라서 현재 설정을 “안전하고 비용이 정확히 3개로 제한된다”고 운영 승인할 단계는 아니다. 실제 Cloud Build cold/warm 연속 실행과 권한·prune 관찰이 남아 있다.
