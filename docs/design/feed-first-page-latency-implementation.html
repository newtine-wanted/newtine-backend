2. 실제 실행 흐름과 상태 경계

candidate ID query는 ID만 읽어 identity map에 부분 issue entity를 남기지 않는다. recommendation projection은 issue score/topic/entity/impact 신호만 읽고, card projection은 summary·score·category·AVAILABLE 기사 수만 읽는다. 사용자 context·relation도 필요한 scalar/PK만 읽는다. feed 경로에서 기사 링크·article·publisher entity를 hydrate하지 않으며 detail mode의 기사 순서와 publisher fallback은 기존 경로를 유지한다.

설계 delta

사용자 결정으로 v2는 신규 session의 기본값이며, 기존 v1 session snapshot과 신규 v1 rollback은 유지한다. 첫 조회 경로는 생성한 session을 재사용하고, 추천·카드의 내부 repository projection과 canonical save outcome을 추가했다. 이번 후속 delta에서는 추가된 standalone raw SQL을 MikroORM QueryBuilder로 재작성하되, API 응답·cursor·DB schema·row lock·pool/infra 설정과 단일 DB 왕복 목표는 유지한다.

6. 독립 리뷰 결과

승인 범위 구현 게이트와 별도 no-write critical review를 완료했다. standalone raw member-input query와 connected predicate를 QueryBuilder projection/subquery로 옮겼고, connected 후보 선별과 최종 표시를 같은 statement 결과로 운반한다. 최초 smoke에서 발견한 joined-column alias 오류는 direct source/target join과 explicit snake_case identifier로 해결했다. source-first SQL은 populated disposable PostgreSQL plan으로 확인했으며, 실제 PostgreSQL 동시 lock·pool wait·HTTP tail latency는 별도 운영 검증으로 남아 있다.

리뷰 한계

7. 잔여 운영 위험과 다음 행동

  1. 배포 전 disposable PostgreSQL에서 candidate/card projection → feed/detail count equivalence → same EntityManager detail reload를 자동 smoke로 추가한다.
  2. 2,000-row disposable source-first plan과 positive connected smoke는 통과했다. 다음 운영 유사 단계에서는 실제 interaction cardinality별 SQL plan·bind 수·추천 결과 parity·pool wait를 측정한다.
  3. v2 기본값으로 배포하기 전과 직후에 새 세션 기준 cold/warm, 회원/게스트, 이력 규모, 동시성별 첫 HTTP p50/p95/p99를 직접 측정한다. 500ms 목표 미달이면 이 구현을 성공으로 포장하지 않는다.
  4. v2 세션 TTL 동안 v2 코드를 유지하고, 운영 rollback은 신규 생성 버전만 v1로 바꾼다. 실제 설정·배포는 별도 승인이다.
현재 작업 상태: 구현은 이 worktree에만 반영했고 commit·push·PR·deploy는 하지 않았다. 기본 환경값은 v2이며, 명시적으로 v1을 설정하면 신규 세션만 v1으로 rollback할 수 있다.
