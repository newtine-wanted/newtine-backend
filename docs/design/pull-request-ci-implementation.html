1. baseline-reference · 승인된 설계 기준선

설계 승인됨 · 권고안 A

기준선은 메인 워크스페이스의 pull-request-ci-design.html이다. 사용자는 2026-09-14T22:59:32+09:00에 “개선 ㄱ”으로 권고안 A를 승인했다. G2-A는 repository-owned checker가 허용된 순서 차이만 정규화하고 나머지 drift를 차단하는 기준으로 갱신됐다.

G1-A: 기본 gate · G2-A: 제한된 canonicalization을 포함한 매 PR 계약 drift · G3-A: merge ref와 지정 event · G4-A: SHA pin

2. execution-contract · 구현 계약

목표
PR 변경이 병합되기 전 재현 가능한 품질·계약 검증을 수행하고 하나의 실패 가능한 gate를 보고한다.
확인된 근거
Node 24·npm과 root package-lock.json이 문서화되어 있다. 저장소 scripts에는 format:check, lint, typecheck, test, build, contracts:check가 있고, contracts:check 자체는 생성 후 git diff 실패를 보장하지 않는다. generated/에는 tracked 결과가 있다.
구현 파일
.github/workflows/pr-ci.yml, scripts/check-generated.mjs, test/unit/checkGenerated.test.mjs · API package source 변경 없음
해결한 구현 이슈
같은 clean source에서 Nestia 생성물 순서가 달라지는 현상을 확인했으므로 raw diff 대신 repository-owned checker를 둔다. checker는 generated/openapi.json의 object key와 generated/api/functional/index.ts의 export line만 canonicalize하고, 나머지 generated 파일은 byte compare한다.
불변식
pull_request에서 실행하고 pull_request_target을 사용하지 않는다. contents: read만 부여하고 secret·쓰기 동작을 추가하지 않는다. npm ci와 npm cache를 사용하며, quality 명령은 단일 job에서 순차 실행한다. checker는 generated의 tracked 변경·누락·untracked 파일을 job 실패로 보고한다. 허용된 두 순서 차이 외의 변경은 숨기지 않는다. 새 PR commit은 이전 실행을 취소한다.
구현 순서
제어 문서 갱신 → checker·순수 규칙 테스트 추가 → workflow 교체 → 정적 점검 → 실제 저장소 명령 검증 → 증거 갱신
완료 조건
workflow가 문법·설계 불변식을 만족하고, clean worktree에서 설치·quality 명령·계약 검사가 실행되며, generated drift 비교가 비결정적 순서 차이로 false positive를 만들지 않는다. 로컬에서 확인할 수 없는 GitHub 운영 공백도 분리 기록한다.
검증 명령
npx prettier --check .github/workflows/pr-ci.yml, npm ci, npm run format:check, npm run lint, npm run typecheck, npm test, npm run build, npm run contracts:check, node scripts/check-generated.mjs, npm run test:unit -- test/unit/checkGenerated.test.mjs, generated 반복 실행 확인
금지 변경
DB service·Docker smoke 추가, secret 사용, privileged trigger, 자동 commit·push, path filter, main push
재설계 조건
checker가 비의미적 차이를 넘어 실제 계약 변경을 숨기거나, 새로운 generated 파일이 canonicalization 규칙 밖에서 비결정적으로 생성될 때 설계를 다시 승인받는다. GitHub 저장소가 merge queue를 사용해 merge_group trigger가 required check에 필요하다는 사실이 확인되는 경우도 운영 검토한다.

5. design-delta · 설계와 구현의 차이

현재 판정: 승인된 개선 반영

trigger·권한·runner·순차 quality 명령은 baseline대로 유지했다. G2-A의 raw diff는 반복 실행 false positive를 해결하기 위해 승인된 A 방식으로 교체했다. checker는 두 명시된 파일의 비의미적 순서만 정규화하고, 그 밖의 generated 변경은 계속 실패시킨다.

7. failure-recovery · 실패·복구 증거

workflow는 실패한 step에서 중단되며 자동으로 generated 파일을 commit·push하지 않는다. 계약 drift가 발생하면 개발자가 로컬에서 npm run contracts:check와 node scripts/check-generated.mjs를 실행해 실제 생성 결과를 PR에 반영하고 다시 실행한다. checker가 허용하는 순서 차이는 두 명시적 파일에만 한정되며, 그 밖의 변경·누락·untracked 파일은 실패한다.

9. verification-gaps · 검증 공백

  • checker allowlist가 현재 관찰된 두 파일을 대상으로만 정의되어 있다. 새로운 generated 파일 형식이나 새로운 비결정적 순서가 추가되면 규칙을 재검토해야 한다.
  • 실제 GitHub-hosted runner에서의 clean checkout과 Actions step 결과는 로컬 검증만으로 확정할 수 없다.
  • branch protection이 PR CI / Quality gate를 required로 지정했는지는 저장소 관리자 확인이 필요하다.
  • 저장소가 merge queue를 사용하는지는 로컬 workspace에서 확인하지 않았으며, 사용 시 merge_group 재검토가 필요하다.
  • DB·Docker runtime 통합 검증은 승인 범위에서 제외했으므로 해당 동작을 이 CI의 성공으로 주장하지 않는다.

11. decision-trail · 구현 중 결정 기록

  1. G1-A: 초기 gate에서 PostgreSQL·Docker runtime smoke를 제외한다.
  2. G2-A: 계약 생성 후 허용된 순서 차이만 checker로 정규화하고 generated tracked·missing· untracked drift를 매 PR에 차단한다.
  3. G3-A: pull_request의 opened·synchronize·reopened를 merge ref로 실행하고 path filter를 두지 않는다.
  4. G4-A: checkout·setup-node 공식 action은 확인한 full-length commit SHA로 고정한다.
  5. 기존 저장소의 생성/cache 충돌 관찰을 반영해 quality 명령은 단일 job에서 순차 실행한다.
  6. 구현 검증 중 같은 계약 생성 명령에서도 functional/openapi 항목 순서 변동을 확인해, repository-owned checker가 두 비의미적 순서만 정규화하도록 G2-A를 개선했다.

운영 조치의 소유자

이 artifact와 workflow는 코드 변경으로 관리한다. GitHub branch protection required check와 merge queue 여부는 저장소 관리자·운영 확인의 책임이며, workflow가 자동으로 수정하지 않는다.
