설계 결과

명시 행동은 LIKE(+2), SKIP(-3), PASS(0). 사용자·이슈별 현재 행동 기여분만 주제 선호에 반영한다. 상세 체류는 별도 기록으로 누적하고 10초부터 +0.5, 30초부터 최대 +1을 부여한다. 기존 상세 GET과 관심 목록 GET을 재사용한다.

성공 기준: 좋아요 후 목록 조회에 나타남, 취소·스킵 후 제외, 재전송 시 중복 점수 없음, 상세 재열람 시 현재 좋아요 유지, 새로운 피드 계산에 갱신 선호 반영.

결정 기록

진행 상태: 완료. 제품 선택의 material frontier 없음. 아래 기술 계약은 사용자 승인으로 구현 기준선이 되었다. as-built 상태와 검증 결과는 연결된 구현 제어 문서에서 관리한다.

범위와 기존 계약의 영향

  • 명시 행동·체류 쓰기는 JWT 회원 전용. 게스트 상세·피드 GET은 유지하고 회원 이벤트나 선호를 만들지 않는다. 게스트 좋아요 저장·로그인 시 이관은 포함하지 않는다.
  • 추천의 배분·순위 수식, 인물·기관·지역·나이대 선호, 기사 생성, 주간 보고서 구현은 제외.
  • 현재 추천은 weight > 0인 주제 집합을 읽는다. 저장 점수가 2배면 순위 영향도 2배라는 의미가 아니다.
  • LIKE/SKIP/PASS가 있는 이슈는 새 피드 후보에서 제외하는 기존 정책 유지. 체류만 있는 이슈는 명시 행동 이력으로 취급하지 않는다. 이미 확정된 묶음은 재정렬하지 않는다.
  • 상세 응답에 회원 현재 상태 myAction: LIKE | SKIP | PASS | null을 추가한다. 게스트·무행동은 null. 좋아요 목록에서 재진입한 화면도 정확히 표시하도록 사용. 이 읽기는 부작용이 없다.

모든 UUID·enum·숫자 범위·미지정 필드를 Typia로 검증한다. userId, previousAction, 점수, 서버 시각은 요청에서 받지 않는다. sessionId는 앱 접속 추적값이며 feed cursor나 인증 세션 FK가 아니다. action body의 dwellTime은 제거하고 기존 이벤트 dwell_time은 신규 명시 행동에서 NULL로 유지한다. 체류는 progress 경로만 담당한다.

행동 응답은 해당 이벤트의 수용 사실이다. 과거 LIKE 재전송에 acceptedAction=LIKE가 반환되어도 지금 SKIP일 수 있다. UI는 같은 이슈 쓰기를 순차 전송하고, 재접속·경합 후 GET 상세로 현재 상태를 동기화한다. 목록은 변경 성공 뒤 첫 페이지부터 새로 조회하며 커서 전체 스냅샷은 보장하지 않는다.

점수와 상태 전환

주제 선호 = 온보딩 등 기존 기여 + Σ 이슈별 명시 행동 기여 + Σ 이슈별 체류 기여. 기존 weight에 변화량만 가산한다. 총 weight가 음수가 되는 것을 허용하며 0으로 잘라 역전환 계산을 훼손하지 않는다.

명시 행동 전환 시 주제 weight 변화량
이전 → 다음LIKE(+2)SKIP(-3)PASS(0)
없음 / PASS(0)+2-30
LIKE(+2)0-5-2
SKIP(-3)+50+3

다른 eventId로 같은 상태를 보내면 감사 이벤트는 새로 남고 점수 변화는 0. 기존 목록 계약에 따라 최신 LIKE 수용 시각이 likedAt이 되므로 새 ID의 반복 LIKE는 목록 순서를 갱신한다. 클라이언트는 재시도에 새 ID를 발급하지 않는다. 같은 eventId 재전송은 시각도 바뀌지 않는다.

체류 보상: 누적 <10000ms는 0, 10000..29999ms는 +0.5, ≥30000ms는 +1. 예: 15초 읽고 다음 방문에 20초 읽으면 +0.5만 추가. LIKE 취소는 명시 행동 +2만 회수한다. 30초 읽고 SKIP하면 합산 기여는 -2다. 상세 체류만으로 관심 목록에는 들어가지 않는다.

체류 측정과 전송

  1. 시트가 실제 열렸을 때 start PUT을 보낸다. 상세 GET·프리패치로 start를 대신하지 않는다. 시작 응답 후부터 시트 표시 및 앱 foreground 시간을 단조 증가 타이머로 측정한다.
  2. 5초마다, 시트 닫기·background 전환 시 누적 ms를 전송한다. 재전송은 동일 viewId와 누적값 사용. 종료 전송을 보장하지 못한 강제 종료에서는 마지막 수용 이후 시간이 유실될 수 있다.
  3. 서버는 소유자·이슈·시작 기록을 검증하고 새 누적값과 저장값의 차이만 더한다. 이전 값이나 같은 값은 0. 누적값이 서버 시작 이후 경과시간보다 크면 400. 서버에서 얻은 시간끼리 비교한다.
  4. 사용자·이슈 합계는 점수 계산에 필요한 30000ms에서 포화한다. 열람별 누적값은 보상 중복 방지용으로 보관한다. 회원·이슈의 모든 열람에서 합산하며 동시 기기의 별도 열람 시간도 합산한다. 사용자 실제 벽시계 시간의 합집합을 보장하지 않는다.
  5. 열람 유효기간은 서버 시작 후 30분. 만료된 progress는 410, 새 열람을 등록해 이어서 측정한다. 시작 기록은 삭제하지 않아 동일 viewId로 보상을 재생하지 못하게 한다.
활성 여부는 클라이언트 보고이며 서버가 실제 독서를 증명하지는 않는다. 경과시간 검증과 이슈당 +1 상한으로 범위를 제한한다. 이번 설계는 독서 인증이나 광고 정산에 사용할 수 없다. 무기한 오프라인 체류 이관은 제공하지 않는다.

이슈 category_code는 첫 기여분 생성 때 고정한다. 이후 이슈 주제가 수정돼도 이전 주제 기여를 자동 이동하지 않는다. 취소·재선택도 저장된 주제에 적용해 잘못된 주제에서 차감하는 것을 방지한다. 분류 수정에 따른 기여 이동은 별도 데이터 정정 작업이다.

최신 판정·이전 데이터 호환

명시 행동 latest는 서버 accepted_order로 선택한다. 같은 사용자 쓰기가 직렬화된 뒤 순서를 발급하므로 client UUID 순서나 클라이언트 발생 시각에 의존하지 않는다. 시계 역행으로 created_at을 인위적으로 미래로 밀지 않는다. 목록의 정렬 키는 기존 likedAt/issueId를 유지하고, 사용자·이슈별 최신 상태 선택만 accepted_order로 교체한다.

빈 이력에서는 sequence가 서버 수용 순서를 발급한다. 기존 이력이 있으면 accepted_order와 과거 점수의 의미를 임의로 추정하지 않고 migration preflight에서 중단한다. 읽기 repository 두 곳의 최신 선택과 관련 fixture를 함께 변경한다. 현재 관심 목록 조회는 애플리케이션 Date의 시각 컷오프 때문에 방금 commit한 이벤트를 놓치지 않게 현재 DB 스냅샷에서 최신을 선택한다. 기간 집계는 별도의 서버 수용 created_at 구간 규칙을 유지한다.

기존 이벤트의 점수가 과거 weight에 반영되었는지는 현재 schema만으로 증명할 수 없다. 적용 전 읽기 preflight에서 기존 이벤트 존재와 기여분 도입 가능성을 검사한다. 기존 이벤트가 있다면 임의로 weight를 재합산하거나 기존 기여를 0으로 가정하지 않고 중단한다. 백필·초기화 정책을 별도 설계 승인받아야 한다. 빈 이력에서의 additive migration이 이번 실행 계약의 전제다. 테스트의 legacy 이력은 순서 호환 테스트용이며 실제 데이터 초기화 권한이 아니다.

불변식

  • JWT principal만 사용자 권한. sessionId와 viewId만으로 다른 회원 기록에 접근하지 못한다.
  • 동일 이벤트 ID·동일 payload는 한 번만 반영. 다른 payload/소유자로 ID가 충돌하면 409, 기존 데이터는 반환하지 않는다.
  • 기여분·이벤트·weight가 부분 성공하지 않는다. 체류 progress도 같은 원자성 적용.
  • LIKE/SKIP/PASS 최신 상태와 체류는 독립. GET은 쓰기 없음.
  • 동일 사용자 최초 행동 경쟁·타 이슈 선호 변경·온보딩 완료 사이의 갱신 손실 없음.
  • 명시 행동 현재 기여는 -3/0/+2 중 하나, 체류 총 기여는 최대 +1. 점수를 변경해도 관심 분석 건수 계산에 weight를 사용하지 않는다.

미인증·무효 JWT401. guest cookie로 쓰기 권한을 대신하지 않음.
신규 행동·열람의 없는/비공개 이슈, 타인 view 접근404. 신규 쓰기는 현재 공개 여부 재검사. 조회와 철회가 겹치면 이슈 공유 잠금으로 현재 검사를 트랜잭션에 묶는다.
eventId/viewId가 다른 소유자·payload와 충돌409. 기존 소유자·내용 노출 없음.
성공 후 응답 유실행동은 같은 eventId로 재시도. 공개 철회 후에도 본인의 동일 수용 이벤트 확인은 성공. progress는 누적값 재시도, 이전 누적값은 점수 추가 없이 현재 값 반환.
progress 재시도 중 철회·만료이미 수용한 값 이하의 재전송은 수용값 확인만 가능. 증가 요청은 철회 404/만료 410. 최초 start 재시도는 원래 만료를 연장하지 않음.
DB 장애·잠금 timeout503, 전체 rollback. 같은 키로 backoff 재시도. 다른 기기 경합은 서버 수용 순서를 따름.

로그: requestId, 처리 종류, 결과 코드, duplicate 여부, 트랜잭션 지연·잠금 timeout을 구조화 기록한다. JWT·원문 선호/관심 이력은 로그에 넣지 않는다. 이벤트 증가와 score delta의 불일치, 체류 +1 상한 위반을 read-only 점검 가능하게 한다. 장애 시 쓰기를 중단하고 기록·원장을 비교하며 이벤트 삭제나 임의 점수 보정으로 복구하지 않는다.

상세 열람 기록은 자동 삭제하지 않는다. 점수 상한 도달 뒤 프런트는 progress 전송을 멈출 수 있다. 기존 API rate-limit 운영 경계를 재사용하되 보호가 없거나 수용량 문제를 발견하면 구현 중 숨기지 않고 운영 제약으로 보고한다.

채택하지 않은 대안

행동마다 점수 누적, 인물·기관까지 자동 가중, 회차마다 체류 보상은 사용자 선택으로 제외. GET에서 열람 행동 생성, 상세를 PASS로 기록, 별도 좋아요 복사 테이블, 재시도에 상태가 뒤집히는 toggle API는 불변식에 맞지 않아 제외한다. 클라이언트 UUID를 최신 수용 순서로 해석하거나 서버 created_at을 미래로 밀어 순서를 만드는 방식 대신 서버 순서를 명시한다.
