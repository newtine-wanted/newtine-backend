implementation-control-state: 운영 제어 보류. 기술 상태·이슈·개발자 운영 이해를 분리한다. 운영 이해 질문은 실제 as-built 코드와 검증 증거를 예측하게 하며, 설계 선택 질문이나 배포 승인을 대신하지 않는다.

2. 현재 구현 기록

승인된 설계 기준으로 다음을 반영했다.

  1. batch.role.ts의 allowlist parser와 batch.job.ts의 공통 token/계약, databaseCheck·report·pipeline 역할 module/adapter를 추가했다.
  2. main.ts가 Nest 초기화 전에 role을 검증하고 BatchModule.forRole()만 생성한다. BatchRunner는 선택된 job만 실행하며 기존 event name과 lease/retry 호출 경계를 유지한다.
  3. report module은 LoggerModule·CoreModule·report provider만 가져오고 PipelineAiConfiguration을 생성하지 않는다. pipeline module만 pipeline 설정과 pipeline provider를 등록한다.
  4. Docker를 api/batch target으로 분리하고 batch target에 standalone news script, prompt, UX direction, config를 명시적으로 포함했다. 두 target 모두 non-root runtime이다.
  5. Compose의 api/migrate는 api target, batch/report-worker는 batch target을 사용한다. Cloud Build는 API와 batch 이미지를 각각 push하지만 자동 deploy는 API만 수행한다.
  6. deploy/cloud-run/report-worker/README.md에 digest pin, command, secret, instance/resource, preflight를 포함한 수동 Worker Pool 운영 정의를 추가했다. 실제 GCP resource apply는 하지 않았다.
  7. focused/full unit, integration, news runner, format/lint/typecheck/build, Docker build와 runtime asset/role smoke를 실행했다.

5. 검증 공백과 잔여 위험

  • GCP 프로젝트·Worker Pool·Cloud SQL 연결·IAM·Secret Manager 상태를 조회하지 않았다. 이번 결과는 배포 정의와 로컬 image 검증까지다.
  • 실제 OpenAI/Naver 인증과 quota는 확인하지 않는다. 테스트에서는 외부 호출을 하지 않는다.
  • 공통 DB와 AI quota는 API/batch 프로세스가 분리되어도 공유 영향이 남는다.
  • Cloud Run Worker Pool의 scale/instance 수·비용은 실사용량 측정 뒤 운영자가 정한다.
  • pipeline의 manifest 영속 저장·재개와 새 Cloud Run Job 운영은 승인 범위 밖이다.
  • 원본 워크트리의 미커밋 report 변경과 이 브랜치의 기준 커밋이 다르므로 병합 시 재검증해야 한다.
