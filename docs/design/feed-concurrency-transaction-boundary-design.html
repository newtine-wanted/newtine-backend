설계 기준 문서 · 현재: 설계 승인됨

/api/feed 동시성·트랜잭션 경계 개선

purpose · 목적
/api/feed의 동일 세션 직렬화와 긴 transaction 점유를 줄여 p95/p99 지연과 connection pool 압박을 완화한다.
audience · 사용자
피드 API를 운영·연결하는 백엔드 개발자, Cloud Run·PostgreSQL 운영자, 피드 클라이언트 개발자.
problem · 문제
조회 요청이 프로세스별 withLock(sessionId)에서 대기하고, getBatchLocked() 전체가 transaction 안에서 추천 계산·최종 hydration까지 수행한다. SQL 단독 실행계획은 약 3ms였지만 HTTP 요청은 약 24초까지 증가했다.
core-flow · 핵심 흐름
커서·소유권 확인 → 읽기 준비 → transaction 밖 추천 계산 → 짧은 DB commit claim → commit 후 카드 hydration → 동일 batch 재시도 시 승자 batch 반환.
강도·범위
High-risk: 동시성·transaction·상태 전이·멱등성 경계를 바꾸는 설계. API 응답 계약과 추천 알고리즘 자체는 유지한다.
생성·추적
2026-09-20 KST · 기존 이슈 카드 조회 설계와 목적이 다른 별도 설계 문서. 사용자가 워크트리 하나 파서 구현 ㄱ으로 구현을 승인했다.

목표와 경계

목표
동일 sessionId의 중복 요청이 전체 feed 계산을 서로 기다리지 않게 하고, DB row lock은 상태 commit에 필요한 짧은 구간으로 제한한다.
성공 신호
동시 동일 커서 요청의 후속 요청이 선행 요청의 전체 계산 시간을 상속하지 않는다. 정상 부하에서 API p95/p99가 개선되고, 동일 sessionId + batchNo는 하나의 저장 batch를 공유한다.
비목표
추천 점수·선택 quota·카드 내용의 제품 정책 변경, API cursor 포맷 변경, 즉시 인덱스 추가, 무근거한 pool 크기 증설, 광범위한 production query logging.

확인된 근거와 가정

코드·DB·운영 자료에서 확인한 사실
구분근거설계 영향
HTTP/api/feed가 약 24초이지만 middleware는 end-to-end 시간만 기록한다.내부 대기 위치는 기존 로그만으로 분해되지 않는다.
SQL대표 후보 query의 Execution Time 3.258ms, 전체 후보 fingerprint의 관측 최대 약 29.7ms.단일 후보 query 인덱스보다 request orchestration·경합을 먼저 본다.
프로세스 락withLock(sessionId)가 getBatchPage() 전체를 직렬화한다.같은 세션 중복 요청의 대기는 DB 관측에 나타나지 않는다.
TransactiontransactionManager.execute(() => getBatchLocked())가 읽기·추천 계산·저장·최종 hydration을 모두 감싼다.비싼 계산 또는 응답 hydration 중에도 pool connection이 점유될 수 있다.
상태 저장feed_batches(session_id, batch_no) primary key와 feed_sessions pessimistic row lock이 있다.프로세스 락을 제거해도 DB가 최종 winner를 결정할 기반이 있다.
분산 배포Cloud Run 여러 instance 사이에서 현재 Map 기반 lock은 공유되지 않는다.프로세스 락은 완전한 정합성 보장이 아니며 DB commit guard가 필요하다.

현재 모델과 제안 모델

핵심 위험: 프로세스 락을 단순 삭제하고 기존 넓은 transaction을 그대로 두면 중복 계산과 DB connection 점유가 동시에 증가할 수 있다. 락 제거와 transaction 축소는 하나의 상태 전이 설계로 함께 검토해야 한다.

B. lock 제거, DB commit winner만 사용

불변식과 실패·복구

  1. 동일 sessionId + batchNo에는 최대 하나의 feed_batches row만 존재한다.
  2. commit 시점에 session owner, 만료, status, next_batch_no를 다시 확인한다.
  3. 이미 winner batch가 존재하면 새 추천 결과를 저장하지 않고 winner를 반환한다.
  4. 다른 요청이 먼저 next_batch_no를 전진시켰으면 현재 계산 결과를 폐기하고 기존 batch 또는 기존 conflict 계약으로 복구한다.
  5. commit 실패·connection 오류 후 재시도는 같은 batch key로 idempotent하게 수행한다. 부분 저장이 외부 응답으로 노출되지 않아야 한다.
  6. commit 후 issue가 withdraw되면 hydration 단계의 기존 공개성 검증을 적용한다. transaction을 줄였다고 비공개 카드를 반환하지 않는다.
설계상 중요한 구분: 피드는 단순 SELECT가 아니다. session과 batch를 기록하므로 “읽기 요청의 계산”은 병렬화할 수 있지만, batch 상태 전이는 짧게 원자화해야 한다.

설계 이해·통제 점검 (design-control)

아래 self-check는 구현 승인이 아니다. 각 질문은 확정된 설계의 동작·불변식·실패 복구를 예측하는 용도이며, 브라우저의 선택 결과는 이 대화로 자동 전달되지 않는다.
