회원 인증·JWT·사용자/관리자 권한 구현 제어

승인된 설계를 코드와 실행 가능한 검증 증거로 옮기는 living control artifact다. 현재 상태와 변경 경계, 실패·복구 불변식, 실제 게이트 결과를 한곳에 기록하고, 구현 중 설계가 바뀌면 기준선으로 돌아가 재승인을 요구한다.

목적
승인된 회원 인증·JWT·사용자/관리자 권한 설계의 구현 상태와 검증 증거 관리

승인된 구조 리팩터링 실행 계약

사용자가 승인한 R1-A·R2-A·R3-A를 현재 인증 동작을 보존하는 구조 리팩터링으로 실행한다. 이 계약은 새 인증 정책을 추가하는 문서가 아니라, 이미 승인·구현된 정책의 책임 경계를 명확하게 만드는 구현 기준선이다.

결정·범위·완료 조건
결정실행 내용금지된 변경완료 조건
R1-A ORM 경계 일반 users·refresh session CRUD는 MikroORM EntitySchema의 findOne/insert/nativeUpdate로 수행한다. SELECT ... FOR UPDATE를 포함한 refresh rotation 원자 상태 전이만 명시적 SQL 경계로 남긴다. rotation의 잠금·used/revoked 의미 변경, ORM metadata와 실제 migration schema 불일치 일반 repository 메서드에 raw SQL이 없고, rotation/reuse 동시성 불변식과 기존 DB 계약 테스트가 통과한다.
R2-A 애플리케이션 경계 signup·login·refresh·logout을 독립 use case로 분리하고 session 발급·refresh token 보안 정책·session response mapping을 명명된 협력 객체로 이동한다. HTTP status, cookie 속성, JWT claims/TTL, refresh rotation/reuse 결과, public error shape 변경 controller는 HTTP adapter로 남고 각 use case가 필요한 port만 의존하며, 기존 unit·contract·Compose smoke가 통과한다.
R3-A Principal guard는 검증된 AuthPrincipal 하나를 request에 주입하고, CurrentUser parameter decorator가 이를 controller에 전달한다. role guard도 동일 principal만 사용한다. body/query의 user id 사용, JWT role claim 권한 부여, optional id/role 필드의 재도입 /me/**가 decorator principal의 userId만 사용하고, 미인증·role demotion·admin seam 테스트가 통과한다.

구현 경계와 상태 전이

  1. controller는 입력·cookie·Authorization scheme을 경계에서 해석하고 각 application use case는 credential과 session workflow를 적용한다.
  2. JWT guard는 signature/issuer/audience/expiry를 검증한 뒤 users를 조회하여 principal id와 current role을 request에 주입한다.
  3. role guard는 principal의 DB role만 사용한다. JWT role claim이나 body role은 권한 근거가 아니다.
  4. refresh row는 active → used(정상 회전) 또는 revoked(로그아웃/재사용 대응)로만 전이한다. expired row는 재활성화하지 않는다.
  5. 회원가입·로그인은 refresh session 발급까지 성공해야 외부 성공 응답을 반환한다. 실패 transaction은 users/session의 부분 상태를 남기지 않는다.
주의: 현재 onboarding migration은 base schema가 users를 소유한다고 기록한다. 실제 base DDL과 데이터가 확인되지 않은 상태에서 kakao_id drop은 되돌릴 수 없는 영향을 가질 수 있으므로 migration 실행 전 preflight 증거를 남긴다.

읽기 전용 critical review

리뷰 유형은 자기 변경(self-change)이다. 승인된 설계 기준선, 실제 구현 흐름, 생성 계약과 fresh gate 결과를 대조했다. 이전 REV-001은 수정·재검증되었고, G14-A 적용 후 Compose bootstrap blocker를 해소했다. 이번 구조 리팩터링도 동일한 기준선으로 no-write 재점검했다. 운영 base schema 호환성·정책 확인과 non-blocking risk는 별도 잔여 항목으로 남긴다.

리뷰 finding
ID심각도·상태관찰된 사실·영향최소 조치·검증 공백
REV-001 fixed · blocker 해소 POST /auth/login·POST /auth/refresh가 명시적 status 없이 Nest 기본 201을 사용하여 G13-A의 200과 불일치했다. @HttpCode(HttpStatus.OK) 추가, SDK/OpenAPI status 200 확인, contract·build·smoke 재실행 통과
REV-002 해결됨 · local contract README.md가 secret 준비 없이 docker compose up --build를 안내했고, production 설정에서 빈 secret과 Secure policy로 startup이 실패할 수 있었다. README에 local .env 준비를 추가하고 Compose가 NODE_ENV/AUTH_COOKIE_SECURE를 env-file에서 받도록 수정했다. secret 미설정은 Compose interpolation에서 명시적으로 실패하며, production fail-closed는 유지한다.
REV-003 해결됨 · Compose 범위 fresh Compose volume에는 users base schema가 없어 onboarding migration이 실패하고 signup이 500이 됐다. G14-A로 Compose에만 disposable base fixture, runtime migration runner, API dependency를 추가했다. fresh volume에서 두 migration applied와 npm run test:smoke:compose 통과를 확인했다. 실제 운영 base schema/data compatibility는 여전히 별도 확인 대상이다.
REV-004 논의 필요 · open Origin 검사는 refresh/logout에만 호출된다(auth.controller.ts:66,79). signup/login도 refresh cookie를 설정하므로, G9의 “same-site only”가 모든 cookie-setting auth endpoint를 뜻한다면 cross-site POST에 의한 login/signup CSRF가 남는다. G9 적용 범위를 확정한다. same-site 전면 정책이면 signup/login에도 Origin 검사를 추가하고 cross-origin 시나리오를 검증한다. 예외를 허용하면 그 정책과 login-CSRF 영향을 명시적으로 승인한다.
REV-005 Non-blocking risk · open refresh_sessions의 used/revoked/expired row를 정리하는 retention job이나 삭제 정책이 없다. 로그인·rotation이 반복되면 테이블이 계속 증가한다. expires_at grace period를 둔 정리 작업과 운영 모니터링을 별도 설계하고, FK/인덱스 부하를 확인한다.
REV-006 fixed · 구조 리팩터링 범위 monolithic AuthService가 workflow·token/session policy·email validation·response mapping을 모두 소유하고, request에 id/role optional field가 따로 존재했다. 네 개 use case, EmailAddress, SessionIssuer, pure session mapper, AuthPrincipal/@CurrentUser()로 분리했다. typecheck·unit·integration·contract·Compose smoke 통과
REV-007 fixed · runtime DI 첫 fresh Compose에서 JwtAuthGuard → AccessPrincipalService 의존성을 OnboardingModule이 resolve하지 못했다. AccessPrincipalService를 AuthModule exports에 추가하고 image rebuild 후 API healthy 및 전체 auth smoke 통과

리뷰 판단: 구조 리팩터링과 fresh Compose의 구현 blocker는 해결됨. 운영 base schema/data compatibility는 실제 운영 DB 적용 전 남은 검증 공백이며, REV-004는 G9 정책 확인 사항, REV-005는 non-blocking 운영 위험이다.

잔여 위험과 중단 조건

  • base schema/data를 확인하지 못한 채 destructive migration을 실행하지 않는다. 실제 column ownership 또는 기존 email 충돌이 발견되면 구현을 중단하고 설계를 재승인한다.
  • Argon2id가 운영 runtime에서 로드되지 않거나 비용이 허용 범위를 넘으면 KDF를 임의로 바꾸지 않고 parameter/runtime 결정을 재승인한다.
  • refresh 동시성에서 두 요청이 성공하거나 used row가 재활성화되면 API 완료로 판정하지 않는다.
  • 현재 DB role이 반영되지 않은 채 JWT claim만으로 admin 접근이 허용되면 G4 위반으로 판정하고 수정한다.
  • access/refresh/password/secret이 log, error detail, generated fixture에 나타나면 redaction과 fixture를 즉시 정리하고 재검증한다.
  • G14-A fixture는 local disposable schema일 뿐 운영 base schema의 호환성 증거가 아니다. 운영 DB에는 fixture를 적용하지 않는다.
