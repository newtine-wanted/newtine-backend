목표와 현재 근거

현재 API 필터는 Nest Logger에 JSON.stringify 결과를 넘기고, batch는 Nest Logger와 console.error를 함께 사용한다. HttpRequestContextMiddleware는 requestId 생성·응답 헤더만 담당하며 서비스 로그의 자동 컨텍스트 전파는 없다.

성공 기준: 운영 로그 각 줄이 JSON으로 해석되고, 병렬 HTTP 요청·배치 실행의 식별자가 섞이지 않으며, parser 실패와 5xx 원인도 동일한 실행으로 조회할 수 있다.

적용 모델

Pino + nestjs-pino를 사용한다. 개발에서만 pino-pretty를 사용하고 운영은 stdout JSON으로 출력한다. 로그 변환용 자체 Logger 인터페이스·메서드 래퍼는 만들지 않는다.

책임과 파일 경계

일반 서비스는 Nest Logger 사용을 유지한다. 컨텍스트 생성·바인딩이 필요한 진입점에서만 PinoLogger의 공개 API를 사용한다. 도메인은 예외를 발생시키고 호출 경계에서 기록한다.

실행 순서

현재 app.useBodyParser 등록은 모듈 미들웨어보다 빠르다. 구현 시 parser를 로깅 다음의 명시적 미들웨어 순서로 옮기고 등록 순서를 검증한다. nestjs-pino 내부 storage나 deep import로 우회하지 않는다. 공개 API로 순서를 보장할 수 없다면 구현을 멈추고 설계를 보완한다.

로그 필드와 출력 정책

  • 공통: time(UTC), level, service(api/batch), context(클래스), event, msg.
  • HTTP 컨텍스트: requestId, method, path. path는 query를 제외한다. 서비스 이벤트와 예외 로그가 같은 식별자를 갖는다. 실패에는 status, 진단용 durationMs를 기록하며 연결 중단 시 실제 전송되지 않은 status를 확정 응답처럼 기록하지 않는다.
  • 예외: exceptionName, domain, domainCode, apiCode. 4xx는 warn, 5xx는 error. 5xx는 `exceptionDiagnostic`으로 message 원문과 stack 첫 줄을 제외하고 cause 이름·stack frame만 깊이 제한으로 기록한다.
  • batch: jobName, executionId, durationMs. HTTP requestId는 붙이지 않는다. 공개 runInContext 지원 버전 확인 후 사용하고 자체 AsyncLocalStorage 중복 구현은 피한다.
  • LOG_LEVEL: 운영 기본 info, 명시적 development 기본 debug. 허용값 검증. pretty는 development에서만 사용한다.
  • 허용한 필드만 기록. body·query·headers·응답 본문·원본 request/response 객체는 기본 제외. redaction은 알려진 비밀 필드에 대한 추가 방어다.
  • 예외 메시지 속 문자열은 필드 redaction으로 자동 보호되지 않는다. 메시지에 토큰·요청 원문을 넣지 않는 기존 규칙 유지.
  • health를 포함한 모든 HTTP 요청에서 자동 시작·완료 로그를 끈다(autoLogging: false). 컨텍스트는 계속 생성한다. 중요한 업무 결과는 서비스가 info 이벤트로 명시적으로 기록한다. 예외적으로 느린 정상 요청은 완료 시 http.slow를 기록한다. 현재 파일럿에 임의의 비즈니스 이벤트를 추가하지 않는다.

실패는 필터에서 warn/error 진단 한 번만 기록하고 HTTP 실패 요약은 추가하지 않는다. 연결 중단은 자동 로깅을 끄면 별도 감지가 필요하다. 요청별 기록 상태로 parser의 중단 예외와 응답 close 이벤트 간 중복을 억제한다. 정상 응답 뒤 close는 중단이 아니다. 먼저 예외 진단을 기록한 요청은 중단 로그를 추가하지 않으며, 중단이 먼저 관측되어도 이후 예상 밖 5xx의 제한된 stack/cause 진단은 숨기지 않는다. 서로 다른 중단·5xx 사건은 최대 한 번씩 기록하고 같은 requestId로 연결한다.

지연 관측 · 전체 분포는 메트릭, 개별 진단은 느린 요청 로그

사용자 합의: 모든 요청의 지연 분포와 느린 요청 추적을 함께 설계한다. 일반 정상 요청을 전부 로깅하지 않는 정책은 유지한다. 메트릭은 집계 데이터이며 requestId별 기록 저장소가 아니다.

결과별 관측 규칙
결과 로그 메트릭
정상·기준 미만 자동 로그 없음 완료 지연·요청 수·상태 집계
정상·기준 이상 http.slow warn 1회 완료 지연·요청 수·상태 집계
예외 응답 기존 예외 진단에 durationMs 포함. http.slow 추가 안 함 응답 finish 시 실제 상태·완료 지연 집계
연결 중단 기존 중단 감지·중복 억제 정책 적용. http.slow 없음 중단 건수 별도 집계. 완료 지연 분포와 분리

측정 시작은 parser 앞의 HTTP 진입 미들웨어다. 단조 시계(process.hrtime.bigint 등)로 측정하고 응답 finish에서 완료 시간을 확정한다. 이는 서버 진입부터 응답을 운영체제에 넘기는 시점까지이며 클라이언트 수신·프록시 대기·전체 네트워크 지연을 뜻하지 않는다.

예외 진단의 durationMs는 예외 처리 시점까지의 경과 시간이다. 완료 histogram은 finish까지 측정하므로 값이 다를 수 있다. 예외 진단을 지연 기록하거나 두 번 출력해 숫자를 맞추지 않는다. 완료·중단 terminal 상태를 요청당 한 번만 확정하여 finish 다음 close를 중복 집계하지 않는다.

느린 요청 로그 · 적용 기본값 제안

HTTP_SLOW_THRESHOLD_MS 기본 1000ms, 양의 유한 정수로 검증한다. durationMs가 기준 이상이고 2xx/3xx로 완료된 요청에 event=http.slow, requestId, method, path(query 제외), status, durationMs를 기록한다. health도 느리면 같은 정책을 적용한다. 완료 시점 기준이므로 끝나지 않는 요청의 실시간 탐지·timeout은 별도 설계 대상이다.

메트릭 집계 계약

  • 완료 지연: histogram, 초 단위. 요청 수·상태별 비율은 histogram count와 상태 label에서 산출할 수 있으므로 동일한 별도 counter는 필요할 때만 추가한다.
  • label은 정규화한 method, route 패턴, 유한한 status로 제한한다. /users/:id처럼 묶고 requestId·사용자 ID·실제 URL·query·메시지는 label에 넣지 않는다. 미지원 method는 OTHER로 묶는다.
  • 라우트가 확정되지 않은 parser 오류와 미등록 경로는 UNMATCHED로 집계한다. 실제 URL에서 임의로 라우트 패턴을 추측하지 않는다. 등록 라우트의 업무 404와 구분한다.
  • 중단은 별도 counter로 method·route만 집계한다. 전송하지 않은 status를 200·499 등으로 꾸미지 않는다.
  • health는 고유 route로 집계하되 업무 지연 대시보드에서는 분리한다. 향후 메트릭 수집 endpoint는 자기 관측을 제외한다. 수집기 scrape 주기와 시간 창을 기준으로 p95/p99를 계산한다.
  • 여러 인스턴스의 histogram을 합쳐 분위수를 계산한다. 인스턴스별 p95를 평균내지 않는다. 분위수는 histogram 해상도에 따른 추정값이다.

구현 범위 분리

1차 로깅 적용: 공통 타이머·느린 요청 로그·실패 경과 시간·중복 방지. 2차 메트릭 적용: histogram 계측, 수집·보관·조회 연결. 둘의 측정 시작·완료 의미는 공유한다. 1차만 구현된 상태를 전체 지연 분포를 조회할 수 있는 상태라고 보고하지 않는다.

메트릭 라이브러리·export 방식·수집기 배치와 접근 경계는 2차 구현 전 결정한다. 현재 설계 반영만으로 공개 /metrics endpoint나 외부 인프라를 추가하지 않는다. histogram 종류·버킷은 선택한 라이브러리와 수집기 호환성, 관심 지연 구간에 맞춰 확정한다.

보존해야 할 동작

  • 서버가 만든 하나의 UUIDv7을 헤더·request.requestId·로그가 공유한다. 클라이언트 x-request-id를 그대로 신뢰하지 않는다.
  • 잘못된 JSON(400), 용량 초과(413), 미등록 route(404)도 식별자와 예외 진단 로그가 남는다.
  • 실패 body는 title/status/detail/code, media type은 application/problem+json 그대로 유지한다.
  • 5xx 응답에 내부 원인을 노출하지 않는다. 같은 예외를 service·filter·자동 HTTP logger가 반복 진단하지 않는다.
  • 동시 실행 컨텍스트가 격리되고, batch가 실패하면 종료 코드 1이 보존된다.

실패·종료 처리

초기화 전후의 로그 유실을 막도록 bootstrap logger와 Nest 교체 시점을 정한다. bufferLogs를 사용하면 standalone batch의 flushLogs도 처리한다. 동일 로그를 두 logger로 재출력하지 않는다.

일반 운영 출력은 stdout 직접 기록으로 시작한다. 정상 종료에서는 자원 종료와 남은 로그 처리를 기다리고 process.exitCode를 사용한다. SIGKILL·프로세스 강제 중단·수집기 장애까지 전달 보장을 제공하지 않는다. 수집기가 느리거나 끊기는 운영 환경은 별도 관측 대상이다.

의존성 버전·공개 API 및 종료 방식은 설치 버전에서 확인한다. 현재 Node 24/Nest 12와 문서의 nestjs-pino v5 호환표는 부합하나 main 브랜치 기능을 출시 패키지 지원으로 단정하지 않는다.

이번 범위 밖

외부 로그 수집기 배포, 보관 기간·대시보드, OpenTelemetry 분산 추적, 감사 로그, DB query 로그 통합, 업무 기능·DB 영속화는 별도 작업이다. 기존 MikroORM 개발 debug 로그는 이번 통일 범위에서 제외한다.

메트릭 관측 정책은 설계에 포함한다. 메트릭 수집·조회 구현은 1차 Pino 적용과 분리하며, 2차 상세 설계와 승인이 필요하다.

설계 의사결정 질문 (grilling)

진행 상태: 완료. G1 및 공유 이해 확인: 정상 자동 로그 없음, 중요 업무 이벤트·실패·중단 중심으로 기록하며 요청 컨텍스트는 유지한다는 요약에 사용자가 “ㅇㅇ 그렇게 하자”로 동의했다. 이는 정책 합의이며 별도 구현 승인으로 취급하지 않는다.

결정 트리: Pino 선택 → 출력·컨텍스트 설계 → G1 기록 범위 확정 → 검증 기준 반영 완료. 1차 로깅의 남은 사용자 의사결정 frontier는 없다. parser 등록 순서와 출시 버전 공개 API는 구현 시 검증 항목이며, 불일치 시 변경 범위를 재검토한다.

G1 · 정상 HTTP 요청도 기록할까?

결정: 기존 A(모든 요청 완료 로그)는 채택하지 않는다. 정상 요청 추적을 위한 일괄 로그 비용을 지불하지 않는다. 후속 합의에 따라 느린 정상 요청만 예외적으로 기록하고 전체 지연 분포는 메트릭으로 집계한다.

B를 보완: HTTP 실패 완료 요약도 제거하고 예외 필터 진단만 기록한다. 중요한 비즈니스 이벤트는 서비스에서 명시적으로 기록한다. 자동 로그 제외는 HTTP에 적용하며 batch의 실행 시작·완료·실패 로그는 유지한다.

잔여 한계: 일반 정상 요청의 개별 지연·결과는 로그로 복원할 수 없다. 외부 수집기와 보관 정책은 이번 범위 밖이다.

G2 지연 관측 조합: 전체 메트릭 + 느린 요청 로그에 사용자 동의 및 설계 반영 요청 확인. 메트릭 수집·조회 상세 선택은 2차 범위로 명시적으로 분리한다. 1000ms는 변경 가능한 제안 기본값이며 사용자가 별도로 정한 SLA가 아니다. 1차 Pino 로깅 구현 범위는 승인됐다.

대안과 배제 이유

Nest JSON logger 단독은 가능하지만 요청·작업 컨텍스트와 정책을 직접 보완해야 한다. Pino 자체 래퍼·별도 logging 패키지는 초기 단계에 추상화를 늘린다. 기본 nestjs-pino 등록만 추가하는 방식은 현재 parser 오류 경로를 포괄하지 못한다.

출력 운영 로그 줄별 JSON 파싱, 필수 필드·level·service, JSON 문자열 이중 인코딩 없음.
HTTP 동시 요청의 테스트용 서비스 이벤트·헤더 식별자 일치와 격리. 기준 미만 정상 200 및 health에서 자동 로그 0건, 느린 2xx/3xx에서 http.slow 1건, 400/413/404/500에서 필터 진단 1건. 중요 이벤트의 명시적 기록.
진단 4xx warn·5xx error, 제한된 stack/cause, 예외 진단 중복 없음. 정상 close 중단 로그 0건, body 수신 중·응답 전 연결 중단 감지. parser 중단 예외와 close 경합에서 중복 억제, 중단 뒤 별도 5xx가 발생하면 원인 진단 보존.
지연 정책 기준 직전·정확한 경계·직후, 설정값 검증, 느린 실패의 slow 로그 0건, 예외 시점 durationMs와 finish 시간 구분. 중단·정상 close 중복 방지.
2차 메트릭 완료 요청당 histogram 관측 1회, 상태별 건수, 중단 counter 분리. 가변 ID 경로의 동일 route label, 미등록 경로·parser 오류의 UNMATCHED, method 제한. 실제 수집기에서 수집·다중 인스턴스 집계·분위수 조회까지 검증해야 운영 조회 완료다.
정보 제외 body·query·authorization·cookie에 sentinel을 넣어 출력 전체에서 누락 검증. 오류 URL 경로도 확인.
batch 성공·실패·알 수 없는 job, 실행별 컨텍스트 격리, 종료 코드·마지막 로그 flush.
생명주기 초기화 실패·listen 실패·정상 종료·연결 중단에서 로그와 종료 동작 확인.

예정 명령: npm run typecheck, npm run lint, npm run format:check, npm test, npm run build, npm run test:smoke, npm run contracts:check. 소스·실제 HTTP 테스트 fixture에 검증 로그를 넣고 운영용 테스트 route는 추가하지 않는다.

설계 단계에서는 소스·공식 문서를 조사했다. 설치·런타임 확인은 구현 제어 문서의 검증 증거에서 다룬다.

설계 이해·통제 점검

상태: 미실시. 정책 합의 후 예측 중심의 self-check를 제공한다. 브라우저 결과는 로컬에만 남고 Codex에 자동 전달되지 않는다. 결과 미전달은 구현 승인 요청을 막지 않는다.

커버리지: C1 요청 격리·parser 실패, C2 로그량·중단·중복, C3 민감정보·계층 경계, C4 batch 종료·보장 한계. C5 지연 메트릭·label·조회 경계. 외부 수집기 상세 운영은 2차 설계까지 보류한다.

총 5문항

C1 · 동시에 온 정상 요청과 잘못된 JSON 요청의 로그는?

C2 · 정상 완료, 400 예외, 연결 중단에서 기대하는 기록은?

C3 · 서비스에서 중요한 업무 성공을 기록하려면?

C4 · batch 실패와 강제 종료 시 보장 범위는?

C5 · /users/123과 /users/456의 지연 관측은?

미실시 · 구현 승인과 별개입니다.

승인 상태

설계 승인됨 · G1/G2 정책 합의 및 1차 구현 승인이 반영됐다. 이해 점검은 미실시다. 1차 범위는 API·batch Pino 적용, 컨텍스트·예외·중단·느린 요청 처리, 공통 설정과 검증이다. 2차 메트릭 상세 설계·구현은 별도 범위다.

구현 기록은 logging.implementation.html에 남겼다. 승인 기준 시각은 2026-09-12이며, 메트릭 수집·조회와 비즈니스 이벤트 표준은 보류 범위다.
