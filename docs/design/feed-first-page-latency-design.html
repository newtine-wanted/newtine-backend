2. 범위와 제외

범위: 추천 계산 상한, 피드용 기사 개수 집계, 후보 ID 조회 경량화, 알고리즘 세션 버전, 회귀·성능 검증 설계.

제외: 사용자별 사전 계산, 공유 피드 캐시, Redis, worker thread, 응답 후 비내구성 백그라운드 계산, 커넥션 풀 확대, 인스턴스 증설, DB 스키마 변경, 운영 상세 SQL 로그, API 응답 형식·cursor 변경, 프런트엔드 변경, region 이동.

후보·카드 내부 typed projection과 compact interaction/context read는 범위에 포함한다. 다만 후보 전체를 무조건 최종 10개로 줄이는 새 SQL/CTE는 이번 기준에 넣지 않는다. 목표 미달이면 단계별 측정으로 cross-region RTT·pool acquire·DB 실행·CPU를 구분한 뒤 별도 설계한다.

2026-09-22 승인·반영된 후속 delta: interaction cardinality에 비례하는 JS ID 목록과 후보 bind를 제거하기 위해 user ID 기반 QueryBuilder subquery($nin, generated NOT IN), acted category subquery, latest LIKE·verified later FOLLOW_UP 연결 predicate를 후보 DB 경계에 적용했다. issue_id NOT NULL 전제 아래 행동 제외 의미는 cap 없이 보존하고, connected flag는 후보를 선별한 같은 SELECT에서 계산해 별도 hydration 왕복을 제거했다. 이 delta는 API·cursor·schema·pool·transaction 경계를 변경하지 않는다.

3. 변경 모델

기존 코드의 IssueFeedService → IssueQueryRepository → recommendFeed → 저장 경계를 유지한다. 동기 계산량 제한은 같은 Node 프로세스의 다른 요청 지연도 완화할 수 있지만, 동시성 성능은 별도로 검증해야 한다.

4. 추천 v2: 유효한 결과부터 확보하고 탐색을 끝낸다

  1. 기존 scoring, eligibleTypes, 후보 예산 B(기본 100, 최대 500), 희소 유형 우선 quota matching을 유지한다. 추천 목표 비율 4/2/1/2/1은 유지하되 전역 최적 충족은 보장하지 않는다.
  2. 기존 matching의 최대 10개 seed와 전체 B개 후보에서 각각 결정적인 greedy 순서를 만든다. 각 단계에서 중복·연속 제한을 먼저 확인한다. seed의 선택 유형을 유지하며, 추가 후보는 eligibleTypes 안에서 미충족 quota 우선, 기존 유형 우선순위로 동률을 푼다. seed 포함 여부 → quota 기여 → 점수 → ID 순으로 다음 후보를 고른다.
  3. 전체 후보 greedy는 처음 10·100개에서 멈추지 않는다. B개 모두가 후보가 되므로 앞 110개가 같은 주제여도 뒤의 대안을 볼 수 있다. 두 greedy의 후보 검사량은 최대 20B로 제한한다.
  4. 두 greedy를 모두 완료하고 기존 기준(길이 → capped quota 합 → 점수 합 → ID 순서)으로 비교한다. 둘 중 유효한 10개가 있으면 반환한다. quota가 덜 채워졌어도 더 나은 10개를 위한 순열 탐색은 하지 않는 것이 이번 제안의 명시적인 품질·지연 절충이다. 단, 기존 희소 유형 회귀 fixture는 통과해야 하며 실패를 허용하도록 테스트를 바꾸지 않는다.
  5. 둘 다 10개 미만이면 기존 순서·교체 탐색을 상한 안에서 수행한다. 호출 전체 공유 transition 최대 10,000회, replacement proposal 최대 24개. 초기 seed 탐색과 모든 대안이 같은 예산을 쓰며 반복마다 초기화하지 않는다. 반환 기준에 도달하면 즉시 중단한다.
  6. 시도 횟수는 제약 검사·메모 적중으로 탈락하는 시도도 포함한다. 대안 생성도 B와 proposal 상한으로 제한한다. 부분 탐색 결과를 완전 탐색한 memo로 저장하지 않는다. 예산이 끝나도 이미 확보한 유효 prefix보다 나쁜 결과로 교체하지 않는다.

10,000/24는 검증할 초기 설계 상한이지 50ms 보장값이 아니다. 동기 루프를 멈추지 못하는 Promise.race 타임아웃은 쓰지 않는다. wall-clock 기반 중단 대신 같은 입력·버전에서 결정적인 횟수 제한을 사용한다. 후보 사전 정렬은 루프 밖에서 수행한다.

기존 API에서 SEARCH_LIMITED는 다음 cursor를 주지 않으며 새 배치 요청은 충돌로 끝난다. v2가 이 상태를 늘리면 사용자 경험 회귀다. 같은 주제·인물만 있는 소규모 풀처럼 증명 가능한 사례는 기존 CONSTRAINT_LIMITED를 유지하고, 나머지는 보수적으로 분류한다. 짧은 응답을 정상적인 10개 성공으로 집계하지 않는다.

증명 규칙: candidate sentinel이 없고 모든 eligible 후보를 반환했으며 10개 미만이면 EXHAUSTED. 후보가 남았으면 (a) 전체 eligible pool이 10개 이하이고 공유 예산 안에서 전체 순서 공간의 최대 길이를 확인했거나, (b) 전체 pool이 동일한 non-null 주제 또는 대표 인물이라 이전 run을 반영한 길이 상한을 계산했고 그 상한을 달성한 경우에만 CONSTRAINT_LIMITED. 그 외의 짧은 greedy/pruned 결과는 예산을 다 쓰지 않았어도 SEARCH_LIMITED다. 후보 sentinel이 있으면 전체 풀 증명으로 취급하지 않는다.

5. 조회 경량화: 계약은 유지하고 불필요한 로딩 제거

새 세션 첫 페이지는 생성 결과를 내부 batch 경로에 전달해 session·빈 batch 재조회를 건너뛴다. 후보 추천과 저장 batch 카드 응답은 각각 typed projection port를 사용하고, 상세 findIssue의 public/detail 결과는 그대로 둔다. 이것은 외부 API 응답을 바꾸지 않는 내부 repository contract 변경이다.

  • 추천 projection은 issue score·topic·representative entity·entity/impact 신호와 public 상태만 읽고 기사·언론사·상세 payload를 hydrate하지 않는다. 응답 card projection은 title·category·summary·score·event/publication과 article count만 읽는다.
  • feed에서는 기사 링크·기사 본문·언론사 entity를 hydrate하지 않는다. 선택된 issue IDs에 대해 링크와 AVAILABLE 기사만 JOIN하여 issue별 개수를 한 번에 집계한다. 누락 그룹은 0, PostgreSQL count 문자열은 안전한 숫자로 변환한다.
  • (issue_id, article_id) 유일 키 기준으로 현재 availableArticles 길이와 동일한 링크 수를 센다. REMOVED/UNAVAILABLE 기사는 제외한다. impact/entity JOIN으로 개수를 증폭시키지 않는다.
  • 집계는 ORM QueryBuilder의 매개변수화된 scalar projection을 우선 사용한다. 승인된 repository ORM 경계를 유지한다. raw SQL helper로의 전환은 자동으로 범위를 넓히지 말고 근거와 함께 상위 판단으로 돌린다.
  • 최초 후보 slice는 QueryBuilder로 ID만 읽는 projection으로 변경한다. 기존 slice 순서, 정렬, seenIds, budget+1 sentinel 및 slice 후 공개 검사를 보존한다. 서로 의존하는 slice들을 무작정 병렬화하지 않는다.
  • 부분 entity가 identity map에 남아 이후 full load를 오염시키지 않아야 한다. generated SQL과 동일 EntityManager 내 연속 조회 회귀로 입증한다.
  • 추천 projection에는 알고리즘에 필요한 impact/entity 배열을 유지하고, 카드 projection에는 public/card 판정에 필요한 summary와 score를 유지한다. 반환형을 빈 값으로 채워서 경량 DTO인 척하지 않는다. 저장 후에는 락 안에서 결정된 canonical batch를 사용하고 별도 batch 재조회는 하지 않는다.

6. 바꾸면 안 되는 조건

  • 최대 10개, 중복 없음, 이전 배치와 사용자 최신 interaction 대상 제외, 소유권·만료 검증.
  • PUBLISHED, 유효한 summary와 score 등 기존 public/card 조건. 응답 직전 비공개 전환 항목은 기존처럼 제외하며 임의 보충하지 않음.
  • 동일 topic / representative entity 3연속 금지, 이전 배치의 run 상태 포함, null의 현재 의미 유지.
  • 선택 유형은 eligibleTypes 안에서만 부여, reasonCodes와 선택 유형 일치. 검증된 FOLLOW_UP과 LIKE·eventAt 조건 유지.
  • 저장된 배치 재요청은 기존 ID·순서·이유를 재사용. 병렬 생성 경쟁은 기존 DB 승자 결과로 응답. transaction과 락 범위를 확장하지 않음.
  • 기사 상세의 내용·순서·언론사 fallback 불변. 회원 데이터가 게스트·다른 회원에게 섞이지 않음.

7. 세션 버전과 안전한 활성화

기존 feed_sessions.algorithm_version text를 사용한다. v1 구현은 기존 동작 그대로 보존하고 새 issue-card-query-v2로 분기한다. FeedAlgorithmSnapshot에 버전을 전달해 세션 생성 때 저장하고, 매 배치마다 환경값이 아닌 저장된 버전으로 실행한다. 예산 상수도 v2의 일부이며 조용히 변경하지 않는다.

  1. 호환 릴리스: v1/v2 모두 실행 가능, 새 설정 RECOMMENDATION_ALGORITHM_VERSION 기본값 v2. 지원하지 않는 설정은 시작 시 검증 실패. 새 세션은 v2로 생성한다.
  2. 새 세션은 v2를 사용하고 기존 v1 세션은 저장된 snapshot으로 v1을 계속 사용한다. v2를 모르는 오래된 revision에 새 v2 세션이 가지 않도록 호환 가능한 revision을 먼저 배포한다.
  3. 되돌릴 때는 새 세션을 v1로 돌리되 기존 v2 dispatch는 유지한다. 마지막 v2 세션의 24시간 TTL과 진행 중 요청 종료를 확인하기 전에는 v2를 모르는 바이너리로 rollback하지 않는다.

저장된 배치는 버전과 관계없이 기존 소유권·만료 확인 후 재사용한다. 미지원 버전에서 새 배치 계산은 기존 FeedBatchConflict로 명시적으로 거절하고 재탐색을 안내한다. 다른 버전으로 몰래 계산하지 않는다. 기존 v1 세션의 미생성 배치는 만료까지 이전 계산 비용이 남을 수 있다.

DB 오류·저장 실패는 가짜 성공이나 미저장 배치로 응답하지 않는다. 운영 500ms 미달 시 풀 크기나 예산을 임의 변경하지 않고, 테스트 환경의 단계별 시간으로 CPU·DB 왕복·저장·기타를 나누어 다음 설계를 결정한다.

8. 의사결정 기록과 남는 불확실성

진행 상태: 설계 결정·재승인·구현 반영 완료. 2026-09-21 승인 범위의 첫 조회 fast path·typed projection·canonical save·v2 기본값은 유지한다. 2026-09-22 독립 리뷰에서 acted category ORM hydration, 역방향 relation 인덱스 부재, 500~999ms 관측 공백이 확인되어 R5-A~E를 추가했고, 사용자의 schema 변경 금지 조건에 따라 source-first query·단일 회원 입력 read·500ms threshold를 구현했다.

의존 트리: 첫 응답 목표 → 사전 생성 금지·최적성 완화 → 계산 상한/조회 모드 → 세션 호환 → 성능·품질 검증 → 활성화.

대화에서 정해진 방향
첫 조회를 빠르게, 사용자별 사전 생성 제외, 충분히 좋은 추천 우선, 500ms를 검증 목표로 삼음.
기술 권고
결정적 bounded search + 첫 조회 fast path + typed recommendation/card projection + canonical save outcome. cache나 topology 변경보다 단계별 검증이 가능하며 API 계약은 유지.
R1-A 관측성
고정 stage 이름·owner/page kind·bounded count만 slow/sample 조건에서 기록한다. SQL·사용자 ID·토큰·본문은 기록하지 않는다. pool acquire wait는 DB/driver 관측으로 별도 확인한다.
R2-A 조회 전략
projection을 우선 적용한다. cross-region RTT나 pool acquire가 지배적이라는 측정이 있을 때만 후보 CTE/UNION 또는 topology 검토를 별도 설계한다.
R3-A 저장 경계
session row PESSIMISTIC_WRITE는 유지하고, lock 안에서 기존/신규 canonical batch를 반환해 저장 직후 재조회 왕복을 제거한다.
R4-A 운영 범위
region·pool·infra 설정은 이번 구현에서 바꾸지 않는다. API 응답·cursor·schema도 그대로다.
추가 결정
새 세션의 기본 알고리즘은 v2로 한다. `RECOMMENDATION_ALGORITHM_VERSION=issue-card-query-v1`로 신규 세션만 v1 rollback할 수 있으며, 기존 session snapshot은 변경하지 않는다.
R5-A~E 구현
category는 QueryBuilder scalar DISTINCT로 축약하고, connected predicate는 최신 사용자 LIKE에서 relation.from_issue_id로 시작하는 source-first 형태로 재작성해 같은 SELECT에서 flag를 반환하며, context·acted 입력은 단일 QueryBuilder read로 합치고, 기본 stage threshold는 500ms로 맞춘다. DB schema·migration은 변경하지 않는다.
검증 필요
10,000/24 예산으로 기존 품질 fixture 유지 가능 여부, 실제 서버 p95, 회원 이력 규모와 DB 왕복의 영향. 대화만으로 확정 불가.

채택하지 않은 대안

사용자별 미리 계산은 사용자 거절. 캐시·worker 이동은 계산 자체의 상한을 해결하지 않으며 별도 상태/실패 경계를 만든다. 후보를 무조건 적게 읽으면 희소 유형·뒤쪽 대안을 잃는다. 완전 최적 순열 유지에는 지연 상한이 부족하다. 전체 DTO 재설계는 이 안 실패 시 근거를 갖고 재검토한다.

성능 harness는 새로 만들 예정이며 아직 없다. 테스트 전용 메모리 측정으로 단계별 경과만 기록한다. SQL 원문·사용자 ID·토큰·본문을 새 운영 로그로 남기지 않는다. 로컬 환경에서 운영 RTT/cold start를 재현하지 못하면 미검증으로 남긴다.

핵심 위험: greedy의 조기 종료가 추천 품질/카드 수를 낮출 수 있음, 원인이 DB 왕복·풀·콜드 스타트라면 CPU 개선만으로 전체 목표를 못 맞춤, 과거 v1 세션 비용이 한동안 공존함.
