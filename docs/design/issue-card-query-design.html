최신 통합 설계안 — 공유 이해 확인용

G1~G23의 사용자 결정을 통합했다. 아래의 ‘확정 정책’과 ‘기술 제안·검증 필요’를 구분한다. 과거 질문·변경 전 초안은 하단 결정 이력으로 보존하며 현재 구현 지시로 사용하지 않는다. 구현 결과·운영 제어·실측 성능 검증은 대응 구현 문서에서 별도로 관리한다.

확정 정책

  • 피드는 무한 탐색이며 내부 요청 단위는 최대 10장이다. 카드별 조회 요청이나 평가 완료를 기다리는 흐름이 아니다. 요약은 묶음에 포함하고 이전 5장 복귀는 클라이언트 버퍼로 처리한다.
  • 목표 배분은 개인화 4 / 주요 2 / 후속 연결 1 / 탐색 2 / 반대 1. 후보 부족 시 다른 적격 유형으로 보충하되 공개·중복·행동 제외·연속 제한을 완화하지 않는다.
  • 온보딩 주제·대상·관심 지역·나이대의 명시적 일치를 이용한다. 축별 일치와 적격 후속 연결 신호는 0/1. 모르는 정보는 불일치의 증거가 아니며 점수 기여만 0이다. 누락 계수 재배분·행동 누적 학습은 하지 않는다.
  • 점수는 주제 25%, 인물·기관 20%, 연결 관심 15%, 지역 10%, 세대 10%, 중요도 10%, 최신성 10%. 중요도·최신성 0~1 값의 생산·갱신은 다른 분기 책임이다.
  • 연결은 현재 최신 행동이 LIKE인 기준 이슈의 검증된 FOLLOW_UP만 허용하고, 양쪽 event_at이 알려져 있으며 후보가 더 늦어야 한다. 주제만 같은 관련 이슈는 연결 자격이 아니다.
  • 탐색은 온보딩 선택 주제와 과거 LIKE/SKIP/PASS가 있는 주제를 제외한다. 반대는 명시적 일치가 없고 알려진 불일치가 있으며 중요도 또는 최신성이 높은 후보다. ‘높음’ 수치는 생산 점수 계약 확인 전 미정이다.
  • 회원 행동 이력이 있는 이슈와 같은 탐색에서 전달한 이슈는 새 묶음에서 제외한다. 새 탐색의 미행동 재등장은 허용한다. feed session은 인증된 회원만 만들며 임의 userId나 guest credential을 사용하지 않는다.
  • 같은 주제·대표 대상은 최대 2장 연속이며 10장 경계에서도 이어 검사한다. 대표 대상은 생산자가 명시한다. 제약을 만족시키지 못하면 적게 제공하며 실제 소진으로 위장하지 않는다.
  • 다음 묶음 생성 시 읽은 확정 상태로 재추천한다. 이미 확정된 묶음의 ID·순서는 유지한다. 프리패치 뒤 발생한 행동이 다음 묶음에 늦게 반영될 수 있다.
  • PostgreSQL에 탐색·묶음·카드 ID를 저장한다. 같은 묶음 재시도는 복원이며 새 묶음 소비가 아니다. 본문은 최신 공개 내용을 읽고 철회 항목은 제거하되 재시도에서 보충하지 않는다.
  • 탐색은 생성 후 24시간 고정 만료. 최초 생성 응답 유실은 새 탐색 생성으로 처리하며 별도 생성 요청 키는 만들지 않는다(G23-B).
  • 유형별 제한된 후보를 비교하고 예산 안에서 추가 조회한다. 전체 후보의 전역 최적 순위를 보장하지 않는다.

확인된 구현 오류는 테스트 fake를 apps/api production module에서 provider로 등록하고 환경값에 따라 선택한 점, 그리고 IssueCardQueryRepository가 MikroORM EntityManager를 주입받고도 getConnection().execute()로 SQL 문자열을 직접 실행한 점이다. G28~G31 구현은 production 실행 그래프·repository port·ORM metadata 경계를 분리해 이 오류를 해소했다.

구현 결과

  • production API: IssueModule은 IssueCardQueryRepository만 등록하고 ISSUE_QUERY_REPOSITORY를 useExisting로 연결했다. NODE_ENV나 ISSUE_QUERY_REPOSITORY에 따른 fake 선택·fallback은 제거했다. transaction은 CoreModule의 MikroOrmTransactionManager 하나를 사용한다.
  • test fixture: InMemoryIssueQueryRepository와 passthrough transaction fake를 test/fixtures/ 아래로 이동했다. 테스트가 직접 생성·주입하며, tsconfig.build의 production compile 대상과 API module graph에는 포함되지 않는다.
  • ORM adapter: 이슈·상세·기사·관계·feed 상태에 대한 MikroORM EntitySchema를 core persistence metadata로 정의하고 database options에 등록했다. repository는 EntityManager.find/findOne와 entity persist/flush 경계만 사용하며 getConnection().execute(), SQL projection helper, 직접 parameter 조립을 제거했다. migration의 SQL은 schema evolution 책임이므로 유지하되 runtime read/write 경로와 구분한다.
  • 검증 실행: unit은 test fixture와 ORM boundary를 검증하고 integration은 metadata 등록을 검증했다. 실제 PostgreSQL smoke는 DB가 준비된 환경에서 별도로 실행하며, DB가 없을 때 fake로 성공시키지 않는다.

bounded candidate query: findCandidates는 public detail·scope relation·제외 ID predicate를 ORM criteria와 QueryBuilder subquery로 DB에 내리고, 각 weighted slice와 fill query에 결정적 ORDER BY·LIMIT을 적용한다. root query가 반환한 ID만 상세·impact·entity/article link와 기사 데이터로 bulk-load하며, full-table candidate materialization은 하지 않는다. direct SQL connection 실행은 추가하지 않는다.

후보 선정·배정 기술 제안

  1. 공개·유효 상세, 본인 행동 이력, 현재 탐색 전달 ID 제외를 ORM criteria/QueryBuilder subquery로 DB에서 적용한다. 최신 LIKE는 전체 종류 행동의 최신을 먼저 구한 후 판정한다.
  2. 유형별 적격 후보를 우선순위와 결정적 issueId 동률 기준으로 제한 조회한다. 각 이슈는 여러 유형에 적격일 수 있지만 응답에는 한 번만 배정한다.
  3. 공통 후보 풀에서 4/2/1/2/1 자리와 후보 자격을 함께 고려한다. 개인화부터 단순 선점하여 유일한 후속 후보를 소모하지 않는다. 연속 제한까지 고려하는 결정적 탐색을 사용하되 탐색량에 상한을 둔다.
  4. 기술 제안의 목적 순서는 하드 제외·연속 제한 준수 → 가능한 전달 장수 → 목표 배분 충족 수 → 점수 → issueId 동률 순이다. 목표 배분이 가능한데 임의로 무시하지 않는다. 정확한 배정 탐색은 소규모 전수 비교 fixture로 검증한다.
  5. 부족하면 예산 내 추가 후보 조회·재배정한다. 한도에서 찾지 못한 것은 불가능의 증명이 아니다. 연속 제약을 위반하는 순서를 반환하지 않고 입증 가능한 상태를 반환한다.
  6. 선택된 최대 10개에만 요약·기사·관점 등 표시 데이터를 일괄 결합한다. 다대다 JOIN의 행 증가가 페이지 크기나 기사 수를 바꾸지 않게 한다. 후보 root query도 유형별 LIMIT을 유지해 전체 issue projection을 애플리케이션으로 가져오지 않는다.

대표 대상·주제가 사후 수정되면 이미 확정된 묶음은 재정렬하지 않는다. 연속 제한은 묶음 생성 시 읽은 분류 기준의 보장으로 정의하고, 다음 묶음은 현재 분류와 이전 전달 ID를 읽어 검사하는 제안이다. 최근 2장 메타데이터의 스냅샷 보존이 필요한지는 이 정의에 따라 구현 전 확정한다.

조회와 이벤트의 경계

  1. 외부 입력을 Typia로 검증하고 회원/비회원 맥락을 구분한다.
  2. PUBLISHED와 유효 상세 조건으로 후보를 확보한다.
  3. 선호·행동·현재 탐색 제외 조건을 적용하고 순서를 산출한다. 구체 알고리즘은 G1~G3 이후 확정한다.
  4. 최대 10개 요약·집계를 일괄 조회한다. 다대다 JOIN으로 행을 늘린 뒤 LIMIT 10을 적용하지 않는다.
  5. 상세 요청은 현재 공개 여부를 다시 검사하고 저장된 공통 상세·허용 개인 영향을 반환한다.

앱 service는 repository port에 의존하며 DB adapter를 직접 참조하지 않는다. 조회마다 LLM 호출 없음. 캐시·서버 추천 목록 저장소는 아직 선택하지 않았다.

불변식

  • 조회·프리패치만으로 행동 이벤트, 열람 확정, 선호 점수 변경을 만들지 않는다.
  • 전송된 카드, 실제 노출, 명시 행동을 동일시하지 않는다.
  • 회원 선호·영향은 검증된 본인 맥락만 사용하며 비회원에게 사용자 행을 생성하지 않는다.
  • 비공개·철회 이슈는 조회 응답에서 제외한다. 이미 클라이언트에 전송된 데이터의 즉시 회수는 조회 API만으로 보장하지 않는다.
  • 정치 성향·수혜 자격을 추론하지 않는다. 영향 미매칭은 영향 없음이 아니라 제공 가능한 설명 없음이다.
  • 추천 weight와 관심 통계 비율을 혼용하지 않는다.

핵심 위험

매번 바뀌는 추천 점수에 단순 OFFSET 또는 마지막 점수 커서를 붙이면, 선호·공개 상태 변화로 이미 받은 카드가 다시 나오거나 후보가 누락될 수 있다. 추천 갱신 주기와 중복 방지 범위를 먼저 결정한 뒤 페이지네이션을 선택해야 한다.

G1·G2 부작용과 성능 비교 — 제안, 미승인

G1은 무엇을 우선할지, G2는 어느 시점의 선호로 다음 묶음을 정할지다. 둘 다 A를 권고하되 아래 비용을 계약으로 제한해야 한다. 현재 DB 데이터량·요청률·실측 지연은 확인되지 않았다.

G1 추천 방식
안효과·부작용성능
A 선호 + 최신성·중요도 + 탐색관심 밖 이슈도 발견. 일부 카드는 당장 덜 맞을 수 있음. 예시 8개 개인화 + 2개 탐색은 설명용이며 비율 미확정. 중요도·최신성 척도와 선호 상한을 정의해야 함.한정 후보를 채점한 뒤 10개를 선택하는 제안. 탐색 선택 비용보다 DB 후보 조회·행동 제외·JOIN 범위가 지배적일 가능성. 실측 필요.
B 선호 우선선호 강한 분류에 집중하고 새로운 관심 발견이 어려움. 반복 LIKE로 가중치가 커지면 편중 심화 가능.같은 후보·제외·JOIN을 사용한다면 A보다 크게 싸다고 보장할 수 없음. 계산 항 몇 개 감소가 DB 조회량 감소를 뜻하지 않음.
C 임베딩 추가분류를 넘어 비슷한 이슈 탐색 가능. 유사성이 중요성이나 다양성을 보장하지 않음. 신규 사용자·벡터 누락 대안 필요.공유 이슈 벡터를 사전 생성하면 조회마다 LLM이 필요하지는 않음. 다만 모델·차원·갱신·검색·품질 검증 운영 비용 추가. 현재 방식·성능 미검증.

G1-A 실행 구조 제안: 공통 최신/중요 후보와 선호 분류·대상 후보를 합쳐 중복 제거 → 본인 행동 이력과 현재 탐색 전달 ID 제외 → 제한된 후보 채점·다양성 선택 → 선택된 10개만 요약·출처 집계 일괄 조회. 후보가 부족하면 추가 범위를 탐색하며, 후보 상한 도달을 전체 소진이라고 응답하지 않는다. 후보 제한은 전역 최상위 추천을 놓칠 수 있는 품질 절충이다.

G3-A 덕분에 과거 행동 제외는 최신 이벤트 정렬 없이 user_id/issue_id의 존재 여부로 처리할 수 있다. 추천 요청에서 이벤트 전체를 다시 합산하지 않고 별도 이벤트 분기가 갱신한 preferences를 읽는 안을 제안한다. 관련 인덱스와 EXISTS 실제 계획은 격리 DB에서 검증한다.

PostgreSQL ORDER BY 문서에 따르면 LIMIT이 작아도 정렬을 만족하는 인덱스가 없으면 상위 행을 찾기 위해 전체 입력을 처리할 수 있다. 사용자별 가변 합산 점수는 공통 인덱스 하나로 정렬이 해결된다고 가정하지 않는다. EXPLAIN으로 실제 스캔·정렬·버퍼를 확인해야 한다.

G2 갱신 시점
안사용자 경험부작용·비용
A 다음 묶음 요청 시남은 카드가 적을 때 다음 묶음을 프리패치 가능. 현재 버퍼는 고정.다음 묶음 요청 이후 수용된 행동은 이미 계산한 묶음에 미반영. 안 보고 이탈하면 프리패치 낭비. 선행 묶음 하나·동시 요청 하나로 제한 제안.
B 10개 탐색 및 이벤트 반영 후직전 묶음 행동까지 반영.이벤트 저장 대기 + 조회가 다음 카드 표시의 임계 경로. 이벤트 실패 시 계속 탐색할지 막을지 정책 필요. 사용자 DB lock으로 기다리지 않음.
C 탐색 시작에 전체 순서 고정계속 읽는 동안 순서 예측이 쉬움.시작 비용·보관 비용이 앞당겨짐. 중간 선호·새 이슈 반영 지연. 공개 철회 재검사는 계속 필요. 이벤트·현재 탐색 제외로 건너뛰기는 발생할 수 있음.
G2-A의 읽기 전용은 행동·선호를 쓰지 않는다는 뜻이다. 재시도 동일 묶음, 게스트 포함 탐색 중 무중복까지 요구하면 전달 ID·묶음 상태가 필요하다. 서버 보관은 쓰기·만료·동시 요청 관리 비용이 있고, 클라이언트/커서 보관은 크기·신뢰·다중 탭 한계가 있다. G2 선택 후 별도 저장 계약을 grilling한다. 서버 메모리나 Redis 도입은 아직 승인하지 않았다.

G12 계산 및 성능 검토

기본안은 한 사용자의 이슈별 최신 행동을 구한 뒤 LIKE만 선택한다. PostgreSQL DISTINCT ON(issue_id)와 ORDER BY issue_id, created_at DESC를 활용할 수 있다. 이벤트 작성 계약이 동일 사용자·이슈 시각의 엄격한 순서를 보장해야 한다. LIKE만 먼저 필터링한 뒤 최신을 구하면 취소된 LIKE가 되살아나는 오류가 생긴다.

인덱스 후보: (user_id, issue_id, created_at DESC), event_type 커버링은 실측 후 검토. 사용자별 탐색·정렬을 지원하지만 해당 사용자의 많은 이벤트를 처리할 가능성은 남는다. 최신 LIKE seed를 소수로 제한해도 DISTINCT ON 입력 스캔이 같은 수로 줄지는 않는다. 성능이 필요하면 최근 LIKE 후보에 더 최신의 모든 종류 이벤트가 없는지 NOT EXISTS로 검증하는 단일 SQL 대안을 비교한다. 후보를 먼저 고정 개수로 자르면 유효 seed가 뒤에 남아도 누락될 수 있으므로 상한과 부족 처리 계약이 필요하다.

새 묶음을 최초 계산할 때만 seed를 계산하고, 저장된 묶음 재시도에는 반복하지 않는 안을 제안한다. 이벤트 누적량이 많은 사용자를 포함한 EXPLAIN (ANALYZE, BUFFERS)로 인덱스·행 수·지연을 검증한다. 현재 상태 테이블 추가는 초기 필수사항이 아니며 측정 이후 별도 설계한다. 계산 비용을 이유로 과거 LIKE 정책으로 변경하지 않는다.

G14 연결 범위 충돌 — 해결, A
사용자 ‘기획대로’ 결정으로 A 확정: 새 문서의 후속 전용으로 변경. 검증된 FOLLOW_UP이며 event_at이 기준 이슈보다 늦은 후보만 연결 유형으로 인정. 후보가 줄면 G9 보충. B 기존 G8-A 유지: 후속 + 주제·대상 관련을 포함하고 후속에만 시간 조건 적용. 문서 내 표현 차이는 최종 정렬의 후속 전용을 따르는 것으로 해소했다. B는 기각. 시간 NULL·중심 대상 규칙은 아직 구체화 필요. 이번 결정은 정책 선택이며 전체 구현 승인이 아니다.
G15 현재 MVP 적용 범위 — 해결, A
사용자 확정: 온보딩 일치·현재 LIKE 연결 신호에 문서의 고정 7항목 비율과 배분·정렬을 적용하고 행동 누적 학습·감쇠 갱신은 후속 분기로 둔다. 계수 자체는 계산 비용이 작지만 각 신호의 0~1 변환 계약은 추가로 정의해야 한다. 이벤트 수집·쓰기는 별도 분기이며 이 선택은 전체 구현 승인이 아니다. 대안 B(고정 7항목 비율도 유예)는 채택하지 않는다.

설계 의사결정 질문 — 점수 입력 계약

사용자 ‘권고대로’ 답변으로 G16-A·G17-A 확정. 점수 생산자의 산식·갱신 주기는 검증 필요이며 그 전에는 높음 임계값을 임의 확정하지 않는다. 로컬 apps/libs에서 importance_score·freshness_score 및 camelCase 대응 이름을 검색했으나 산출 구현은 없고 ERD의 numeric 필드만 확인했다. 기본값 0은 실제 산정 완료의 증거가 아니다. 이번 단계는 설계 판단을 주 에이전트가 직접 수행하며 구현하지 않는다.

G16 일치도 계산 — 해결, A
A 사용자 확정: 주제·대상·지역·세대는 해당 축에 명시적 일치가 하나라도 있으면 1, 없거나 입력이 없으면 0. 연결 관심도는 현재 LIKE 기준의 G14 적격 후속이면 1, 아니면 0. 누락 축의 계수를 다른 축에 재배분하지 않는다. 미정보 0은 순위 기여 없음이며 반대 자격의 불일치 증거가 아니다. B 기각: 집합형 축은 일치한 후보 태그 수/후보의 전체 해당 축 태그 수, 후보 태그가 없으면 0; 세대·연결은 A와 같다. A는 단순하며 태그 수가 많은 이슈의 희석을 피하지만 일치 개수 차이를 구별하지 않는다. B는 일치 비율을 구별하지만 후보 태깅 양·품질에 순위가 민감하다. 이 결정은 입력 점수 테스트와 SQL 형태를 연다.
G17 중요도·최신성 산정 책임 — 해결, A
A 사용자 확정: 이슈 생성·갱신 측에서 0~1로 산정한 공통 점수를 제공하고 이번 조회 분기는 검증·읽기·가중합만 담당한다. 이는 현재 생산자가 구현됐다는 뜻이 아니다. 실제 산식·갱신 주기·값 유효성 계약은 제공 측과 확인할 필수 의존성으로 남기며, 미제공 상태를 실제 추천 완성으로 보고하지 않는다. B 기각: 이번 범위에 공통 점수 산정과 갱신까지 포함한다. B는 독립 완성이 가능하지만 사회적 영향·보도량의 측정 기준과 최신성 감소 함수 및 갱신 작업 설계가 추가된다. 조회마다 전체 후보의 상대 백분위를 계산하는 대체안은 채택하지 않는다. 이 결정 후 높음 임계값과 최신성 유효기간을 구체화한다.

G14의 엄격한 시간 비교에서 어느 한쪽 event_at이 NULL이거나 시간이 같으면 후속 자격을 입증하지 못한다. 따라서 연결 유형에서 제외하는 것이 확정 정책의 직접 결과이며 published_at 대체는 하지 않는 설계로 정리한다. 다른 유형 자격은 별도로 평가한다.

남은 후속 설계: 점수 계약 이후 높음 임계값·동률/보충 우선순위·후보 조회 예산, 정렬 분기의 중심 대상 정의·묶음 경계·연속 제한을 지킬 수 없는 경우 처리, 저장 분기의 수명·재시도·오류 계약. 이 항목들은 확정 또는 승인된 것으로 취급하지 않는다. 응답 형식: G16-A / G17-A — 필요하면 이유 한 줄.

유형 배정·부족분 기술 초안

개인화부터 순서대로 4장을 선점하면 연결에도 적격인 유일한 카드가 먼저 소모될 수 있다. 제안은 4/2/1/2/1의 10개 자리를 만들고 각 후보의 적격 유형을 연결해, 원래 배분을 가장 많이 충족하는 중복 없는 배정을 먼저 찾는 것이다. 같은 충족 수일 때 유형 내 순위, 최종 issue_id 기준으로 결정적으로 선택한다. 이슈 전체가 아니라 조회된 후보 집합 안에서의 최적 배정이며 후보 제한에 따른 누락 가능성은 별도 측정한다.

그 뒤 빈 자리는 남은 적격 후보에서 채운다. 보충된 카드에는 실제 적격 유형을 기록하며 없는 연결·개인화·반대 근거를 만들지 않는다. 출력 순서는 배분 장수와 별개로 분산하는 안을 제안한다. 유형별 최종 정렬과 보충 우선순위는 G13 점수 계약 이후 결정한다.

게스트·완전 무선호 사용자는 개인화·연결·반대 자격을 꾸며내지 않고 주요·탐색 후보로 보충한다. 나이대만 있으면 이슈의 명시적 세대 타깃과 비교할 수 있으나, 미분류 이슈를 불일치로 취급하지 않는다. 온보딩·이벤트·이슈 대상 데이터 제공 전 실제 개인화 완성을 주장하지 않는다.

연결은 확정된 최신 LIKE를 기준으로 검증된 FOLLOW_UP이며 기준 이슈보다 event_at이 늦은 후보만 인정한다(G14-A). 단순 주제·대상 일치는 연결 자격이 아니며, 해당 이슈는 별도 적격 조건을 충족할 경우 개인화 등 다른 유형에서 선정할 수 있다. 기준 LIKE 수를 제한한다면 전체 현재 관심 대비 후보를 놓칠 수 있으므로 그 범위와 비용을 명시해야 한다.

설계 의사결정 질문 — 연속 노출 제한

사용자 ‘권고대로’로 G18-A·G19-A 확정. 기획 근거는 같은 주제·중심 대상 최대 2장 연속이다. 내부 10장 묶음 경계에서도 직전 묶음의 마지막 2장을 이어 검사한다. 이전 카드 돌아보기는 서버의 신규 전달 순서와 구분한다.

G18 중심 대상 정의 — 해결, A
A 사용자 확정: 이슈 생성 측이 명시적으로 제공한 대표 대상 1개를 기준으로 한다. 현재 확인된 issue_entities에는 대표 표시가 없어 데이터 계약 추가가 필요하다. 생성 측의 판정을 조회 시 추측하지 않으며 제공 전 대상 다양성 구현 완료로 보고하지 않는다. 대표 대상이 없다는 명시적 판정과 데이터 미제공은 구분한다. B 기각: 현재 연결된 모든 대상 중 동일 대상이 세 카드에 공통이면 연속 제한에 걸린 것으로 본다. 스키마 추가 없이 가능하지만 주변 인물·기관까지 중심 대상으로 취급하는 보수적 근사이며 기획 의미와 차이가 있다. 선택 후 필요한 생산자 계약 또는 집합 비교와 검증을 정의한다.
G19 연속 제한과 장수 충돌 — 해결, A
A 사용자 확정: 2장 제한을 지킨다. 다른 적격 후보로 교체·재배치해도 불가능하면 10장 미만 반환하며 제한 위반으로 채우지 않는다. 후보가 남아 있으면 실제 소진으로 표시하지 않는다. 이전 묶음 끝과 남은 후보가 모두 같은 경우 다음 묶음이 0장이 될 수 있으며 별도 상태와 재진입 UX가 필요하다. B 기각: 교체·재배치로 해결되지 않을 때만 연속 제한을 완화해 최대 10장을 채운다. 탐색이 덜 끊기지만 기획의 최대 2장 보장에 예외가 생긴다. 공개·행동 이력·중복 제외는 어느 쪽도 완화하지 않는다. 후보 조회 예산 내 미발견을 전체 후보 없음으로 단정하지 않는다. 선택 후 응답 상태·배정 우선순위·탐색 예산을 확정한다.

답변 형식: G18-A / G19-A — 필요하면 이유 한 줄. 정책 답변은 전체 설계 승인과 별개이다.

설계 의사결정 질문 — 재시도와 수명

사용자 ‘권고대로’ 답변으로 G20-A·G21-A 확정. ID·순서 저장과 최신 공개 본문 조회, 생성 후 고정 24시간 만료를 적용한다. 구현 승인과는 별개이다.

G20 같은 묶음 재시도의 내용 — 해결, A
A 사용자 확정: ID·순서만 고정하고 본문은 현재 공개 콘텐츠를 읽는다. 철회·비공개·유효 상세 없는 항목은 제거하고 그 자리에는 새 카드를 보충하지 않는다. 순위 고정이지 응답 전체의 동일성 보장은 아니며 정정된 제목·요약이 보일 수 있다. B 기각: 제목·요약까지 묶음 생성 당시 스냅샷으로 저장한다. 재시도 표시가 안정적이지만 저장량·보존 정책 부담이 늘고 공개 중인 콘텐츠의 정정 반영이 늦다. B도 현재 공개 상태 검사와 철회 제외는 필수다. 두 안 모두 이미 전달된 클라이언트 사본을 회수한다고 주장하지 않는다. 선택 후 저장 필드·재조회 테스트를 확정한다.
G21 탐색 기록 수명 — 해결, A
A 사용자 확정: 생성 후 고정 24시간. 만료되면 새 탐색을 만들고 기존 요청을 조용히 새 탐색으로 바꾸지 않는다. B 기각: 마지막 사용부터 24시간으로 연장. 장시간 복귀에 유리하지만 활동하는 동안 기록이 계속 쌓이며 최장 수명·보관 상한이 추가로 필요하다. 24시간은 기획 원문이나 실측에서 도출한 값이 아니라 사용자가 채택한 초기 운영값이다. A는 수명·정리가 단순하나 하루 넘은 복귀 시 이전 재시도 복구를 보장하지 않는다. A도 24시간 내 데이터량 상한을 보장하지 않으므로 요청 제한·세션당 상한·정리량은 성능 검증 대상으로 남긴다. 새 탐색에서는 G3에 따라 미행동 카드가 다시 나올 수 있다. 선택 후 만료 오류·정리 작업을 구체화한다.

G19 배치 제한 상태는 후보 소진과 구별한다. 같은 빈 묶음의 무한 재시도로 해결된다고 가정하지 않는다. 신규 후보 재평가·새 탐색 안내를 포함한 응답 계약은 저장 설계에 통합할 후속 항목이다. 답변 형식: G20-A / G21-A — 필요하면 이유 한 줄.

설계 의사결정 질문 — 후보 조회 예산

사용자 G22-A 확정. 기획의 10장 배분·연속 제한·G9 보충을 수행하려면 10장보다 넓은 후보 풀이 필요하다. 기존 G1 규칙 기반 결정은 전체 후보를 얼마나 탐색할지까지 정한 것은 아니다.

G22 비교할 후보 범위 — 해결, A
A 사용자 확정: 유형별 우선순위로 제한된 후보를 조회하고 그 안에서 중복 없는 배정·연속 제한을 만족시킨다. 부족하면 정해진 예산 안에서 추가 조회한다. 응답 크기·애플리케이션 비교량을 제어할 수 있지만 풀 바깥의 더 좋은 후보를 놓칠 수 있다. B 기각: 전체 적격 이슈를 비교하여 후보 절단에 따른 누락을 피한다. 데이터가 작으면 단순하지만 누적 시 사용자별 평가·정렬 비용이 커질 수 있다. A도 SQL LIMIT만으로 DB 스캔·정렬 비용이 제한되는 것은 아니므로 인덱스·쿼리 실행계획·타임아웃 검증이 필요하다. 유형별 후보 수·추가 조회 횟수·SQL 시간·배정 탐색량은 아직 실측 전이며 구현 전 검증 가능한 초기 예산을 명시한다. 같은 요청·같은 스냅샷의 동률 기준은 결정적으로 유지한다.

A에서 탐색 예산을 다 쓴 상태는 후보 소진과 다르다. 응답 계약은 실제 소진, 배치 제약, 탐색 예산 도달, DB 실패를 구별해야 한다. 상한 밖 후보의 부재를 주장하지 않는다. 이 선택 후 조회·배정 알고리즘과 성능 검증 계약을 통합한다. 사용자 선택은 후보 제한 정책에 대한 결정이며 아직 수치 예산이나 전체 구현 승인은 아니다.

최초 생성 재시도는 새 탐색을 허용한다. 생성 요청 키·키 매핑 저장소는 이번 범위에서 구현하지 않는다. 최초 A 권고는 사용자 비용 검토 후 B로 수정했다. 응답 유실로 남는 탐색 기록은 고정 24시간 만료와 정리 대상이다. 만료 자체가 물리 삭제는 아니며 정리 작업이 필요하다. 새로운 탐색 사이에는 미행동 카드가 다시 선정될 수 있다는 G3 경계를 유지한다. 생성 자체는 행동 이벤트가 아니다.
유지할 중복 방지
같은 탐색의 서로 다른 묶음에는 동일 issue_id를 새로 배정하지 않는다. 같은 session/batch 재시도는 저장된 ID·순서를 재사용하며 새 묶음을 소비하지 않는다. 클라이언트는 같은 묶음 응답을 중복 append하지 않아야 한다. 재시도에 같은 카드가 포함되는 것은 복원이며 새로운 중복 배정이 아니다. 회원의 기존 행동 이슈 제외는 유지한다. 새 탐색·다중 탐색을 포괄하는 전역 미행동 카드 중복 방지는 추가하지 않는다.

검증: 동일 탐색 연속 묶음의 ID 교집합 없음, 동시 동일 묶음 요청의 동일 배정, 응답 유실 후 같은 묶음 복원, 프론트엔드 동일 묶음 중복 append 방지 계약. 남은 점수 제공 계약과 실행 예산은 검증 필요이며 확정값으로 위장하지 않는다. 이 결정은 전체 설계나 구현 승인이 아니다.
