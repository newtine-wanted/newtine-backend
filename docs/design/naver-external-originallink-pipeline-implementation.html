Naver originallink 외부 원문 파이프라인 구현 기록

목적
Naver 검색 메타데이터의 originallink 외부 언론사 원문을 실제 본문 근거로 사용해 LLM 콘텐츠를 생성·검증·공개한다.
사용자
NEWTINE 백엔드 개발자와 파이프라인 운영자
문제
기존 본문 provider가 naverUrl과 Naver host만 허용해 외부 publisher 원문을 SOURCE_UNAVAILABLE로 거부했다.
핵심 흐름
originallink 안전 fetch → 정적 HTML 본문 추출 → 기존 구조화 LLM 출력 → 독립 근거 검증 → PUBLISHED
승인 기준
외부 원문 기반 설계의 G1-A / G2-A / G3-A / G4-A 및 사용자 구현 승인 “ㄱㄱ”
변경안전 경계실행 검증게이트리뷰잔여 위험이해 점검

구현 변경

설계 baseline과 실제 반영
영역반영 내용
원문 선택NaverArticleBodyProvider가 naverUrl보다 sourceUrl(originallink 우선)을 사용한다.
URL fetchHTTP/HTTPS·기본 port만 허용하고 DNS의 모든 결과에서 private, loopback, link-local, multicast, reserved, documentation IP를 거부한다. 검증된 주소를 실제 socket destination에 고정하고 원래 hostname은 Host/SNI에만 사용한다. redirect는 hop마다 재검증하고 최대 3회로 제한하며 resolver timeout과 public address fallback을 적용한다.
본문 추출script/style/navigation 계열을 제거한 정적 HTML에서 중첩 article, 본문 class/id, main/section 후보 중 충분히 긴 텍스트를 선택한다. 200자 미만·JS-only·paywall·비HTML은 원문 불가로 처리한다.
LLM 계약기존 summary, viewpoints, glossary, AGE_GROUP impacts, articleIds를 유지하고 prompt를 1.2.0으로 강화했다. 숫자 효용성 점수나 새 DB/API 필드는 추가하지 않았다.
운영 로그구조/semantic validator의 안전한 실패 사유와 fetch article count만 남긴다. 원문 body, prompt, provider raw response는 로그·DB·usage·embedding에 남기지 않는다.

변경 파일: apps/batch/src/pipeline/naverNews.provider.ts, apps/batch/src/pipeline/pipeline.worker.ts, config/pipeline-ai.yml, 관련 provider/OpenAI 단위 테스트.

안전·실패 경계

originallink URL
  → scheme/userinfo/port 검사
  → DNS/IP public-address 검사
  → redirect마다 같은 검사
  → response content-type/2 MiB/timeout 검사
  → 정적 본문 ≥ 200자
  → LLM strict schema + articleIds
  → semantic PASS + 겹치지 않는 독립 근거 2개 이상
  → issue 저장·공개

검색 description은 본문 대체재가 아니다. 원문 확보 실패나 LLM 검증 실패는 해당 job만 실패시키며, 검증되지 않은 issue는 공개하지 않는다.

실제 실행 검증

Docker PostgreSQL에 실제 pipeline run을 넣고 새 batch image의 pipelineWorker를 실행했다. 첫 실행은 외부 원문 fetch 8건 성공 후 LLM 결과 검증에서 실패했다. validator 실패 사유를 운영 로그로 남기고 독립 근거 그룹 조건을 prompt에 명시한 뒤 CONTENT 재시도를 수행했다.

잔여 위험과 후속 범위

  • JS-only/paywall publisher는 정적 추출 baseline에서 의도적으로 실패한다. 실패율이 높으면 headless/browser 또는 extraction service를 별도 설계한다.
  • 원문을 저장하지 않으므로 retry 시 재수집한다. publisher 콘텐츠 변경과 fetch 비용은 운영 지표로 관찰해야 한다.
  • categoryCode는 승인된 G3-A 범위상 metadata 단계 분류를 유지한다. 본문 기반 category 재분류가 필요하면 별도 제품 계약으로 결정해야 한다.
  • 실제 live 재검증에서는 원문 fetch는 성공했지만 LLM semantic validation 2건이 실패했다. prompt/validator 재시도율과 publisher별 본문 품질을 운영 지표로 관찰한다.

구현 리뷰 (2026-09-17)

판정: 재검토 필요. 기능 경로와 live 결과는 확인됐지만, public internet URL을 적대적 입력으로 보는 G1-A 기준에서는 SSRF 방어와 재현 가능한 검증에 열린 항목이 있다. 아래 리뷰는 소스 구현을 수정하지 않은 read-only 판정이다.

발견 사항
ID / 심각도근거와 영향최소 후속 조치
SEC-001
P1 · 해결됨		DNS 결과를 검증한 뒤 resolved address를 http/https.request의 실제 destination으로 사용하고, hostname은 Host/SNI에만 사용하도록 수정했다. public address별 fallback도 추가했다.pinned options 회귀 테스트와 권한 환경 localhost socket fixture를 통과했다.
SEC-002
P1 · 해결됨		IPv6를 global-unicast 2000::/3로 제한하고 IETF 특수 대역·documentation·6to4를 차단했다. IPv4 AS112·benchmarking·documentation 대역도 보강했다.site-local·benchmarking negative test와 mixed DNS negative test를 통과했다.
OPS-003
P2 · 해결됨		DNS resolver 단계에 5초 timeout을 추가하고 ETIMEDOUT을 retryable UPSTREAM_ERROR로 변환했다.fake-timer timeout 회귀 테스트를 통과했다.
REQ-004
논의 필요		외부 본문은 content stage의 요약·viewpoints·glossary·AGE_GROUP impacts에 들어가지만, categoryCode는 candidate stage에서 Naver title/description metadata만 보고 생성된다. “본문으로 분류”가 요구사항이면 현재 구현은 그 범위를 충족하지 않는다.metadata 기반 categoryCode를 승인된 범위로 확정하거나, 본문 확보 뒤 category를 재분류하고 공개 전 검증하는 계약을 별도 승인한다.
VERIFY-005
P2 · 완화됨		resolver/transport seam과 deterministic tests를 추가했고 실제 live에서 FETCH 9건이 성공했다. 전체 DNS provider·실제 HTTPS 인증서 조합은 외부 환경 의존성으로 계속 남는다.publisher별 HTTPS 표본과 운영 실패율을 계속 관찰한다.
LOG-006
P2 · 해결됨		structure.reason를 로그에 넣기 전 control character 제거와 200자 상한을 적용했다.구조 검증 실패 로그가 원문 body/raw response를 포함하지 않는 기존 확인을 유지한다.
QUALITY-006
Non-blocking risk		본문 추출은 후보 중 가장 긴 텍스트를 선택한다. live에서 7개 publisher가 통과한 것은 긍정적이지만, 추천/관련기사까지 포함된 main/section이나 publisher별 markup 변형을 품질상 보장하지 않는다.주요 publisher fixture와 추출 품질 metric(본문 길이·실패율·boilerplate 비율)을 추가하고, 실패율이 높은 publisher는 별도 extractor 범위로 분리한다.

확인된 통과 항목: 기존 live run에서 3 jobs/3 issues가 PUBLISHED 되었고 7개 외부 source, 9개 AGE_GROUP impact, 2~3개 evidence가 확인됐다. 이번 hardening 후 live run에서도 FETCH 9건이 성공했다. unit 217건, integration 11건, typecheck/lint/build/Docker build도 통과했으며 원문 body·prompt·raw response의 로그/DB 보존도 확인하지 못했다. 남은 핵심 위험은 LLM semantic validation 변동성과 metadata 기반 category 범위다.
