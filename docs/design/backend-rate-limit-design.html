백엔드 공통 Rate Limit 설계

설계 기준선 · High-risk · 설계 승인됨 · 2026-09-17 KST

목적
외부 WAF·gateway 없이 API 서버 자체에서 공통 요청 빈도 제한을 적용한다.
사용자
백엔드 개발자와 운영 담당자
문제
현재 앱에 전역 limiter가 없어서 인증 전 endpoint와 공개 feed가 무제한으로 비용 큰 작업에 도달한다.
핵심 흐름
클라이언트 요청 → 조기 admission limiter → body parser·인증 → controller → 429 또는 정상 응답
범위 현재 근거 설계 결정 확정 설계 grilling 이해 점검 승인 상태

목표와 범위

목표
모든 HTTP 요청이 body parsing·인증·DB·도메인 처리에 들어가기 전에 공통 quota를 통과하도록 한다.
포함
public, auth, guest/member feed, user, admin route의 공통 admission 제한과 429 응답·Retry-After·관측성·회귀 검증.
별도 override
로그인·가입·refresh·guest feed처럼 abuse 비용이 큰 경로는 공통 limit보다 엄격한 제한을 둘 수 있다.
제외
Batch worker의 HTTP가 아닌 작업, 외부 WAF·gateway 구축, 제품별 최종 quota 수치의 근거 없는 확정.

현재 확인된 근거

  • apps/api/src/main.ts에는 request context와 body parser만 등록되어 있다.
  • apps/api/src/api.module.ts에는 전역 예외 필터만 있고 limiter guard/interceptor가 없다.
  • package.json과 Compose에는 rate-limit 저장소·공유 상태 구성이 없다.
  • POST /me/reports/:reportId/retry의 60초 cooldown은 서버 공통 요청 제한이 아니다.
  • /feed의 cursor 없는 요청은 feed session을 새로 생성하므로 guest abuse의 admission 제한이 중요하다.

설계 결정 기록

사용자 선택이 반영된 의사결정
ID결정확인된 사실·가정권고상태
G1 제한 상태 저장소와 배포 단위 현재 Compose는 API 1개와 PostgreSQL 1개다. API가 여러 인스턴스로 늘어나면 process-local quota는 합산되지 않는다. 사용자 선택 G1-A. Cloud Run 인스턴스마다 bounded in-memory limiter를 독립적으로 둔다. DB·Redis shared quota는 사용하지 않으며, scale-out 시 인스턴스 수만큼 유효 허용량이 늘어날 수 있고 재시작·scale-to-zero·revision 교체 시 quota는 초기화된다. 선택 완료 · G1-A
G2 식별자와 적용 계층 인증 전 요청은 userId를 알 수 없다. 직접 연결 기본값에서는 외부 proxy를 신뢰하지 않으며, 운영 토폴로지에 따라 trust proxy hop 수를 별도 검증해야 한다. 사용자 선택 G2-B. body parser보다 앞선 전역 IP limiter와 인증·계정·guest feed의 더 엄격한 endpoint override를 둔다. raw forwarded header는 직접 파싱하지 않고, RATE_LIMIT_TRUST_PROXY_HOPS=0 기본값에서 Express가 계산한 직접 peer IP만 사용한다. 선택 완료 · G2-B
G3 health 예외와 실패 정책 Compose healthcheck는 127.0.0.1/health를 호출한다. 실제 운영 health 공개 범위는 별도 확인이 필요하다. 사용자 선택 G3-A. /health는 전역 limiter에서 명시적으로 제외하고, 제한 초과는 application/problem+json과 Retry-After를 반환한다. 선택 완료 · G3-A

확정 설계

상태 저장
Cloud Run 인스턴스별 process-local bounded in-memory token bucket을 사용한다. DB·Redis에는 기록하지 않는다. key 수와 idle entry 수를 상한·TTL cleanup으로 제한하며, 인스턴스 수가 늘면 quota가 공유되지 않고 재시작·scale-to-zero·revision 교체 시 상태가 초기화된다는 운영 위험을 기록한다.
조기 전역 경계
main.ts에서 request context보다 앞서 또는 최소한 body parser보다 앞서 IP 기반 admission limiter를 실행한다. 초과 요청은 body parsing·인증·controller·DB에 진입하지 않는다.
보조 제한
전역 IP quota 위에 로그인·가입·refresh와 guest feed에 더 엄격한 endpoint/account 또는 guest-key 제한을 둔다. 인증 전 요청도 전역 IP quota로 먼저 보호하며, endpoint key는 trailing slash를 제거한 canonical path로 비교한다.
key 정책
Express가 계산한 request.ip를 사용한다. 기본 RATE_LIMIT_TRUST_PROXY_HOPS=0에서는 직접 peer IP이며, proxy hop 수를 운영 환경에서 명시한 경우에만 해당 trust 설정을 통해 proxy 경로의 원주소를 반영한다. raw X-Forwarded-For는 limiter가 직접 파싱·신뢰하지 않는다.
health
GET /health는 liveness probe를 위해 명시적으로 예외 처리한다. 나머지 HTTP operation은 공통 정책 또는 더 엄격한 override를 가져야 한다.
응답·관측
제한 시 429, RATE_LIMITED, application/problem+json, Retry-After를 일관되게 반환하고, 표준 RateLimit-* 헤더와 민감정보 없는 구조화 429 로그로 rule·route·key cardinality·eviction을 관찰한다. 별도 metrics collector는 현재 범위 밖이다.

불변 조건과 실패·복구

  • 제한된 요청은 JSON parsing, Argon2, JWT 조회, guest feed_sessions insert보다 먼저 종료한다.
  • 사용자 입력이나 raw forwarded header로 다른 client key를 임의로 선택할 수 없다. proxy 신뢰 hop 수는 명시적 운영 설정으로만 변경한다.
  • bounded map은 요청량에 따라 무한히 증가하지 않으며 idle key는 TTL cleanup 또는 eviction으로 제거한다.
  • 인스턴스별 in-memory 상태는 재시작·scale-to-zero·revision 교체 시 사라진다. 이는 장애 시 fail-open 정책이 아니라 선택된 Cloud Run per-instance 모델의 잔여 위험이다.
  • quota 수치와 endpoint override는 환경 설정으로 조정하되, 안전하지 않은 0·음수·비유한 값은 startup에서 거부하거나 안전한 기본값으로 정규화한다.

검증 계획

  1. unit: token bucket 경계, burst, refill, zero/negative/maximum 설정, key normalization, TTL cleanup.
  2. HTTP integration: /auth/login, /auth/signup, /feed, /issues/search burst에서 429가 parser·controller·DB보다 먼저 발생하는지 확인.
  3. HTTP contract: 429 ProblemDetails와 Retry-After, /health 예외, route override를 확인.
  4. 운영 smoke: 재시작·scale-to-zero 시 counter 초기화, scale-out 시 per-instance 동작, trailing slash endpoint override·account limit, 메모리 상한·429 metric·로그 sampling을 확인.
수평 확장·다중 리전에서 동일 quota가 필요해지는 순간 현재 per-instance 범위는 충분하지 않다. 그때도 DB·Redis 도입은 별도 요구사항·설계 승인으로 결정해야 하며, fail-open/fail-closed 정책도 함께 정한다.
