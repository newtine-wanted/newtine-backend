백엔드 보안 강화 설계

현재 보안 리뷰에서 확인된 로그인·회원가입 CSRF 경계, 원격 DB TLS 강제 여부, 분산 rate limit, 관리자 입력 배열 상한을 하나의 보안 강화 작업으로 조정하기 위한 설계 baseline이다. SQL Injection과 내부망 SSRF는 현재 직접 취약점이 확인되지 않았으므로 방어 불변식과 회귀 검증 대상으로 유지한다. 구현·migration·운영 설정 변경은 이 설계의 명시적 승인 전에는 시작하지 않는다.

목적
백엔드 브라우저·API 보안 경계의 출시 차단 이슈를 수정하기 위한 보안 강화 설계
사용자
NEWTINE 백엔드 개발자·운영 담당자·보안 정책 결정자
문제
로그인·회원가입의 CSRF 경계, 원격 DB TLS 강제, 분산 rate limit, 관리자 입력 상한과 외부 데이터 전송 정책을 보안 작업별로 분리·확정해야 함
핵심 흐름
요청 Origin·입력 검증 → 인증·세션 발급 → DB·외부 호출 경계 → 실패 차단·관측·복구

이전 문서인 초기 보안 리뷰는 정보 노출 중심의 별도 목적이므로 덮어쓰지 않는다. 설계 승인 후 연결된 구현 제어 문서 security-hardening-implementation.html을 생성한다.

목표·범위 확인된 근거 시스템 모델 의사결정 불변식 실패·복구 검증 Grilling 상태 Design-control 상태

1. 목표와 범위

목표

  • 브라우저 form 기반 cross-site 요청이 세션을 발급하거나 세션 상태를 변경하지 못하게 한다.
  • 운영 환경에서 DB 연결 암호화 정책이 설정 누락으로 조용히 비활성화되지 않게 한다.
  • 현재 process-local quota의 수평 확장 잔여 위험을 숨기지 않고 별도 이슈로 추적한다. 이번 작업에는 인프라 투자를 추가하지 않는다.
  • 관리자 입력과 비싼 조회 경로의 상한을 명시적으로 유지한다.
  • SQL Injection·SSRF·authz 방어 불변식을 회귀 테스트로 고정한다.

성공 신호

  • 허용되지 않은 Origin의 signup·login 요청은 세션 cookie 없이 거부된다.
  • 브라우저 same-origin 흐름은 테스트하고, 이번 release에서 non-browser login/signup은 지원하지 않음을 명시적으로 검증한다.
  • 운영·staging DB TLS 정책 위반은 기동 또는 연결 단계에서 fail-closed 된다.
  • 현재 인스턴스 내부 rate limit의 회귀와 residual risk 기록이 검증된다. 분산 quota는 이번 완료 기준으로 주장하지 않는다.
  • failedJobIds 및 사용자별 대량 조회가 고정된 상한을 넘지 않는다.

비목표

  • 현재 직접 취약점이 확인되지 않은 SQL query builder 전면 교체.
  • 현재 SSRF 방어 구현의 전면 재작성. 외부 egress allowlist는 별도 운영 정책으로 결정한다.
  • 프론트엔드 전체 보안 헤더·HTML sanitization 구현. 서버 계약과 필요한 전제만 정의한다.
  • OpenAI 데이터 처리 계약의 최종 법무 승인. 기술적 최소화·차단 지점만 기록한다.

2. 확인된 근거

현재 코드와 보안 리뷰에서 확인된 상태
영역 확인된 사실 설계상 영향
CSRF auth.controller.ts의 signup/login은 writeSession으로 cookie를 발급하지만 assertAllowedOrigin을 호출하지 않는다. JSON과 urlencoded body parser가 모두 켜져 있다. 브라우저 session issuance 정책을 먼저 확정해야 구현 범위와 client 호환성이 결정된다.
Cookie refresh cookie는 HttpOnly; SameSite=Lax이며 Secure는 production 기본값이다. Origin helper는 header 부재를 허용한다. Origin 강제와 SameSite 정책을 browser cookie 계약으로 고정하고, 향후 non-browser 계약은 별도 설계로 분리한다.
DB transport database.options.ts에 PostgreSQL SSL/TLS 옵션이 없다. Compose DB는 private network지만 원격 DB는 배포 조건에 따라 달라진다. 앱이 fail-closed 할지, 인프라가 보장할지 소유권 결정을 해야 한다.
Rate limit 현재 store는 process-local memory이며 README도 인스턴스별 best-effort quota로 설명한다. shared store, gateway, 또는 현재 정책 유지 중 운영 목표를 결정해야 한다.
입력 상한 일반 API는 Typia·도메인 재검증이 양호하지만 pipelineRun.input.ts의 failedJobIds에는 MaxItems가 없다. 관리자 endpoint라도 request·DB·메모리 상한을 계약에 명시한다.
SQLi / SSRF SQL 값은 parameter binding이고, 기사 fetch는 DNS public-IP 검사·IP pinning·redirect 재검증·timeout/body limit을 적용한다. 구현 변경보다 회귀 테스트와 egress 정책의 잔여 위험 기록이 우선이다.

최종 결정 반영

  • G1-A 확정: cookie 발급·회전 경계는 strict Origin allowlist를 사용하고 Origin 부재는 허용하지 않는다.
  • G2-A 확정: 브라우저는 same-origin cookie 세션만 사용한다. non-browser client는 이번 release에서 지원하지 않으며, 향후 별도 Bearer/OAuth 계약으로 분리한다.
  • G2.1-C 확정: 현재 구현에는 non-browser login/signup endpoint를 추가하지 않는다.
  • G3-A 확정: 애플리케이션이 운영·staging TLS 정책을 강제하며 인프라가 이중 검증한다.
  • G3.1-A 확정: 운영은 verify-full + 명시적 CA, 개발·test만 disable을 허용한다.
  • G4-C 확정: shared rate limit은 이번 범위에서 도입하지 않고 process-local 잔여 위험을 별도 이슈로 남긴다.
  • G5-B 확정: AI data egress는 별도 privacy/compliance 이슈로 분리한다.

의존 관계

G1 CSRF 방식 ──→ G2 브라우저/non-browser 계약 ──→ auth controller·cookie·integration test 범위

G5 data egress ──→ 별도 privacy/compliance issue

5. 유지해야 할 보안 불변식

  1. 허용되지 않은 cross-site 요청은 access/refresh session을 발급하거나 회전시키지 않는다.
  2. 이번 범위에서는 Origin 부재 요청을 cookie session endpoint에 허용하지 않는다. 향후 Bearer client는 별도 인증 계약과 endpoint로 설계한다.
  3. 사용자 입력은 SQL 문자열·식별자·URL 요청 옵션에 직접 삽입하지 않고, parameter 또는 고정 allowlist로만 전달한다.
  4. 외부 URL은 scheme/port/userinfo/DNS/public IP/redirect를 매 hop 검증하고 resolve된 주소에 pinning한다.
  5. DB 연결 보안 설정이 운영 환경에서 누락되면 연결을 허용하지 않는다.
  6. 이번 범위에서는 rate limit 저장소를 변경하지 않으며, process-local best-effort quota와 수평 확장 우회 위험을 운영 문서에 명시한다.
  7. 사용자·관리자 resource 조회는 principal/role 및 owner predicate를 거친다.
  8. token, password, cookie, authorization header, 원문 request body는 응답·로그·외부 provider payload에 불필요하게 남기지 않는다.

Origin 불일치/부재 cookie 발급·회전·삭제를 수행하지 않고 403 request id, endpoint, decision reason만 기록. credential은 기록하지 않음.

수평 확장 rate limit 이번 범위에서는 shared store를 추가하지 않고 현재 process-local best-effort 정책을 유지한다. 인스턴스 수에 따른 quota 증가를 residual risk로 기록하고, shared quota 도입은 별도 이슈에서 운영 비용과 함께 결정한다.

7. 검증 계획과 완료 기준

설계 승인 후 실행할 검증
축 검증 완료 기준
CSRF same-origin, 허용 cross-origin, 금지 cross-origin, Origin 부재 form/API 요청을 controller/integration test로 실행 금지 요청과 현재 지원하지 않는 non-browser 요청은 403이고 Set-Cookie 없음. browser same-origin만 세션 발급.
TLS/config 개발·test·staging·production config matrix와 실제 PostgreSQL handshake 확인 운영 mode에서 TLS 검증 실패가 fail-closed이고, 개발 예외가 운영에 전파되지 않음.
rate limit 현재 process-local quota, eviction, proxy IP 정책과 수평 확장 residual risk 기록을 검증 이번 범위에서 shared quota를 주장하지 않고, 기존 in-process 동작의 회귀가 없음.
입력·SQLi unknown field, oversized array, malformed UUID, LIKE metacharacter, array binding regression test 400/413으로 종료되며 SQL 문자열 변경이나 예외 detail leak 없음.
SSRF private IPv4/IPv6, DNS mixed answers, rebinding-shaped redirect, HTTP downgrade, oversized body/timeout private 대상은 요청 전에 차단되고 public redirect만 bounded hop 내에서 허용.
회귀 npm run typecheck, npm run lint, 관련 auth/rate-limit/naver/provider unit test, 필요한 integration/smoke 기존 인증·refresh rotation·owner scoping·AI output validation 회귀 없음.

설계 시점의 기존 증거: 관련 단위 테스트 9개 suite/71개 통과, typecheck/lint 통과. 이는 새 설계 구현의 검증 결과가 아니며, 구현 후에는 연결된 implementation-control 문서에 fresh evidence를 기록한다.
