로컬 Docker·Compose 실행 환경 설계

NEWTINE 백엔드를 새 개발 환경에서 같은 순서로 띄우고, PostgreSQL 연결 상태와 데이터를 예측 가능하게 관리하기 위한 설계 기준선이다. 현재 문서는 구현 명세가 아니라 선택이 필요한 설계와 검증 기준을 기록한다.

purpose · 목적
로컬에서 NEWTINE NestJS API·batch와 PostgreSQL을 반복 실행할 수 있는 Docker 환경 확립
audience · 사용자
로컬 개발을 시작하거나 재현하는 백엔드 개발자

호스트 Node 실행과 컨테이너 PostgreSQL 사이의 실행 순서·호스트명·데이터 보존·환경변수 계약이 정의되지 않음
core-flow · 핵심 흐름
Docker Compose로 PostgreSQL 기동 → readiness 확인 → API 또는 batch 실행 → 로그·DB 상태 확인 → 명시적 종료·초기화

기존 NestJS 초기 골격 설계는 앱·core 코드 경계를, 견고성 설계는 설정 실패를 다룬다. 이 문서는 컨테이너와 로컬 실행 토폴로지를 다루므로 목적이 달라 새 peer 설계로 기록한다. 구현 승인 후에는 local-docker-environment-implementation.html을 이 문서와 연결한다.

이 문서는 구현·review 결과를 덧씌우지 않는 승인 기준선이다. 구현 및 최종 검증 상태와 갱신일은 연결된 구현-control 문서에서 관리하며, 이 문서의 2026-09-13은 설계 선택·승인 기준일이다.

목표와 확인된 근거

성공 신호는 로컬 개발자가 명시된 한두 개의 Compose·npm 명령으로 PostgreSQL을 준비하고, 기존 API의 /health 및 batch의 databaseCheck로 연결을 확인하며, 재시작 후에도 의도한 로컬 데이터 상태를 설명할 수 있는 것이다. 운영 배포나 외부 서비스 연동을 이 문서의 성공으로 간주하지 않는다.

저장소와 현재 환경에서 확인한 사실
영역 확인된 사실 설계에 미치는 영향
앱 apps/api와 apps/batch가 libs/core의 MikroORM/PostgreSQL 경계를 공유한다. API와 batch가 같은 DB 접속 변수·네트워크 규칙을 사용해야 한다.
DB 설정 createDatabaseOptions가 DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD를 읽는다. development/test에만 기본값이 있고 ensureDatabase=false이며 schema sync·자동 migration은 없다. Compose가 DB를 준비해도 앱이 schema를 자동 변경한다고 약속할 수 없다. 컨테이너 내부와 호스트 실행의 DB host 값은 실행 위치에 따라 달라진다.
실행 npm run start:dev:api는 ttsx 기반 개발 실행이며 현재 script에 watch 옵션은 없다. npm run start:api는 빌드 산출물 실행, npm run start:batch -- databaseCheck는 일회성 DB 확인이다. 개발 편의와 production-like 컨테이너 실행은 서로 다른 흐름으로 명시할 수 있다.
환경 로드 애플리케이션은 .env를 자동으로 읽지 않는다. Node의 --env-file 또는 셸 주입이 필요하다. Compose의 env_file와 호스트 npm 실행의 env-file은 별도 계약으로 설명해야 한다.
컨테이너 런타임 API는 API_HOST 기본값이 127.0.0.1이고, 개발 로그 pretty 출력은 pino-pretty devDependency에 의존한다. 컨테이너 API는 publish된 포트를 받도록 API_HOST=0.0.0.0을 명시하고, production dependency만 포함하는 runtime image라면 NODE_ENV=production을 사용한다.
상태 경계 /health는 DB 쿼리를 하지 않는 프로세스 확인 endpoint이고, batch databaseCheck는 실제 select 1을 실행한다. Compose DB healthcheck, API liveness, batch 연결 확인을 서로 다른 검증으로 유지한다.
현재 설정 Dockerfile·Compose·.dockerignore·전용 Docker script는 없다. 확인 환경은 Node v24.18.0, npm 11.16.0, Docker 27.5.0, Compose v5.0.1이다. 기존 파일을 덮어쓸 기준선이 없으므로 새 목적 문서와 새 실행 파일을 설계한다.

변경 모델과 제외 범위

최종 구현 후보는 Compose project 안에 PostgreSQL 서비스와 필요 시 API·batch 실행 경계를 정의하고, 실행 위치에 맞는 DB host와 readiness 확인 절차를 제공하는 것이다. 명령어와 파일 이름은 토폴로지 결정 후 확정한다.

제외

  • 운영·staging 배포, 이미지 registry, TLS, secret manager, Kubernetes, CI 배포 파이프라인
  • 업무 entity·repository·migration·seed 및 데이터 모델 변경
  • 애플리케이션의 /health 계약을 DB readiness endpoint로 바꾸는 코드 변경
  • 현재 사용하지 않는 임베딩 모델·차원·추천 정책을 확정하는 일

후보 시스템 모델

유지해야 할 불변식과 경계

설계 전 과정에서 유지하는 계약
ID 불변식 검증 또는 관찰
D-INV-01 PostgreSQL readiness와 앱 실행 가능성을 같은 상태로 취급하지 않는다. DB가 healthy여도 앱 bootstrap·schema·업무 기능은 별도 검증 대상이다. pg_isready, API /health, batch databaseCheck 결과를 구분해 기록한다.
D-INV-02 Compose는 DB를 생성·기동할 뿐 schema sync, 자동 migration, 업무 seed를 암묵적으로 실행하지 않는다. PostgreSQL 시작 로그와 앱 설정(ensureDatabase=false)을 확인하고, init SQL을 넣지 않는다.
D-INV-03 컨테이너 내부 DB host와 호스트 프로세스의 DB host는 실행 위치에 맞게 명시한다. db를 호스트에서 해석된다고 가정하지 않는다. 각 실행 모드의 환경변수 표와 실제 databaseCheck 연결 성공으로 확인한다.
D-INV-04 개발 비밀번호는 로컬 전용 예시로만 두고 .env와 실제 비밀값은 git에 포함하지 않는다. .gitignore, .env.example, Compose env 전달 경로를 확인한다.
D-INV-05 볼륨 삭제는 기본 종료 동작이 아니며, 데이터 초기화는 사용자가 대상을 인지하는 별도 절차다. 정상 재기동과 명시적 초기화 검증을 분리한다. destructive command는 문서에 경고를 둔다.
D-INV-06 API 컨테이너의 정상 종료·DB 연결 실패·batch one-shot 실패가 조용히 성공으로 변환되지 않는다. non-zero exit, Compose 상태, 로그, 재실행 후 상태를 확인한다.

결정 트리와 현재 권고

  1. 실행 토폴로지를 결정한다.
  2. 토폴로지에 맞춰 환경변수 전달과 DB host를 결정한다.
  3. 그 결과에 따라 API image, hot reload, batch one-shot 및 profile 필요성을 정한다.
  4. DB image·pgvector 여부와 volume 보존·초기화 정책을 확정한다.
  5. readiness, 연결 확인, API smoke, build/lint/test의 검증 명령을 확정한다.

선택된 설계 기준선

사용자가 말한 “실행이 한번에 되는 구조”와 최신 G1-A 답변을 반영해 후보 B를 선택된 기준선으로 좁힌다. docker compose up --build 한 번으로 DB와 API를 계속 실행하고, batch는 같은 Compose 프로젝트에서 명시적으로 한 번 실행하는 one-shot 도구로 둔다. batch를 상시 up에 포함하지 않는 이유는 현재 작업이 종료 프로세스라 API 재시작 때 자동 반복되거나, 완료된 batch가 Compose의 정상 실행 흐름을 바꿀 수 있기 때문이다.

필요하면 docker compose up -d db와 기존 npm 실행을 병행하는 호스트 개발 경로도 보존할 수 있다. 다만 그것은 선택된 container mode와 별도의 실행 계약으로 문서화하며, 컨테이너 개발용 watch는 현재 script에 없으므로 이 설계에서 약속하지 않는다.

보류된 branch

실패·복구 모델(결정 전 기준)

예상 실패와 안전한 다음 행동
상황 관찰해야 할 사실 복구 방향 자동으로 하지 않을 것
DB가 아직 준비되지 않음 Compose health 상태, pg_isready 출력, 앱 bootstrap 로그 readiness가 healthy가 된 뒤 API/batch를 재실행한다. 앱 retry가 있다고 가정하거나 schema 변경을 시작하지 않는다.
앱이 db를 찾지 못함 앱 실행 위치와 실제 DB_HOST의 불일치 host mode면 127.0.0.1, container mode면 Compose service name을 사용한다. DNS 실패를 PostgreSQL 데이터 손상으로 해석하지 않는다.
기존 volume의 schema가 기대와 다름 DB 연결은 성공하지만 업무 쿼리·migration 전제는 별도 실패할 수 있다. 현재 범위에서는 schema migration/seed를 별도 작업으로 열고 원인을 기록한다. Compose up이나 container start에서 volume을 자동 삭제하지 않는다.
batch databaseCheck 실패 batch exit code 1과 batch.failed 로그 DB health·env·로그를 확인한 뒤 같은 one-shot job을 명시적으로 재실행한다. 실패를 성공으로 감싸거나 무한 재시도하지 않는다.
데이터를 초기화해야 함 reset 대상 volume과 로컬 데이터의 보존 필요성 대상을 표시한 별도 reset 절차 후 다시 up·readiness·연결 검증을 한다. 일반 down에 -v를 숨겨 넣지 않는다.

검증 계획(토폴로지 결정 후 명령 확정)

  1. 빈 로컬 환경에서 Compose config가 해석되고 DB container가 생성된다.
  2. DB healthcheck가 healthy가 된 뒤 psql 또는 databaseCheck가 연결에 성공한다.
  3. 선택한 API 실행 모드가 /health 200과 기존 smoke 계약을 통과한다.
  4. API/batch bootstrap 실패 시 non-zero exit와 기존 구조화 로그·예외 계약이 유지된다.
  5. 정상 종료 후 volume 보존 정책이 실제로 유지되고, reset 절차만 데이터를 삭제한다.
  6. 변경 범위에 비례해 npm run format:check, npm run lint, npm run typecheck, npm test, npm run build와 focused Docker smoke를 실행한다.
Docker daemon 접근과 실제 PostgreSQL 기동은 설계 확정 후 별도 실행 검증이다. 현재 문서에 Docker CLI 버전이 기록되어 있다는 사실을 실제 container 성공의 증거로 해석하지 않는다.

현재 단계에서 배제하거나 보류하는 대안

대안과 배제 이유
대안 현재 판단 다시 열 조건
PostgreSQL latest tag 보류·비권고. 재현성이 없어 local gate 결과가 달라질 수 있다. 버전 갱신 정책과 호환성 검증을 별도 운영 계약으로 정할 때
Compose 시작 시 자동 schema sync/migration 배제. 현재 저장소의 자동 schema 변경 금지와 충돌한다. migration 도구·락·실패 복구·rollback을 별도 승인한 뒤
호스트와 컨테이너에서 같은 .env를 무조건 재사용 비권고. DB_HOST의 의미가 실행 위치에 따라 바뀐다. Compose interpolation과 앱 env override를 명시적으로 검증해 혼동을 제거한 경우
컨테이너 내부에서 무제한 npm install 비권고. lockfile 재현성과 startup 시간이 나빠진다. 개발 전용 bind mount 전략과 캐시를 별도 설계할 때
지금 바로 pgvector를 활성화 현재는 보류 권고. 코드·차원·migration이 없어 image 복잡성만 늘어난다. 임베딩 차원·extension migration·실제 query가 확정될 때

공유 이해 확인 · 확인됨

아래 내용은 G1~G6의 선택을 하나의 실행 계약으로 합친 요약이다. 사용자가 “ㅇㅇ”으로 공유 이해를 확인했고, 이후 “구현 ㄱㄱ”으로 이 기준선의 구현을 승인했다. 이 문서는 승인된 설계 baseline이며 as-built 사실은 구현 제어 문서에 기록한다.

공유할 실행 계약
항목 확정 내용 의도적으로 하지 않는 것
서비스 Compose의 기본 서비스는 db와 api다. batch는 one-shot 도구다. batch를 API 재시작마다 자동 실행하거나 상시 scheduler로 만들지 않는다.
DB postgres:18 local baseline, pgvector 후도입, named volume 보존 latest, 자동 schema sync, migration, seed, init SQL
앱 image Node 24 기반 multi-stage built runtime, production dependencies, non-root 실행 검증되지 않은 source bind mount와 watch 동작
연결·노출 container는 DB_HOST=db·API_HOST=0.0.0.0, host는 DB_HOST=127.0.0.1; publish는 loopback host/container에서 같은 DB_HOST를 무조건 재사용하거나 외부 공개하지 않는다.
상태 확인 DB healthcheck, API /health, batch select 1를 별도 검증 API /health가 DB readiness까지 보장한다고 약속하지 않는다.
남은 가정
운영·CI PostgreSQL major는 아직 저장소에서 확인되지 않았다. 운영 기준이 발견되면 postgres:18 local baseline과 호환성을 다시 검토한다.
후속 범위
업무 entity가 생기면 migration·seed·schema 검증을 별도 설계한다. 임베딩을 실제 저장하면 pgvector image·extension·차원·migration을 별도 설계한다.
잔여 위험
DB healthcheck는 애플리케이션 자격증명·업무 쿼리 성공을 보장하지 않는다. 기존 volume은 초기화 환경변수 변경을 재적용하지 않으며, major 변경은 단순 tag 교체로 처리하지 않는다.
