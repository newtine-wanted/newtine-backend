PR #3 issue-card-query·회원 feed 인증 통합

설계 기준 문서 · 설계 승인됨 · 회원 feed 전환 구현 완료

목적
PR #3의 issue detail·personalized feed 기능을 최신 main의 pipeline/onboarding과 함께 유지한다.
사용자
PR을 통합·검증하는 백엔드 개발자.
문제
origin/main=1215526에는 PR #5의 JWT 인증·principal 경계가 들어왔지만, PR 브랜치 a43bfc0의 issue/feed는 raw x-user-id와 guest session credential을 사용한다.
핵심 흐름
최신 main 인증 기준 확인 → merge → feed 회원 전용 정책 확정 → 검증된 principal 연결·raw x-user-id와 guest key 제거 → migration·계약·테스트·게이트 검증.
강도
High-risk: 인증·인가, 개인화 데이터 소유권, API·DB 계약과 기존 PR 통합을 함께 다룬다.
변경 관리
기존 최신 main merge·migration 통합 범위와 공개 issue 상세 계약은 보존하고, feed 회원 전용 전환·principal 연결·DB guest schema 제거를 이번 구현 승인 범위로 기록한다.

목표와 불변식

  • PR 브랜치의 issue detail/feed API, repository port, 테스트와 문서를 삭제하지 않는다.
  • 최신 main의 onboarding·pipeline API, 상태 머신, provider·migration을 유지한다.
  • feed 테이블 SQL은 Migration202609130003IssueCardQuery의 addSql()로 옮기고 down()은 데이터 삭제를 막기 위해 명시적으로 중단한다.
  • generated/ 산출물은 controller/source 통합 후 npm run contracts:all로 재생성한다. 생성 파일을 손으로 합치지 않는다.
  • origin/main의 PR #5 인증 구현(AuthPrincipal, JwtAuthGuard, CurrentUser, DB current-role 조회)을 인증 기준선으로 재사용하고 JWT·refresh 정책은 변경하지 않는다.
  • 현재 issue/feed의 raw x-user-id를 신뢰하지 않고, 회원 사용자 ID는 검증된 principal에서만 얻는다.
  • /feed-sessions*는 회원 JWT 필수로 전환한다. x-feed-guest-key, guest session 발급·검증·저장 schema는 production code·계약·migration에서 제거한다.
  • 공개 issue 상세는 기존 계약을 유지하되, 선택적으로 제시된 Bearer만 검증해 principal을 사용한다. pipeline 접근 정책은 ADMIN으로 보호한다.

인증 principal 통합 · 회원 feed 전환

최신 origin/main의 PR #5는 이미 service access JWT를 검증하고 AuthPrincipal { userId, role }를 request에 주입한다. 따라서 이 작업은 새 JWT·refresh 구현이 아니라, issue/feed consumer를 그 기준선에 연결하는 통합이다. 현재 PR 브랜치의 @Headers('x-user-id'), x-feed-guest-key와 이전 authenticatedUserId seam은 신뢰 경계에서 제거한다.

현재 route별 목표 정책 초안
경로정책사용자 식별 경계실패·소유 증명
/health, /auth/*, /onboarding/options, /onboarding/entities, /issues/search PUBLIC principal을 사용하지 않음 기존 공개 route 계약 유지
/me/onboarding* REQUIRED USER 기존 main의 JwtAuthGuard + CurrentUser().userId 토큰 없음·무효는 401
GET /issues/:issueId PUBLIC + optional principal Bearer가 있으면 principal의 userId로만 개인 영향 계산 헤더 없음은 익명, 잘못된 Bearer는 401
POST /feed-sessions
POST /feed-sessions/:sessionId/batches		 REQUIRED USER guard가 주입한 principal의 userId만 사용 토큰 없음·무효는 401; 다른 회원의 session은 기존 404 경계 유지
/pipeline/runs* ADMIN main의 JwtAuthGuard + Roles(AuthRole.Admin) 토큰 없음·무효는 401, USER role은 403
중요: “optional”은 공개 issue 상세에만 적용한다. 두 번째 인증 체계를 만들지 않고 기존 JwtAuthGuard의 명시적 route policy metadata로 헤더 부재만 허용한다. feed session은 회원 JWT 필수이며 guest key라는 별도 credential을 두지 않는다.

공유 이해 확인

기존 승인 범위는 PR 브랜치에 최신 origin/main을 merge해 pipeline/onboarding과 issue-card-query를 함께 유지하는 것이다. 이번 승인 delta는 main의 PR #5 인증을 기준선으로 삼아 issue/feed의 raw x-user-id를 제거하고, feed session을 회원 JWT 필수로 전환하는 것이다.

결정 반영: strict 회원 route는 main의 JwtAuthGuard + CurrentUser를 그대로 사용한다. 공개 issue 상세만 같은 guard의 명시적 optional policy에서 헤더 부재를 허용하며, 존재하는 Bearer는 반드시 검증한다. feed session에는 principal userId만 사용하고 guest key·guest 저장 schema는 제거한다. pipeline run·retry·interrupt는 ADMIN principal을 요구한다.

잔여 가정: main의 service JWT(sub=UUIDv7, issuer/audience 검증)를 API access token 계약으로 재사용한다. 실제 production DB·role seed·pipeline network ACL은 구현 전 확인한다.
