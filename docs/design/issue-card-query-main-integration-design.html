설계 기준 문서 · 설계 승인됨 / 구현 진행 중

목적
PR #3의 issue detail·personalized feed 기능을 최신 main의 pipeline/onboarding과 함께 유지한다.
사용자
PR을 통합·검증하는 백엔드 개발자.
문제
origin/main=d4db486가 PR 브랜치의 기준 4634e1c보다 전진했고, 공통 예외·생성 계약·core export·migration 경계에서 충돌한다.
핵심 흐름
최신 main 확인 → merge → 두 기능의 등록·export·계약 합집합 → feed schema를 ordered MikroORM migration으로 등록 → 생성 계약·테스트·게이트 검증.
강도
Standard: API·DB migration·생성 계약 경계를 함께 다루지만, 기존 승인 기능의 의미와 공개 endpoint는 변경하지 않는다.

목표와 불변식

  • PR 브랜치의 issue detail/feed API, repository port, 테스트와 문서를 삭제하지 않는다.
  • 최신 main의 onboarding·pipeline API, 상태 머신, provider·migration을 유지한다.
  • feed 테이블 SQL은 Migration202609130003IssueCardQuery의 addSql()로 옮기고 down()은 데이터 삭제를 막기 위해 명시적으로 중단한다.
  • generated/ 산출물은 controller/source 통합 후 npm run contracts:all로 재생성한다. 생성 파일을 손으로 합치지 않는다.
  • 충돌 해소 목적을 넘어 인증 principal, 추천 정책, pipeline 상태, 공개 API 의미를 새로 설계하지 않는다.

공유 이해 확인

이 설계는 PR 브랜치에 최신 origin/main을 merge해 기존 이력을 보존하고, pipeline/onboarding과 issue-card-query의 등록·export·공개 계약을 모두 남긴다는 뜻이다. feed SQL은 Migration202609130003IssueCardQuery로 옮겨 onboarding → pipeline → embedding-task → issue-card-query 순서의 MikroORM migration history에 등록한다. 생성 SDK·e2e·OpenAPI는 source 통합 뒤 재생성하며, API 의미·추천 규칙·pipeline 상태 머신은 변경하지 않는다.

잔여 가정: 실제 PostgreSQL 왕복과 migration up/down은 로컬 환경에서 가능한 범위만 검증하고, 연결되지 않는 운영 검증은 잔여 위험으로 기록한다.
