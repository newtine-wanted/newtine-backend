운영 DB 수동 SQL 적용 구현 제어

승인된 설계 기준에 따라 빈 production PostgreSQL에 운영자가 직접 실행할 SQL 산출물과 검증 절차를 만든다. 이 작업은 production DB에 접속하거나 SQL을 실행하지 않는다.

기준선
운영 DB 스키마·기준 시드 배포 설계 · 설계 승인됨 · 승인 범위는 빈 DB baseline, 정적 reference seed, 수동 실행 문서다.
현재 구현 상태
임시 빈 PostgreSQL에서 DDL·seed·verify를 실제 순서로 적용해 성공했다.
구현 제어 상태
운영 제어 보류 · 기술 산출물은 완료됐고, production DB 적용은 운영 담당자의 직접 실행과 검증 결과를 기다린다.
운영 이해 점검
미실시. 아래 구현 이해 점검에서 실제 운영 순서·실패 대응을 확인할 수 있다.

승인된 실행 계약

  1. deploy/db/production/001_schema.sql을 빈 DB에 직접 실행한다.
  2. deploy/db/production/002_seed.sql을 실행한다.
  3. 같은 문서에 기록된 사전·사후 검증 쿼리를 실행한다.
  4. 모든 검증이 성공한 뒤 API와 worker를 배포한다.

애플리케이션 startup, Docker Compose init, npm run db:migrate는 production 적용 경로에 포함하지 않는다.

검증 근거

PGPASSWORD=local_only psql -h 127.0.0.1 -p 55439 -U postgres -d newtine_verify -v ON_ERROR_STOP=1 -f deploy/db/production/001_schema.sql
PGPASSWORD=local_only psql -h 127.0.0.1 -p 55439 -U postgres -d newtine_verify -v ON_ERROR_STOP=1 -f deploy/db/production/002_seed.sql
PGPASSWORD=local_only psql -h 127.0.0.1 -p 55439 -U postgres -d newtine_verify -v ON_ERROR_STOP=1 -f deploy/db/production/003_verify.sql
  • 세 명령 모두 ON_ERROR_STOP=1로 성공했다.
  • 검증 결과: issue_categories=10, regions=17.
  • seed를 한 번 더 실행한 뒤에도 row count는 10|17로 유지됐다.
  • production DB에는 접속하지 않았다.

검증 공백과 잔여 위험

  • production DB 자체에는 접속하지 않으므로 실제 운영 적용 성공은 검증하지 않는다.
  • 운영 DB가 빈 DB라는 전제 밖의 delta·데이터 보존은 이번 산출물 범위가 아니다.
  • SQL 적용 후 운영 담당자가 검증 쿼리 결과를 확인해야 API 롤아웃이 안전하다.
  • 운영 담당자의 실제 적용 결과가 아직 보고되지 않았으므로 운영 제어 상태는 보류다.
