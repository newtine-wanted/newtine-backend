온보딩 API

기획 코멘트의 결정을 보존하고, ERD와 충돌하는 계약부터 확정한다. G1~G10 의사결정을 반영했고 사용자의 “구현 ㄱㄱ”으로 이 기준선을 승인했다.

목적
회원 온보딩 API의 수집·저장·완료 계약 확정
사용자
NEWTINE 백엔드 개발자와 기획 결정자
문제

회원 식별 → 선택지 조회 → 관심 주제·대상·나이·지역 입력 → 완료 또는 건너뛰기 → 선호 저장

목표와 성공 기준

회원이 선택지를 조회하고 설문을 완료하거나 건너뛸 수 있다. 저장된 상태는 재접속 시 일관되며, 같은 요청이 재전송되어도 초기 선호 가중치가 중복 적용되지 않는다. API 형식과 영속 모델은 아래 미확정 결정을 해소한 뒤 고정한다.

범위 경계

소셜 로그인·카카오 연동·토큰 발급은 사용자의 명시적 제외 범위다. 비회원 서버 계정 생성도 하지 않는다. 피드 추천 계산, 행동 학습, 진단 보고서, 위치 권한 요청은 이번 온보딩 API의 구현 범위로 자동 포함하지 않는다. 인증된 회원 식별을 전달받는 경계는 필요하다.

직접 확인한 근거

ERD v1.3는 커넥터 404 후 로그인된 브라우저로 읽었다. 피그마 온보딩 페이지의 코멘트 #1과 답글, 화면 및 스펙 노트를 직접 확인했다. 해결된 코멘트 표시를 켠 목록에서도 온보딩 관련 스레드는 #1이었다.

현재 코드와 제안 구조

현재 저장소는 NestJS/Nestia/Typia/MikroORM 골격이다. 업무 사용자·인증·선호 구현이 준비되었다고 가정하지 않는다. 아래는 승인된 구현 경계의 구조 기준선이다.

저장 모델 초안

users, issue_categories, entities, user_category_preferences, user_entity_preferences를 기능 단위로 구현하는 방향이다. 지역은 regions(code PK, name)와 user_region_preferences(id UUID PK, user_id FK, region_code FK, weight numeric)로 제안한다. 사용자·지역 복합 UNIQUE를 적용하고 최초 선택마다 +1을 반영한다(G9-B). 지역 추천 계산은 별도 계약으로 남긴다. 나이대에는 생년월일·정확한 나이를 추가하지 않는다.

선호 weight에 초기 선택과 행동 학습이 합쳐질 수 있으므로, 재설문 시 기존 행을 지우거나 모두 2로 덮어쓰는 설계는 사용할 수 없다. 재편집을 허용하면 초기 선택과 학습 기여를 분리할지 추가 결정이 필요하다.

불변식 제안

  • 요청 body/path의 userId를 회원 인증 증거로 신뢰하지 않는다.
  • 완료 상태·완료 시각·나이·선호 저장은 선택한 제출 계약 안에서 원자적으로 반영한다.
  • 같은 제출 재전송·동시 완료가 초기 가중치를 두 번 더하지 않는다.
  • 선택하지 않은 값, 존재하지 않는 코드, 비활성 대상의 허용 여부를 서버에서 명시적으로 검증한다.
  • 사용자별 대상 선호 중복을 복합 UNIQUE로 막는다. 유일성 제약만으로 +2 중복 가산이 방지되는 것은 아니다.
  • 나이 미수집은 NULL, 지역 전국 선택은 빈 집합으로 구분한다. 나이로 거주·취업·정치 성향을 추론하지 않는다.

핵심 위험

재전송·재설문·학습된 선호가 같은 weight에 합쳐지면 선택 이력을 복원하거나 초기 가중치를 안전하게 다시 적용하기 어렵다. 최초 온보딩은 한 번만 반영하고 재요청은 기존 상태를 반환한다(G8-A). 추후 수정 기능은 별도 API로 제공할 예정이며, 구현 전에 초기 선택과 학습 점수의 분리·이행을 설계한다. 이번 결정이 기존 선택 원본의 완전 복원까지 보장하는 것은 아니다.

코드 근거: 로컬 ERD v1.2는 최신 Notion과 달리 category_id 및 나이·지역 없는 users 모델이다. ORM 설정은 entities가 비어 있고 package.json에는 migration 도구가 없다. API 모듈에는 인증 경계가 없다. 승인 후 관련 로컬 문서를 최신 계약에 맞출 필요가 있다.

G1 — 관심 주제는 10개인가, 12개인가?

ERD는 housing/labor/finance/welfare/education/health/climate/security/local/politics 10개다. 화면은 주거·노동·금융세제·교육·복지·외교안보·환경에너지·지역·청년세대·사법검찰·국회정당·미디어 12개이며 노트에도 팀 결정이라고 적혀 있다. 단순 표시명 차이로 매핑할 수 없다.

A: ERD 10개를 공통 분류로 채택(권고). B: 화면 12개로 공통 분류 개정. A는 피드·상세·선호의 코드 일치를 유지하지만 화면을 바꿔야 한다. B는 분류·집계 계약까지 함께 개정해야 한다. 이 결정은 선택지 응답과 seed를 연다.

G2 — 나이 구간과 미응답은 어떻게 확정할까?

ERD 4구간과 화면 6구간은 서로 정확히 변환되지 않는다. ERD는 필수 여부 미정, 화면은 미응답을 허용한다.

A: ERD 4구간 + NULL 허용(권고). B: 화면 6구간 + NULL 허용. A는 issue_impacts와 동일 코드이나 화면을 바꿔야 한다. B는 영향 생성·조회 대상 코드도 함께 바뀐다. 필수로 받고 싶다면 별도 의견이 필요하다. 이 결정은 ageGroup 검증을 연다.

G3 — 이번 범위는 최초 온보딩인가, 설정 수정까지인가?

화면 노트는 재진입·설정 없음, ERD는 나이대를 설정에서 수정한다고 명시한다. 모두 같은 weight를 쓰는 선호 재설문은 학습 점수 보호 문제를 만든다.

A: 최초 완료/skip만 구현, 설정 수정은 별도 작업(권고). B: 나이 수정 API까지 포함. C: 관심 항목 재설문까지 포함. A는 범위를 좁히되 ERD의 향후 수정 요구를 폐기하지 않는다. B는 프로필 수정 경계, C는 초기 선택과 학습 기여 분리 설계가 추가된다.

G4 — 단계별 저장인가, 마지막 한 번 저장인가?

기획은 여러 화면과 마지막 시작하기를 설명하지만 서버 저장·중단 복구 시점을 확정하지 않는다. 이는 가정이며 원문 결정으로 처리하지 않는다.

A: 화면 이동은 클라이언트 초안, 마지막에 한 번 원자 저장(권고). B: 각 단계에서 서버 초안 저장·이어하기. A는 중복 가산·부분 완료를 줄이지만 앱 데이터가 사라지면 미완료 입력을 잃는다. B는 기기 간 재개가 가능하지만 초안/skip 폐기 규칙이 필요하다.

G5 — 소셜 로그인 없이 회원 식별을 어디까지 연결할까?

현재 인증 구현이 없으며 임의 userId로 사용자 데이터를 수정하게 할 수 없다. 소셜 로그인은 제외한 채 다음 범위를 고른다.

A: 인증된 사용자 공급 경계를 정의하고 테스트에서만 대체, 실제 인증 연결 전 보호 API 사용 불가(권고). B: 외부에서 발급한 access token 검증까지 이번 범위에 포함. A는 온보딩을 독립 검증하지만 운영 연결은 후속 작업이다. B는 발급 주체·서명·만료·사용자 매핑 계약을 먼저 확인해야 한다.

G6 — 대상 선택 화면에 어떤 목록이 필요한가?

정정: “기본 목록은 최근 30일 보도량 상위 순”은 피그마 스펙 노트 11:224의 유형 탭 설명이었다. 코멘트 #1과 답글에서는 확정되지 않았다. 사용자는 모르는 기획이라고 밝혔으며, 이를 확정 기획의 변경 여부로 질문한 이전 프레이밍을 철회한다. 전체 노트의 다른 세부 규칙도 코멘트 결정과 구분한다.

A: 등록된 인물·정당·기관 목록 + 이름 검색 + 유형 필터, 기본 이름순(권고). B: 처음에는 목록 없이 검색했을 때 결과만 표시. A는 검색할 이름을 몰라도 둘러볼 수 있지만 마스터 목록 준비가 필요하다. B는 간단하지만 탐색성이 낮다. 실제 보도량/추천 순위는 현재 요구로 확정하지 않는다. 검색 방식·페이지 경계는 이 결정 뒤 확정한다.

G7 — 도중에 전체 건너뛰기를 누르면 앞선 선택도 버릴까?

G4에서 마지막 일괄 저장을 선택했다. 화면 노트는 전체 skip 시 초기 가중치 0이라고 쓰지만 도중에 이미 선택한 값의 처리는 코멘트로 확인되지 않았다.

A: 모든 초안을 버리고 SKIPPED, 나이 NULL·선호 없음(권고). B: 그때까지 선택을 저장하고 나머지만 생략. A는 건너뛰기의 의미가 단순하나 앞선 입력을 잃는다. B는 입력을 살리지만 완료 최소 조건·SKIPPED 의미를 추가 정의해야 한다. 이 결정은 skip payload와 상태 불변식을 연다. 개별 나이 미응답과 전체 건너뛰기는 구분한다.

G8 — 이미 완료한 회원이 다시 제출하면?

G3에서 최초 온보딩만, G4에서 마지막 일괄 저장을 선택했다. 커밋 성공 후 응답이 유실되면 재전송이 발생할 수 있다. 어떤 선택이든 초기 가중치를 다시 적용하지 않는다.

A: 최종 상태가 이미 있으면 변경 없이 저장된 상태를 반환(권고). 완료/skip 경합은 먼저 저장된 결과를 따르고 응답에 실제 상태를 명시한다. 같은 payload인지 증명하지는 않으며, 뒤의 다른 선택도 반영되지 않는다. B: 동일 요청 키와 payload만 성공 재응답하고 다른 요청은 409. B는 의도를 엄격히 검증하지만 제출 키·요청 해시 보관과 클라이언트 키 관리가 추가된다. 설정 변경 처리는 둘 다 후속 작업이다.

G9 — 관심 지역은 선택만 저장할까, 초기 점수 +1도 둘까?

코멘트는 지역 수집을 확정했지만 +1은 스펙 노트에만 있고, ERD에 지역 저장/가중치 구조는 없다. 카테고리·대상 +2는 ERD 근거가 있으나 지역 +1은 동일한 확정사항으로 볼 수 없다.

A: 사용자별 지역 코드 선택만 저장(권고). 실제 추천 점수는 후속 추천 계약에서 결정. B: 지역 선호 weight도 만들어 초기 +1을 저장. A는 미확정 점수를 데이터 계약에 넣지 않지만 이후 점수 모델을 추가할 수 있다. B는 노트와 맞지만 소비 규칙이 없는 점수가 생긴다. 지역은 17개 시도 복수 선택·전국은 빈 목록으로 제안한다. 이 결정은 지역 영속 모델을 확정한다.

G10 — 첫 대상 마스터는 어떻게 준비할까?

현재 저장소에 인물·정당·기관 업무 데이터와 수집 경로가 없다. G6의 목록/검색 API가 있어도 마스터가 비어 있으면 빈 결과가 정상이며 실제 선택이 불가능하다.

A: 승인된 목록을 추후 넣을 수 있는 초기 적재 절차와 테스트 fixture만 이번에 준비(권고). 실제 서비스 목록 확보는 별도 선행 조건으로 표시. B: 실제 초기 목록 선정·확인·적재까지 이번 작업에 포함. A는 임의 명단을 만들지 않고 API를 검증하지만 서비스 사용 전 데이터가 필요하다. B는 실제 선택 가능한 상태까지 만들 수 있으나 대상 범위·출처·관리 책임을 추가로 정해야 한다. 이 결정은 API 완성과 운영 준비 상태의 경계를 확정한다.

G9-B / G10-A로 해결. 의사결정 답변은 구현 승인이 아니다. 공유 이해 확인 뒤 별도 design-control과 구현 승인 단계를 진행한다.

HTTP·상태 계약 제안

경로와 세부 제한은 이 설계 승인과 구현 계약에 따라 확정됐다. 실제 DB·인증 연결 공백은 구현 제어 문서에서 별도로 보류한다.

온보딩 API 제안
API 책임
GET /onboarding/options 관심 주제 12개·나이 4구간·지역 17개 코드와 표시명, 표시 순서
GET /onboarding/entities 활성 대상 목록. q/name prefix 검색, type 필터, name+id 안정 정렬. q 없음은 전체 목록. limit 기본 20·최대 100, offset 기본 0. 이름과 id 동률 방지, 변경 중 페이지 고정 스냅샷은 보장하지 않음.
GET /me/onboarding 인증된 사용자의 status, completedAt, ageGroup, regionCodes. 최초 선택 원본 복원을 약속하지 않음.
POST /me/onboarding/complete topicCodes, entityIds, ageGroup(nullable), regionCodes. 사용자 id와 weight는 받지 않음.
POST /me/onboarding/skip 초안 payload 없이 전체 skip. 완료/skip 응답 모두 실제 저장된 status, completedAt 반환.

검증 제안: topicCodes 1~12개, entityIds 0~100개, ageGroup 허용 enum 또는 NULL, regionCodes 0~17개. 배열 중복은 400, PENDING 상태에서 없는 코드·비활성 대상은 전체 400으로 거절하고 상태를 유지한다. 상한 100은 자원 제한 제안이며 화면의 선택 권장 개수를 뜻하지 않는다. 마스터 조회에는 개인 데이터가 없어 공개, /me 경로는 인증 공급자가 없으면 401로 닫는다.

  1. HTTP 형식 검증과 인증 후 사용자 트랜잭션 시작.
  2. 사용자 행 잠금, 존재·상태 확인. 인증된 사용자 행이 없으면 생성하지 않고 401.
  3. COMPLETED/SKIPPED면 실제 기존 상태를 반환. 형식이 유효한 다른 payload에도 선택 대상을 다시 조회하거나 점수를 반영하지 않음.
  4. PENDING complete는 선택 유효성을 검사하고 주제·대상 +2를 각각 한 번 더한다. 이미 학습된 weight가 있으면 2로 덮어쓰지 않음. 지역은 최초 선택마다 +1을 더함(G9-B). 나이·COMPLETED·서버 완료 시각을 함께 저장.
  5. PENDING skip은 온보딩 선택을 저장하지 않고 SKIPPED. 기존 행동 학습 선호는 삭제하지 않음. completedAt은 NULL 유지하여 실제 완료 시각과 구분.
  6. 커밋 후 응답. 첫 피드 요청은 클라이언트가 별도로 수행하며 실패해도 온보딩은 유지.

주의: skip에서 선호 없음은 온보딩이 생성한 선택이 없다는 의미다. 향후 다른 경로에서 생긴 학습 선호까지 초기화하지 않는다. 모든 사용자 선호 쓰기가 동일 사용자 잠금 규칙을 공유해야 동시 학습과 충돌하지 않는다. 선택 당시 활성 여부는 제출 시 조회한 DB 스냅샷 기준이며 미래 마스터 비활성화에 대한 영구 활성 보장은 하지 않는다.

검증 계획

승인 당시 검증 계획은 단위 테스트로 허용 입력·상태 전이를 확인하고, 실제 PostgreSQL 통합 테스트로 FK·UNIQUE·롤백·동시 완료·skip·재전송을 확인하는 것이다. 현재 실행 결과는 구현 제어 문서에 기록했으며, 다른 회원 접근·실제 인증·코드/선택값 로그 노출은 운영 DB와 인증 provider 연결 후 추가 검증한다.

현재 실행 기반: npm run test:jest -- test/unit, npm run test:jest -- test/integration, npm run build, npm run contracts:check, npm run test:smoke. 새 테스트의 정확한 파일·명령과 migration 검증은 설계 확정 후 Execution Contract에 기록한다. 계약 생성 명령은 생성 파일을 바꾸므로 승인 전 실행하지 않는다.

공유 이해 확인

G1~G10의 사용자 결정과 아래 기술 제안을 함께 확인한다. 이 확인은 구현 승인이 아니다.

  • 회원 최초 설문: 주제 12개 → 인물·정당·기관 → 나이 4구간 → 지역 17개. 나이는 미응답 허용. 주제 최소 1개, 대상·지역은 빈 선택 허용으로 제안.
  • 클라이언트에서 초안을 모아 마지막 한 번 저장. 주제·대상 +2, 지역 +1, 나이와 완료 상태를 한 트랜잭션에서 반영.
  • 전체 skip은 미저장 초안을 버리고 SKIPPED. 개별 나이 미응답과 구분.
  • 최종 상태 이후 재요청은 변경 없이 기존 상태 반환. 완료/skip 경합도 먼저 저장된 결과 유지. 추후 수정 기능은 별도 API로 설계.
  • 대상 목록은 활성 대상 이름순·이름 prefix 검색·유형 필터. 초기 적재 절차와 테스트 fixture를 준비하되 운영 명단은 후속 제공.
  • 소셜 로그인·실제 인증은 제외. /me API는 인증 공급자가 없으면 401. 테스트에서만 인증 공급자를 대체.

남은 기술 제안: 완료만 completedAt을 기록하고 SKIPPED는 NULL; 잘못된 입력·중복 선택·없는/비활성 대상은 PENDING에서 전체 거절; 주제 1~12·대상 0~100·지역 0~17개 제한; 최초 온보딩 상태 조회는 선택 원본 복원을 약속하지 않음. 실제 추천 계산·설정 수정·운영 명단·인증 연결은 별도 작업이다.

스키마·코드 목록·migration 도구·검증 명령은 공유 이해 확인 후 최종 설계 기준선에 구체화하고 별도 구현 승인을 받는다. 구현 파일은 수정하지 않는다.

설계 이해·통제 점검 (design-control)

상태: 미실시. 의사결정·공유 이해 확인과 별도의 정보성 자가점검이다. 결과는 브라우저 안에만 남으며 Codex에 자동 전달되지 않는다. 결과가 없다는 이유로 구현을 되돌리거나 승인으로 간주하지 않는다.

후속 통합 결정으로 기존 문서의 12개 uppercase topic 기록은 과거 설계 이력으로 남기고, 현재 API 계약은 lowercase canonical 10개로 교체했다. GET /onboarding/options와 complete request의 topicCodes는 housing, labor, finance, welfare, education, health, climate, security, local, politics만 허용하며 배열 상한은 10이다. 표시명과 순서는 shared category catalog가 소유한다.

저장소에서는 issue_categories.code가 PK이고, 이슈와 category preference는 category_code FK를 사용한다. 레거시 category id/code는 승인된 mapping만 backfill하며 미지원 값이나 양쪽 컬럼 불일치는 migration을 중단한다.
