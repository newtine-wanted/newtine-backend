승인 기준선

사용자는 통합 설계안과 후속 G24-A~G27-A 선택을 확인한 뒤 “승인 — 구현 시작”으로 직접 승인했고, G28~G31 production wiring·ORM 경계 재설계와 회원·비회원 동일 feed contract도 2026-09-15 KST 승인했다. 유효한 JWT principal은 회원 경계로 사용하고, 인증이 없는 요청은 서버 발급 guest cookie로 익명 소유권을 이어간다. 임의 x-user-id와 x-feed-guest-key는 신뢰하지 않는다. 공통 점수 산정·대표 대상 자동 해석·행동 이벤트 쓰기·최초 생성 멱등 키는 이번 실행에서 제외한다.

구현 계약의 허용 변경은 위 후속 행과 그에 필요한 회귀 테스트로 한정한다. G26의 mainTopic·representativeEntity는 producer가 제공하기 전까지 NULL로 남기며, category나 첫 entity를 대체값으로 쓰지 않는다. PERS-001의 세 onboarding preference는 기존 ORM 테이블에서 양수 weight만 읽고 조회 중 쓰지 않는다. 실제 PostgreSQL 업무 schema가 현재 migration과 다르면 우연히 동작하도록 숨기지 않고 migration·entity·query의 계약을 함께 맞춘다.

현재 저장소에는 실제 업무 schema·이슈 생성 측 점수/대표 대상 데이터와 production rate-limit 정책이 없다. production API는 검증된 JWT principal 또는 서버 발급 guest cookie와 MikroORM adapter만 사용하고, 인메모리 adapter와 passthrough transaction manager는 test/fixtures에서만 명시적으로 주입한다. 실제 PostgreSQL 왕복·lock 경쟁·운영 schema·rate-limit/session-cap 연결은 잔여 위험으로 추적한다.

현재 구현(as-built)

승인 기준선의 API·추천 규칙·상태 경계와 후속 리뷰 개선을 구현했다. 하나의 cursor feed API에서 선택적 JWT 분기와 guest cookie owner 경계까지 포함한다. PostgreSQL 계약 정합성, 공개 기사 상태 predicate, transaction/만료 경계, 이전 batch bulk-load, InMemory scope parity, production ORM provider 경계를 반영했다. 최신 사용자 context의 onboarding category/entity/region 선호와 producer-owned issue metadata pass-through도 연결했으며, 기존 검색 계약과 인증·사용자 정보 경계는 보존한다.

  • FeedController: GET /feed 하나. cursor가 없으면 첫 페이지를 만들고, 응답의 opaque nextCursor를 그대로 받은 요청은 다음 페이지를 복원한다. 내부 feed_sessions·feed_batches는 재시도·중복 방지용으로만 유지한다.
  • IssueController: GET /issues/:issueId 상세와 기존 POST /issues/search.
  • issueRecommendation.ts: 7항목 가중합, 4/2/1/2/1 배정, 후속·중복·연속 제한·예산 상태. 대체 후보는 candidate budget 전체를 스캔하되 최대 3 rounds·후보당 2개 replacement proposal로 bounded search한다. 이 상한으로 미입증된 불완전 결과는 SEARCH_LIMITED로 분류한다.
  • 후보 예산은 RECOMMENDATION_CANDIDATE_BUDGET(10~500, 기본 100), 높은 점수 기준은 RECOMMENDATION_HIGH_SCORE_THRESHOLD(0~1, 기본 0.7)로 제한한다. 운영 기본값은 외부 점수 계약 확인 전 최종 정책이 아니다.
  • 테스트 전용 InMemory adapter와 passthrough transaction fixture를 test/fixtures로 이동하고, production에는 IssueCardQueryRepository 하나만 등록했다. 이슈·상세·기사·관계·feed 상태 EntitySchema를 database options에 등록하고, feed/read-model migration은 schema evolution 책임으로 유지한다.
  • 단일 feed route는 기존 JwtAuthGuard의 optional policy를 사용한다. 유효한 JWT는 검증된 principal 기반 MEMBER owner·personal context로, 인증 없음은 GUEST owner·generic public ranking으로 분기한다. 제공된 JWT가 invalid이면 guest로 삼키지 않고 401이다.
  • guest 첫 feed 요청은 JWT secret으로 nonce와 수명을 서명한 고엔트로피 opaque HttpOnly·SameSite=Lax cookie를 발급하고, DB에는 SHA-256 hash만 저장한다. cursor feed 요청은 같은 유효 cookie를 요구하며 x-user-id·x-feed-guest-key·client pseudo-user를 사용하지 않는다. member/guest owner는 DB XOR constraint와 별도 partial index로 격리한다.
  • 현재 guest cookie 서명 키는 JWT_SECRET과 동일하다. 따라서 JWT secret 회전은 TTL이 남은 기존 guest cookie도 즉시 무효화하는 전역 guest session invalidation으로 취급한다. versioned guest key ring과 이전 키의 유예 검증은 별도 운영 설계 범위다.
  • guest는 user row·preference·interaction을 읽거나 쓰지 않고 공개 generic 후보만 사용한다. 같은 공개 데이터·시점에서는 member context와 무관한 deterministic public ranking을 사용하며, 이후 게시·철회·시간 변화는 새 session에 반영한다. global frozen snapshot은 만들지 않는다.
  • 회원과 guest 모두 session lifecycle은 24시간이다. 현재 저장소에는 edge/app rate limit과 guest session 상한 enforcement가 없으므로 이를 실제 배포 환경에서 확인하기 전에는 production release로 판정하지 않는다.
  • cursor는 AES-GCM으로 암호화한 owner-bound opaque token이며 내부 session ID·batch 번호를 외부에 평문으로 노출하지 않는다. 변조/형식 오류는 400, 만료는 410, 다른 owner나 proof 없는 재생은 401/404로 거절한다.
  • 상세의 관점·용어 JSON article reference는 현재 이슈의 연결 기사에 없는 ID를 제거한다.
  • 제한 상태 이후 새 batch는 서비스와 저장소 transaction에서 모두 거절하며, 같은 batch 재시도는 저장된 묶음을 복원한다.
  • batch 계산은 use case의 TransactionManager 경계에서 후보 조회부터 저장까지 수행한다. PostgreSQL adapter는 ambient transaction만 사용하고, 저장 직전 잠금 후 ORM criteria에서 database clock으로 세션 만료를 재확인한다.
  • 이전 batch item은 한 번에 bulk-load한다. test fixture adapter도 personalized/major/ connected/exploration/mismatch slice, 제외 ID, limit, global fill semantics를 production ORM adapter와 맞춘다.
  • 공개 기사·개수·reference는 source_status = 'AVAILABLE'만 사용한다. 현재 producer가 main topic·대표 대상을 쓰지 않으므로 PostgreSQL capability는 명시적으로 비활성이고 임의 대체값을 만들지 않는다.

상태: 기술 구현·로컬 게이트 및 Compose DB smoke 완료, 운영 제어 보류. 후속 G24~G27·G28~G31, CQ-REV-011·PERS-001~003·GUEST-001~004 보완은 승인된 범위로 반영했지만, 실제 업무 PostgreSQL lock/EXPLAIN/p95·점수/대표 대상 producer 계약·rate-limit/session-cap enforcement에 대한 운영 이해 점검은 아직 실시하지 않았다. 운영 연결 전에 JWT member와 cookie guest의 요청 소유권, 같은 묶음 재시도/동시성, 24시간 만료 race, 후보 탐색 상한과 빈 피드 구분, AVAILABLE 기사 정책을 담당자가 설명하고 격리 환경 증거로 재검증해야 한다. 이 점검은 기술 완료나 설계 승인과 별개다.
