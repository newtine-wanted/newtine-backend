현재 구현(as-built)

승인 범위의 API·추천 규칙·상태 경계를 구현했다. 개선 승인에 따라 제한 상태의 새 묶음 생성 차단과 후보 예산 내 대체 탐색 상한도 반영했다. 기존 검색 계약은 설계 범위대로 보존하고, 새 구현은 상세·피드 조회에 집중한다.

  • FeedController: POST /feed-sessions와 POST /feed-sessions/:sessionId/batches.
  • IssueController: GET /issues/:issueId 상세와 기존 POST /issues/search.
  • issueRecommendation.ts: 7항목 가중합, 4/2/1/2/1 배정, 후속·중복·연속 제한·예산 상태. 대체 후보는 candidate budget 전체를 스캔하되 최대 3 rounds·후보당 2개 replacement proposal로 bounded search한다. 이 상한으로 미입증된 불완전 결과는 SEARCH_LIMITED로 분류한다.
  • 후보 예산은 RECOMMENDATION_CANDIDATE_BUDGET(10~500, 기본 100), 높은 점수 기준은 RECOMMENDATION_HIGH_SCORE_THRESHOLD(0~1, 기본 0.7)로 제한한다. 운영 기본값은 외부 점수 계약 확인 전 최종 정책이 아니다.
  • 인메모리 테스트 adapter와 ERD v1.3용 PostgreSQL raw adapter, feed 상태 migration을 추가했다.
  • 게스트 세션은 서버가 발급한 고엔트로피 bearer key를 생성 응답으로 한 번 전달하고, 저장소에는 SHA-256 해시만 남긴다. 배치 요청은 해당 key를 소유 증명으로 보내며, 최초 생성 멱등 키는 구현하지 않았다.
  • x-user-id는 인증 분기 연결 전 임시 principal 경계이므로 운영에서 직접 신뢰하지 않고 검증된 인증 principal로 교체해야 한다.
  • 상세의 관점·용어 JSON article reference는 현재 이슈의 연결 기사에 없는 ID를 제거한다.
  • 제한 상태 이후 새 batch는 서비스와 저장소 transaction에서 모두 거절하며, 같은 batch 재시도는 저장된 묶음을 복원한다.

완화됨 초기 설계 초안의 피드 경로가 기존 이슈 컨트롤러 경로와 겹칠 수 있었다. FeedController를 분리해 정식 경로를 /feed-sessions로 고정하고 계약을 다시 생성했다. npm run contracts:check 통과. 구 경로 생성물은 제거.
해결됨 CQ-REV-001: 제한 continuation 뒤에도 새 batch를 저장하던 상태 경계. 서비스가 마지막 묶음 continuation을 검사하고, InMemory/PostgreSQL 저장 transaction도 현재 session·마지막 continuation·예상 번호를 재검사해 새 batch를 409로 거절한다. 제한 batch 재시도 복원·새 번호 거절 unit 회귀 통과. 실제 PostgreSQL 왕복은 별도 공백.
해결됨 CQ-REV-002: candidate budget보다 작은 100개 대체 후보 hard cap으로 유효 후보를 놓치던 문제. candidate budget 전체를 스캔하고, 대체 탐색을 최대 3 rounds·후보당 2개 proposal로 제한해 CPU 상한을 명시했다. 예산 밖 미검증은 SEARCH_LIMITED로 유지한다. 100개 이후 후보 선택·기존 SEARCH_LIMITED unit 회귀 통과. 실데이터 p95는 별도 측정.
보류 운영 데이터·인증 principal·지역 선호·대표 대상·점수 생산 계약이 저장소에 없다. DB 실패를 503으로 세분화하는 운영 오류 계약도 아직 없다. 인메모리 adapter와 ERD용 raw PostgreSQL adapter를 분리했다. 외부 계약을 임의로 채우지 않는다. 격리 PostgreSQL 왕복·EXPLAIN 및 인증/온보딩 연결 후 운영 제어 재개.
신규 없음 로컬 게이트에서 추가로 남은 실패는 없다. 새 재현 사례가 생기면 이 표에 영향 범위와 조치를 기록한다. 검증 명령과 결과는 아래 증거와 함께 갱신.

CQ-REV-002 · fixed · P2 해소 초기 구현은 issueRecommendation.ts:237-240에서 대체 후보를 slice(0, 100)으로 잘랐다. 이제 이미 읽은 candidate budget 전체를 스캔하며, 100개 이후 다른 주제 후보를 선택하는 fixture로 회귀한다. 대체 순열 탐색은 최대 3 rounds·후보당 2개 proposal로 제한한다. CQ-REV-006 · fixed · Blocker 해소 PostgreSQL의 raw MikroORM get 결과는 배열이 아닐 수 있어 transaction 안의 session/latest 조회가 비어 보일 위험이 있었다. 공통 normalizeRows가 get의 단일 row를 [row]로 정규화한다. fake connection 회귀가 insert/update 경계를 확인했다.
CQ-REV-007 · fixed · P2 해소 InMemory 저장소의 존재 확인과 첫 write 사이에 비동기 양보가 있으면 동시 요청의 서로 다른 결과가 마지막 write로 덮일 수 있었다. 검사·저장을 동기 구간으로 유지하고 Promise.all first-write 회귀를 추가했다.
CQ-REV-008 · fixed · P2 해소 candidate budget 전체를 읽어도 bounded replacement의 후보당 2개·최대 3 rounds 상한 때문에 유효 조합을 입증하지 못할 수 있었다. replacement 절단 또는 round 상한으로 불완전한 결과는 SEARCH_LIMITED로 보존한다. 실제 연속 제약만 CONSTRAINT_LIMITED로 남기며 전용 fixture로 분류를 검증했다.
CQ-REV-003 · accepted(scope) · 운영 blocker PostgreSQL adapter의 issueSelect는 main_topic과 representative_entity_id를 항상 NULL로 반환하고 (postgresIssueQuery.repository.ts:569-573), findUserContext는 age_group 외 주제·대상·지역 선택을 빈 집합으로 반환한다(:260-279). 따라서 현재 실 schema로 운영하면 2장 연속 제한과 대부분의 개인화 일치가 동작하지 않는다. 외부 producer·온보딩 계약이 승인 범위 밖이라는 사실은 결함을 제거하지 않으며, 연결 전 운영 blocker로 남긴다. 더불어 controller는 x-user-id를 UUID 형식만 검사해 owner/context로 사용하므로(feed.controller.ts:26,51), 인증 guard가 없는 현재 상태에서 임의 회원 UUID를 가장할 수 있다. 인증 principal을 주입하고 외부 x-user-id를 신뢰하지 않도록 한 뒤, producer가 대표 대상/주제를 제공하고 온보딩 선택 집합을 조회 port로 연결한다. 실제 PostgreSQL·권한 통합 테스트 전에는 운영 배포로 판정하지 않는다.
CQ-REV-004 · discussion-needed · P2 articles.source_status(AVAILABLE/REMOVED/UNKNOWN)가 데이터 계약에 있지만 loadArticles(postgresIssueQuery.repository.ts:345-362)는 상태를 조회하거나 필터하지 않는다. 제거된 원문 URL도 상세 응답에 남을 수 있고, 현재 response 타입에는 상태를 표현할 필드도 없다. 제거 원문을 숨길지 상태를 내려줄지 계약을 결정한 뒤, articleCount·article reference 정합성과 함께 통합 테스트한다.
CQ-REV-005 · non-blocking risk · P2 런타임에서 guest batch에 필요한 x-feed-guest-key와 회원 x-user-id가 raw @Headers로만 읽혀 생성 OpenAPI/SDK의 operation parameter에 나타나지 않는다. IConnection.headers를 직접 채우면 호출되지만, per-session bearer key 요구가 계약에서 발견되지 않는다. typed headers 또는 OpenAPI header 명세를 추가하고 생성 SDK에서 요구 조건을 드러낸다. 인증 principal 연결 시 x-user-id 임시 경계도 제거한다.
CQ-REV-009 · fixed · Non-blocking 설계·구현 문서의 개선 상태와 테스트 수치가 구현 완료 후에도 이전 값으로 남아 있었다. 두 문서의 구현 완료·운영 검증 대기 상태와 unit 10 suites/41 tests 증거를 갱신했다.
CQ-REV-010 · accepted verification gap · Non-blocking 실제 PostgreSQL 왕복·lock 경쟁·운영 p95는 로컬 환경에서 입증할 수 없다. 격리 PostgreSQL과 운영 데이터 연결 후 SQL·rollback·lock·EXPLAIN·p95를 측정한다. 현재 배포 완료로 판정하지 않는다.

검증 증거와 공백

개선 후 npm test를 재실행해 unit 10 suites/41 tests와 integration 1 suite/5 tests가 통과했다. format:check, lint, typecheck, build, contracts:check, smoke, git diff --check도 통과했다. PostgreSQL raw get row 정규화는 adapter 코드로 보강했지만 실제 왕복·rollback·lock 대기· EXPLAIN·인증 격리는 아직 검증하지 않았다.

리뷰 판단: CQ-REV-001·002는 수정·회귀 검증으로 해소됐다. CQ-REV-003은 인증·외부 producer/온보딩 연결 전 운영 blocker로 남고, CQ-REV-004는 제품·데이터 계약 논의, CQ-REV-005는 API 계약 보완이 필요한 P2다. CQ-REV-006·007·008은 수정·재검증으로 해소됐고 CQ-REV-009는 문서 갱신으로 닫혔다. CQ-REV-010의 실제 PostgreSQL·인증·성능 실측 전에는 배포 완료로 판정하지 않는다.

구현 이해·통제 점검

상태: 운영 제어 보류. 구현 결과와 로컬 검증은 확인했지만, 실제 PostgreSQL·인증 principal· 온보딩 지역/나이대·점수 생산 계약에 대한 운영 이해 점검은 아직 실시하지 않았다. 운영 연결 전에 요청 소유권, 같은 묶음 재시도/동시성, 24시간 만료, 후보 탐색 상한과 빈 피드 구분, 철회 콘텐츠 재조회 정책을 담당자가 설명하고 격리 환경 증거로 재검증해야 한다. 이 점검은 기술 완료나 설계 승인과 별개다.
