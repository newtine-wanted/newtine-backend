목표와 범위

‘내 관심 분석’에 기간·분야별 건수·표본 상태를 제공한다. 마이페이지의 ‘관심 뉴스’ 전체 건수와 별도 목록 조회도 연계 초안으로 제시한다. 온보딩 선호 점수나 정치적 찬반·성향을 분석하지 않는다.

비범위: 회원탈퇴·로그아웃·프로필, 주간 진단보고서 생성, 추천 알고리즘, 분류 개편. 관심 등록·해제 쓰기 API는 선행 의존성이며, 이번에 함께 설계할지는 G2에서 결정한다.

분석 응답 예시 — 피그마 표시대로 최근 7일 적용

{
  "asOf": "2026-09-15T03:00:00.000Z",
  "period": {
    "type": "ROLLING_DAYS", "days": 7,
    "startAt": "2026-09-08T03:00:00.000Z",
    "endAt": "2026-09-15T03:00:00.000Z",
    "timeZone": "Asia/Seoul"
  },
  "sampleStatus": "LOW_SAMPLE",
  "minimumSampleSize": 10,
  "issueCount": 3,
  "likedIssueCount": 12,
  "categoryCounts": [
    { "code": "housing", "name": "주거", "count": 2 },
    { "code": "labor", "name": "일자리", "count": 1 }
  ]
}

예시의 categoryCounts는 표시할 0 초과 분야만 반환한다. 건수 내림차순, 동률은 공통 분류의 displayOrder. 전체 필터 선택지는 기존 GET /onboarding/options의 공통 분류를 재사용한다. issueCount는 기간 내 서로 다른 이슈 수, likedIssueCount는 기간 제한 없는 현재 공개 관심 이슈 수다. 두 값은 같을 필요가 없다.

제안 상태: 0건 EMPTY, 1~9건 LOW_SAMPLE, 10건 이상 READY. 임계값 10은 화면의 예시를 따른 제안이며 보고서의 5건 기준과 공유하지 않는다. 기간 내 0건이면 안내는 ‘이 기간에 관심 표시한 뉴스가 없어요’로 표시해 과거 기록이 없다는 오해를 피한다.

목록 응답 예시

{
  "items": [{
    "issueId": "01994508-0000-7000-8000-000000000001",
    "title": "청년 주거 지원 정책 개편",
    "category": { "code": "housing", "name": "주거" },
    "likedAt": "2026-09-14T12:00:00.000Z",
    "thumbnailUrl": null
  }],
  "totalCount": 1,
  "nextCursor": null
}

totalCount는 선택한 분야 필터를 적용한 전체 건수, nextCursor: null은 마지막 페이지. 제목은 뉴스 기사 대신 이슈 제목이다. 현재 이슈 스키마에는 썸네일 필드가 없어 초기에는 null을 반환하는 제안이다. 상세 조회 구현은 별도 의존성이다.

순서는 likedAt DESC, issueId DESC. 커서는 마지막 정렬 키와 필터를 담는 검증 가능한 불투명 값으로 제안한다. 다른 필터의 커서는 400, 필터 변경 시 첫 페이지부터 요청한다. 매 페이지는 현재 상태 기준이므로 페이지 사이 관심 변경 시 이동·누락이 가능하며 고정 스냅샷을 보장하지 않는다. 해제 후 프론트는 분석과 목록 첫 페이지를 재조회한다.

집계 모델과 데이터 의존성

  1. 요청의 인증 주체와 조회 기준 시각 asOf를 정한다.
  2. 해당 회원의 이슈별 최신 행동을 결정한다. 기간으로 먼저 자른 뒤 최신 상태를 고르면 안 된다.
  3. 최신 행동이 LIKE이고 이슈가 PUBLISHED인 경우만 현재 관심 집합으로 남긴다.
  4. 현재 관심 집합 중 최근 LIKE 서버 수용 시각이 [startAt, endAt)인 이슈를 한 번씩 센다.
  5. 공통 분류로 집계한다. 중복 LIKE 이벤트 수, 온보딩 선택 수, 추천 weight는 사용하지 않는다.

제안 기본안의 likedAt은 최신 LIKE 이벤트의 서버 created_at이다. 같은 LIKE를 새 이벤트 ID로 다시 보내면 건수는 늘지 않지만 likedAt·정렬·집계 기간은 바뀔 수 있다. 이 정책은 행동 수용 계약을 확정할 때 함께 검토한다. 동일 ID 재전송은 새 이벤트가 아니므로 시각도 바꾸지 않는다.

조회 모듈 후보: apps/api/src/interest/의 controller/service/type, libs/core/src/interaction/의 domain/repository. 기존 이슈·분류를 참조하고 별도 bookmark 테이블을 임의 도입하지 않는다. 이벤트 persistence가 먼저 준비되어야 하며 현재 ERD만으로 배포 가능하다고 판단하지 않는다.

인덱스 후보는 (user_id, issue_id, created_at DESC). 최종 동률 순서와 보존 정책은 행동 저장 설계의 선행 결정이다. 임의 UUID로 서버 수용 순서를 대체하지 않는다. 실측 EXPLAIN으로 확인한 뒤 필요한 인덱스만 채택한다.

불변식

  • 타인의 행동·관심 집합은 결과에 포함되지 않는다.
  • 각 이슈는 한 분류에 한 번만 집계하고 categoryCounts 합은 issueCount와 같다.
  • 온보딩만 완료한 회원은 실제 관심 행동이 없으면 EMPTY다.
  • 공개 중단 이슈는 목록·건수에서 제외한다. 로그로 해당 회원의 관심 제목·분야 목록을 남기지 않는다.
  • 현재 관심 취소가 지난주에 고정된 진단보고서 입력을 물리적으로 삭제하면 안 된다.

완료·G2 보류 수용 — G1은 사용자 지시로 해결했고, G2의 쓰기·해제 정책은 승인 범위에서 제외했다.

결정 트리
G1 집계 기간 → 기간 경계·빈 상태 → 최종 분석 DTO. G2 범위 → 해제·이벤트 저장 정책 → 최신 상태·정렬 계약.
현재 경계
G1은 사용자 지시로 해결했다. G2 범위와 해제 이벤트 형식·가중치 처리는 별도 미확정 상태다. 이번 기간 선택을 등록·해제 구현 승인으로 확대하지 않는다.
확인된 결정 근거

G1 — 그래프 집계 기간

해결 — 사용자가 “그러면 피그마 설계대로 해”라고 지시해 화면에 표시된 최근 7일을 채택했다. 서버 설정 기본값은 7일이며 실제 기간을 응답에 포함한다. 구현 해석은 조회 기준 시각 직전 7×24시간의 [startAt, endAt)이다. 이 시간 경계는 피그마에 명시된 사실이 아니라 본 설계의 구체화다. 지난주 월요일~일요일 기준 진단보고서와는 집계 기간이 다르다.

G2 — 이번 설계 범위와 해제 충돌 처리

권고는 분석·목록 조회 계약까지 우선 설계하고 행동 저장·해제는 선행 후속 설계로 명시적으로 보류하는 것이다. 대안은 등록·해제 쓰기 계약까지 이번에 함께 확정하는 것이다. 후자는 실제 연결 가능한 전체 흐름을 확보하지만 이벤트 삭제 여부·취소 시 점수·재요청 정책까지 설계해야 한다. 조회만 확정해도 이벤트 저장 없이 기능을 출시할 수는 없다.

미확정 분기를 승인된 기본값으로 취급하지 않는다. 최근 7일 기간은 사용자 선택으로 반영했다. 임계값·likedAt·페이지네이션은 검토용 제안이다. 이벤트 물리 삭제는 이전 행동을 되살리거나 과거 보고서 근거를 바꿀 수 있어 권고하지 않는다.

채택하지 않은 접근

추천 weight를 그래프로 사용, 기사 수나 반복 LIKE 수 집계, 별도 북마크 이원화, 화면 문구만으로 12개 분류 추가, GET에서 이벤트 생성. 최근 7일과 집계 기간이 다른 주간 보고서 응답을 그대로 그래프로 재사용하지 않는다.
