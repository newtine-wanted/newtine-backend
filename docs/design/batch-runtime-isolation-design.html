1. 목표와 기준선

report 실행에 pipeline AI 설정이 필요하지 않고, batch 이미지 하나로 기존 작업을 명시적으로 선택해 실행할 수 있게 한다. report 배포 정의는 API·pipeline 배포와 분리한다.

원본 작업 디렉터리에는 일별 report·DB 관련 미커밋 변경이 있다. 새 워크트리는 HEAD에서 생성했고 변경을 복사하지 않았다. report의 기간·스키마 계약은 이 개선이 결정하지 않는다. 후속 구현의 병합 전 최신 report 변경과 재검증해야 한다.

이번에 하지 않는 것

  • 기존 pipeline 폐기, 새 pipeline으로 운영 전환, 자동 공개·스케줄 등록, 클라우드 manifest 보관·재개.
  • 큐 교체, Pub/Sub 도입, DB 스키마·claim·lease·retry·과금 상태 변경, 전체 CoreModule 분해.
  • 실제 GCP 리소스 생성·배포, secret/IAM/DB 권한 변경, 유료 외부 API 호출. 구현 승인은 운영 배포 승인이 아니다.
  • 역할별 package.json 분리와 의존성 최소화. 공통 의존성을 유지하므로 이미지 분리를 보안 경계로 과장하지 않는다.

3. 초기화와 이미지 변경 모델

  1. 작업을 먼저 검증: main에서 인자를 allowlist로 검사한다. 없거나 모르는 작업이면 구조화 오류·exit 1, DB 연결·provider 생성 전 종료한다.
  2. 선택 모듈만 구성: 역할 registry가 선택된 feature module을 지연 import하고 공통 로깅과 결합한다. Report / Pipeline / DatabaseCheck가 각각 실행 adapter를 공통 BATCH_JOB 토큰으로 내보낸다.
  3. runner는 실행 계약만 참조: run(processExecutionId, signal) 계약에 의존하고 구체적인 Report/Pipeline job을 import하지 않는다. 기존 event 이름·processExecutionId·종료 코드·AbortSignal을 adapter로 보존한다. repair의 reclaim-owner 검증은 repair adapter에서 유지한다.
  4. 업무 로직은 그대로: ReportBatchJob/Worker 및 pipeline job의 데이터 처리 알고리즘을 변경하지 않는다. CoreModule은 공유하되 역할과 무관한 AI provider를 만들지 않는다.

Docker target 2개

공통 Node 24 runtime/dependency stage에서 api와 batch를 분기한다. cloudbuild·compose는 target을 명시한다. 기존 target 없는 API 빌드 호환을 위해 마지막/default target은 api로 유지한다. 두 이미지 모두 비루트 사용자로 실행한다.

batch CLI 자산은 명시적 목록으로 포함한다: news-pipeline.mjs, news-discovery.mjs, news-collection.mjs, news-generation.mjs, news-validation.mjs, news-generation-report.mjs, news-validation-report.mjs, news-pipeline-report.mjs, 문서에 있는 준비 명령 호환용 news-pipeline-prepare.mjs. 여기에 prompts/news-pipeline/, docs/news-pipeline/direction/ux-writing.md를 포함한다. 구현 시 상대 import의 전체 의존 파일을 검증한다.

WORKDIR=/app를 유지한다. /app/.local을 node 사용자가 쓸 수 있게 준비하고, 로컬 컨테이너 재개 시 이 경로를 사용자 소유 볼륨에 보관한다. 기존 --output·--resume 의미를 바꾸지 않는다. 컨테이너 로컬 파일은 영구 저장소가 아니다.

리소스 복사만으로 끝났다고 판단하지 않는다. ESM 상대 import, Core barrel의 의존성, JSON/YAML·프롬프트·UX 파일, 비루트 쓰기 권한까지 이미지 안에서 확인해야 한다. 누락을 피하려고 무조건 저장소 전체·.env를 복사하지 않는다.

4. 배포·구현 계약

기존 Cloud Build의 빌드·캐시는 유지하고 두 target을 빌드·각각 한 번 push한다. 기존 API 이미지 이름과 서비스 경로는 유지하며 batch용 이미지 이름만 추가한다. 기존 API 자동 배포는 유지하지만 batch push에 report/pipeline 자동 배포를 연결하지 않는다.

별도 report 배포 입력에서 검증된 batch digest를 명시한다. report 전용 Worker Pool 정의·배포 안내를 추가하되 실제 적용은 별도 운영 승인 대상이다. 다른 실행 단위의 digest는 변경하지 않는다. 공유 DB 호환성이 깨지면 이미지 rollback만으로 복구된다고 보장할 수 없다.

  • report 프로세스: node를 직접 실행하여 신호가 전달되게 하고 reportWorker 인자를 명시한다. HTTP 포트를 열기 위한 가짜 서버는 추가하지 않는다.
  • 초기 운영안: Worker Pool 인스턴스 1개, 프로세스 내부 동시성은 기존 1 유지. 상주 비용이 있으며 이미지 수를 줄인다고 상주 비용이 줄어드는 것은 아니다.
  • 환경변수: 기존 DB_*, report AI/worker 설정과 로깅 설정만 명시한다. 필요한 OPENAI 키·DB 비밀번호는 secret 참조로 주입한다. NAVER 키·API JWT secret은 report에 주입하지 않는다.
  • 전용 서비스 계정 식별자와 secret별 접근 권한을 배포 전 확인한다. 서비스 계정 분리만으로 PostgreSQL 테이블 권한이 분리되지는 않는다. 이번 범위는 DB grant 변경을 포함하지 않는다.
  • 기존 지역 후보 asia-northeast3의 사용 가능성·할당량, DB 연결 방식(사설망/Cloud SQL 연결 등), 계정·secret 이름, CPU·메모리는 실제 환경 확인 후 배포 전 확정한다. 실환경을 읽거나 추정 값으로 배포하지 않았다.
  • 로컬 compose.yaml의 api/batch build target을 명시하고 기존 프로필·명령을 유지한다. 기존 pipeline 로컬 설정은 report 역할로 자동 복사하지 않는다.

승인 후 구현 순서와 소유 범위

  1. apps/batch/src/main.ts, batch.module.ts, runner/, feature module/adapter: 역할 검증·초기화 격리.
  2. Dockerfile, 필요 시 .dockerignore, compose.yaml: 두 target·리소스 목록·비루트 출력 경로.
  3. cloudbuild.yaml, 신규 deploy/cloud-run/report-worker/: 이미지 발행과 report 명시적 배포 정의·운영 안내. live trigger나 GCP 리소스 변경 금지.
  4. test/unit/batchRunner.test.ts, 신규 test/unit/batchBootstrap.test.ts, 신규 test/scripts/batchImage.check.mjs: 경계·패키징 회귀 검증. 현재 없는 파일은 계획이며 생성하지 않았다.

실행 계약 상태: 제안됨 / 미승인. 완료 조건은 검증 표를 충족하는 diff와 배포 전 미확인 사항의 명시다. API/report 데이터 계약, DB 스키마, pipeline 업무 로직 변경이 필요해지면 작업을 멈추고 설계를 재승인한다.

5. 보존할 규칙

  • 한 프로세스는 한 역할만 수행한다. report가 pipeline job을 호출하거나 대신 시작하지 않는다.
  • report 실행은 pipeline YAML·NAVER 키 없이 가능해야 한다. 단, report 자신의 필수 설정·DB는 필요하다.
  • databaseCheck는 report/pipeline AI 설정 없이 실행할 수 있다. 잘못된 역할은 DB 초기화 없이 실패한다.
  • 기존 작업명·CLI 인자·ONCE 모드·종료 신호·로그 상관관계·성공/실패 exit 의미를 유지한다.
  • report claim의 lease·heartbeat·attempt·소유권 fencing과 기존 재시도 한도를 변경하지 않는다. 외부 AI 호출의 exactly-once를 보장하지 않는다.
  • 이미지에 .env·secret 값·로컬 결과물을 포함하지 않는다. report에 pipeline 전용 secret을 부여하지 않는다.
  • DB 테이블과 업무 상태는 그대로다. 공개 데이터에서 report를 생성하는 경계와 새 pipeline의 미공개 결과를 구분한다.

실패 시 예상 동작과 안전한 다음 조치
상황동작·영향확인 / 복구

report 버전 문제report 배포만 이전 호환 digest로 되돌린다. pipeline·API 배포는 불변.DB 호환성 먼저 확인. 기존 미완료 요청은 lease 규칙으로 회복; 외부 호출 중복 비용 가능.
새 CLI 파일 소실로컬 manifest 기반 resume이 불가능할 수 있다. 이미지에 파일이 있다고 운영 저장 문제가 해결되지 않는다.로컬 볼륨으로 결과를 보관한다. GCP 영구 보관·재개·스케줄은 이번 범위 밖.
공유 DB/외부 API 할당량 장애별도 프로세스여도 동시 영향 가능.DB 연결 한도·AI 오류/사용량 확인. 별도 이미지로 해결된다고 판단하지 않는다.

운영 안내에는 역할·image digest·revision·processExecutionId·reportId로 로그를 추적하는 방법, QUEUED 수/최장 대기시간·오래된 RUNNING·실패/재시도 추세를 확인하는 조회를 포함한다. 경보 임계치는 트래픽 관측 후 정하며 자동 경보 리소스 생성은 별도다.

7. 설계 의사결정 기록

진행 상태: 완료. 범위 결정을 이해 점검·구현 승인과 분리했다.

G1 질문과 답
report만 우선할지, 새 CLI Job 또는 기존 pipeline 상주 운영까지 포함할지 질문. 사용자 답: “report 우선, pipeline은 패키징·기존 실행 호환까지만”.
결정의 대가
report 배포 개선을 작게 유지하는 대신 pipeline 클라우드 운영은 이 작업으로 완료되지 않는다.
중요 가정 / 검증 필요
Worker Pool 사용 가능성·DB 접속·리소스 크기는 미확인. 실제 배포 전 스테이징 검증이 필요하다. 이용 불가 시 다른 실행 플랫폼으로 임의 전환하지 않고 재설계한다.

채택하지 않은 대안

  • API/report/pipeline 이미지 3개 이상: 현재 공통 runtime·lockfile을 고려하면 빌드 관리 증가 대비 이점이 작다. 향후 시스템 의존성·보안 요구가 달라지면 재평가.
  • 하나의 프로세스에서 모든 batch 루프 실행: 종료·장애·자원 경계가 섞이고 현재 단일 job 계약도 변경된다.
  • 이미지만 분리하고 BatchModule 유지: report가 pipeline 설정에 묶이는 근본 원인을 해결하지 못한다.
  • pipeline 단계별 서비스 분해 및 Core 전면 분할: 선택된 범위를 넘어선다.

10. 구현 승인

설계 승인됨 · 2026-09-20. 사용자의 “ㄱㄱ”를 이 설계의 구현 시작 승인으로 해석했다. 설계·자가 점검·구현 승인은 서로 다른 기록이다. 구현 제어 기록: batch-runtime-isolation-implementation.html

승인 대상: 작업별 초기화 격리, API/batch 이미지 분리와 pipeline 자산 패키징, 기존 실행 호환, report 전용 배포 정의·안내, 관련 테스트. 실제 클라우드 적용·pipeline 운영 전환·DB 계약 변경은 제외.

승인된 구현 범위는 작업별 초기화 격리, API/batch 이미지 분리와 pipeline 자산 패키징, 기존 실행 호환, report 전용 배포 정의·안내, 관련 테스트다. 실제 클라우드 적용·pipeline 운영 전환·DB 계약 변경은 제외한다. 이 페이지의 자가 점검 제출은 승인 처리하지 않는다.

공식 문서와 확인 한계

  • Cloud Run Worker Pool 배포: 상주 백그라운드 실행, 별도 배포 리소스, digest 기반 revision·인스턴스 수 지정의 근거. 기본 자동 확장으로 큐를 처리한다고 가정하지 않는다.
  • Worker Pool secret 설정: 실행 환경별 secret 참조 근거.
  • Cloud Run 컨테이너 계약: 종료 신호·강제 종료·컨테이너 파일시스템 제약 확인 기준.
  • Cloud Run 실행 모델: service / job / worker pool 구분. 새 pipeline의 Job 전환은 이번에 구현하지 않는다.

공식 문서 확인일 2026-09-20. 로컬 코드와 문서를 조사했으며 GCP 계정·리소스·실제 비밀값을 조회하지 않았다.
