회원 인증·JWT·사용자/관리자 권한

로그인·회원가입을 시작점으로 서비스 세션을 발급하고, 현재 API와 이후 개인·관리자 API의 접근 경계를 고정하기 위한 고위험 설계 문서다. G1~G13 의사결정을 반영했고, 사용자의 명시적 “구현 ㄱ” 지시와 G14-A 선택으로 설계를 승인받았다. 이후 fresh Docker Compose DB에서 migration과 signup을 실제 실행하는 과정에서 base schema 부트스트랩 경계가 미해결임을 확인했고, G14-A를 선택했다. 운영 base schema 소유권은 G12-A대로 유지하면서 Compose에만 disposable fixture와 migration runner를 추가한다. 사용자의 후속 진행 지시 r(영문 자판의 ㄱ)을 이 변경 범위에 대한 구현 승인으로 기록하며, 구현·migration·생성 계약은 연결된 구현 제어 문서에 기록한다.

목적
회원 로그인·가입과 JWT 세션, API 사용자·관리자 권한 경계 확정
사용자
NEWTINE 백엔드 개발자·기획 결정자·운영 담당자
문제
현재 API의 실제 인증 guard와 사용자·관리자 권한 판정이 없고 users 스키마의 인증 경계가 미구현
핵심 흐름
email/password 가입·로그인 → 사용자 조회·생성 → access JWT·refresh cookie 회전 → principal·현재 role 판정 → API 접근
강도
High-risk: 인증·인가, 개인 데이터 소유권, refresh token 재사용, 관리자 권한 상승·회수를 검토한다.

목표와 성공 기준

회원이 정의된 로그인·가입 흐름으로 자신을 인증하고, API는 요청 본문·query·path의 사용자 식별자를 신뢰하지 않고 검증된 principal만 사용한다. 일반 사용자는 자신의 개인 API만, 관리자는 명시된 관리자 API만 접근하며, 인증 실패와 권한 부족을 구분한다.

이번 설계의 성공 신호
영역 성공 기준 아직 열려 있는 결정
회원 생명주기 canonical email과 password 자격으로 users 행을 중복 없이 조회·생성하고 가입 직후 session을 발급한다. Argon2id 파라미터와 users schema 경계

인가 현재 API의 공개·회원·관리자 경계를 route별로 선언하고, DB의 현재 role을 공통 guard로 판정한다. ADMIN 초기 부여·승격 경로
운영·검증 401/403, 토큰 회전, 사용자 소유 조건, 일반 사용자→관리자 우회 실패를 계약·통합·smoke로 재현한다. cookie same-site와 Argon2id 운영 파라미터
범위 원칙: 로그인·가입·JWT·현재 API 인증/인가까지를 이번 기준선으로 다룬다. 비밀번호 재설정, 다중 provider 계정 병합, 관리자 계정 발급 화면, 세밀한 permission (RBAC의 role보다 작은 권한), rate limit/WAF는 별도 설계 없이는 자동 포함하지 않는다.

docker compose up -d --build + fresh PostgreSQL db와 api는 healthy로 기동했지만, 빈 DB에서 npm run db:migrate가 relation "users" does not exist로 실패했고 POST /auth/signup은 500을 반환했다. /health는 200, 인증 없는 /me/**는 401이었다. G12-A의 기존 base schema 전제와 Compose fresh 환경의 재현성 사이에 경계 결정이 필요하다. 이 결정 전에는 “Compose 전체 인증 흐름 동작”을 성공으로 판정하지 않는다.

확인하지 못한 사실: 프론트 종류(browser/mobile), 실제 base schema DDL과 배포 secret manager, Argon2id native package의 운영 build 조건, 관리자 계정 발급 절차는 현재 worktree에서 확인되지 않았다. 이 항목들은 구현 중 읽기 전용 확인과 운영 문서로 보완하며, 설계 범위를 바꾸면 재승인한다.

새로 확인된 경계: 현재 Compose는 빈 PostgreSQL과 API만 제공하고 application table이나 migration을 자동 생성하지 않는다. 기존 migration은 users, entities, issue_categories, preference table을 외부 base schema로 가정한다. fresh Compose까지 성공 기준에 포함하려면 local-only bootstrap fixture를 둘지, 애플리케이션 migration history가 운영 base schema를 소유하지 않도록 유지하고, Compose에만 disposable fixture와 migration runner를 둘지 G14-A로 선택했다.

제안 구조와 경계

  1. 로컬 email/password 가입·로그인 endpoint가 입력을 검증하고 내부 user id를 결정한다.
  2. 가입 시 canonical email unique 기준으로 users를 생성하고, 로그인 시 기존 row를 재사용한다. 비밀번호는 원문이 아니라 선택한 password KDF 결과만 저장한다.
  3. access JWT는 서명·issuer·audience·subject·issued-at·expiration을 검증 가능한 형태로 발급한다. refresh 원문은 HttpOnly cookie로만 전달하고 저장소에는 hash만 둔다.
  4. 보호된 요청은 Authorization Bearer를 검증한 뒤 principal을 request context에 두고, 현재 role은 DB에서 확인한다. 개인 데이터는 principal의 user id로만 조회한다.
  5. 관리자 route는 별도 role guard에서 현재 principal의 role을 확인한다. 인증 실패는 401, 인증됐지만 role 부족은 403으로 기존 ProblemDetails 계약에 맞춘다.

Auth HTTP 계약 제안 · G13-A

로그인·가입 성공 시 access token은 JSON으로 반환하고 refresh token은 JSON에 포함하지 않는다. 서버는 refresh cookie를 회전하며, 현재 프론트엔드의 별도 계약이 확인되지 않아 아래 표를 기본 외부 계약으로 제안한다.

인증 endpoint 성공·입력 계약
경로 입력 성공 부작용
POST /auth/signup { email, password } 201 + access response USER 생성, refresh cookie 설정
POST /auth/login { email, password } 200 + access response 새 refresh session 생성, cookie 설정
POST /auth/refresh body 없음, refresh cookie만 사용 200 + 새 access response 기존 refresh 소비, 새 refresh session 생성·cookie 교체
POST /auth/logout 현재 refresh cookie 204, cookie 없음도 idempotent 성공 현재 refresh session revoke, cookie 삭제 
{
  "accessToken": "JWT",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "user": {
    "id": "uuidv7",
    "email": "user@example.com",
    "role": "USER"
  }
}

refresh cookie는 newtine_refresh, HttpOnly, 운영 환경 Secure, SameSite=Lax, Path=/auth, 30일 수명, Domain 미지정으로 제안한다. refresh token은 opaque random value이며 저장소에는 hash만 둔다. 입력 오류는 400, 잘못된 자격·refresh는 401, CSRF/role 부족은 403, 중복 email은 409의 기존 ProblemDetails 형식을 사용한다.

이 계약은 G13-A의 승인된 설계 기록이다. 구현 시 Nestia route 선언과 실제 cookie·ProblemDetails 동작을 일치시키고, 다른 외부 계약이 발견되면 재승인한다.

데이터 모델과 토큰 상태 초안

기존·추가 데이터의 책임
대상 제안 필드/규칙 불변식 상태
users 기존 users를 확장한다(G12-A): canonical email, Argon2id 결과 password_hash, role을 추가하고 기존 kakao_id는 제거한다. 이번 구현에는 social provider/auth endpoint가 없다. email 정규화 결과는 unique. password·role은 client 입력으로 변경 불가. 모든 신규 가입은 USER이며, 기존 row의 기본 role은 USER로 backfill하되 실제 데이터 확인 후 migration한다. refresh_sessions 기존 초안의 id, user_id, token_hash, expires_at, used_at, revoked_at, created_at를 사용한다. refresh는 opaque random value로 발급하고 HttpOnly cookie에 넣는다. 원문 refresh 저장 금지. cookie의 token hash 조회·기존 row 소비·신규 row 발급은 같은 transaction. 만료·used·revoked row는 재사용 불가; 재사용 시 사용자의 활성 session 전체 취소. G9·G11 해결, G13 의존
access JWT sub, iss, aud, iat, exp, jti 중심. jose + HS256, access 15분. role claim은 넣지 않거나 참고값으로만 둔다. algorithm/issuer/audience/expiration을 고정 검증. JWT_SECRET·개인정보·refresh 원문을 payload에 넣지 않음. refresh 수명은 30일 안. G4·G6 해결, G9 운영 의존
principal request에 JWT의 userId와 DB에서 읽은 현재 role, 인증 scheme에서 검증된 token metadata만 저장. controller는 이 값을 service에 전달. body/query/path의 user id로 principal을 덮어쓰지 않음. 사용자가 없는 row는 401로 처리. 구조 제안

기존 migration이 “users와 기존 선호 테이블은 base schema가 소유한다”고 명시하므로, 인증 구현은 base schema 변경 소유권을 먼저 확인한 뒤 role·session DDL을 추가해야 한다. 실제 DB에 이미 존재하는 users row를 모두 USER로 안전하게 backfill할 수 있는지 확인하지 않고 migration을 작성하지 않는다.

반드시 유지할 불변식

  • 인증된 user id는 검증된 access JWT 결과에서만 오며, 요청 입력의 user id는 소유권 증거가 아니다.
  • 로컬 계정의 canonical email은 unique이며, password hash는 원문·로그·응답에 나타나지 않는다. 이번 범위에는 provider 계정이나 email 병합이 없다.
  • access JWT는 짧은 수명·고정된 issuer/audience/algorithm을 사용하고, 만료·위조·잘못된 scheme을 거부한다.
  • refresh token 원문은 HttpOnly cookie 외의 저장·로그·예외 응답에 나타나지 않는다. 저장소에는 검증용 hash만 남긴다.
  • refresh rotation은 기존 token 소비와 새 token 발급이 원자적이어야 하며, 동시에 같은 refresh를 성공시키지 않는다.
  • role은 사용자가 입력·변경할 수 없고, ADMIN route는 인증 guard와 별도 authorization guard를 모두 통과해야 한다.
  • 401(인증 증거 없음/무효/만료/계정 없음)과 403(인증됐지만 role 부족)을 구분한다. 내부 token parsing·DB 오류는 안전한 detail로 숨긴다.
  • 새 인증 관련 값과 예외는 기존 logging redaction을 우회하지 않으며 access/refresh 원문을 구조화 log에 넣지 않는다.

refresh rotation 중 DB 충돌/연결 끊김 500 또는 안전한 503 정책을 별도 결정 transaction rollback; old token은 성공적으로 소비된 것으로 오인하지 않음 재시도 전에 old row 상태를 조회. 같은 요청을 무조건 재실행하지 않음
email 중복·비밀번호 불일치 가입은 409, 로그인은 401 + 계정 존재 여부를 과도하게 노출하지 않는 detail users 생성·password 변경 없음 credential 원문과 password hash는 로그 금지. 반복 시 rate limit은 별도 운영 경계
cross-site refresh cookie 요청 CSRF 검증 실패 시 403 또는 401 정책 refresh rotation 없음 same-site 배포를 기본으로 하고, cross-site SPA를 지원하면 Origin/CSRF token 정책을 추가 확정
refresh 재사용은 탈취 가능성을 의미하지만 정상적인 동시 요청과 구별해야 한다. 단순히 “다시 시도”로 처리하면 이미 소비된 token을 여러 번 살리는 위험이 있으므로 G5에서 취소 범위와 동시성 결과를 함께 확정한다.

설계 의사결정 질문 (grilling)

진행 상태: 완료 / 공유 이해 확인 대기. 아래 질문은 settled design의 이해도 시험이 아니라 구현 전에 사용자와 선택하는 인증·인가 계약이다. G1~G14의 material frontier가 해결되었고, G12-A로 기존 users를 확장하며 G14-A로 운영 base schema 소유권은 유지하고 Compose에만 disposable bootstrap을 두기로 했다. 이번 구현에서는 소셜 provider·카카오 식별자를 사용하지 않는다는 범위를 고정했다.

범위
로컬 계정 생명주기·비밀번호 KDF, 현재 route 접근 정책, cookie CSRF 경계, role source/freshness, refresh 재사용·취소, JWT key/TTL, 관리자 발급·로그아웃, 계정 schema·HTTP contract
결정 트리
G1 local identity → G7 가입 활성화·endpoint → G8 Argon2id/password schema → G12 users 확장 경계; G3 cookie → G9 same-site/CSRF; G4 role source → role guard·demotion; G5 reuse policy → user-wide revoke; G6 key/TTL → config·검증; G10 admin provisioning → role backfill; G11 logout → session revoke API; G12 → G13 auth response·cookie/error contract; G14 bootstrap boundary → Compose migration/E2E
현재 가정
단일 NestJS API가 access JWT를 발급·검증하고 PostgreSQL이 users와 refresh session을 소유한다. 이번 구현은 email/password만 사용하며 소셜 provider와 카카오 식별자는 사용하지 않는다. browser same-site 배포를 기본으로 하고, 가입 즉시 session을 발급하며 password/email verification은 범위 밖이다. 운영 base schema 소유권은 G12-A대로 기존 schema를 전제로 유지하고, G14-A에 따라 fresh Compose에만 disposable bootstrap을 둔다.
보류된 가지
소셜 로그인·provider 계정 병합·password reset·email verification·cross-site SPA·rate limit은 이번 범위 밖이다. Argon2id 파라미터 benchmark와 실제 base schema DDL 확인은 구현 전 검증 항목이다. Compose bootstrap은 운영 schema를 대체하지 않는 disposable fixture로만 다룬다.

G14 · fresh Compose bootstrap 경계

결정: 제공된 Compose에서 빈 DB를 올린 뒤에도 인증 E2E를 재현 가능하게 만들 것인지, 그리고 그때 base schema를 누가 소유할지를 정한다. 확인된 사실은 현재 migration이 외부 base schema를 요구하고 fresh DB에서 signup이 500이 된다는 것이다.

결정 반영 · G14-A: 운영 migration은 G12-A대로 기존 base schema 확장을 유지하고, Compose에만 명시적인 disposable base-schema fixture와 migration runner를 추가한다. 장점은 운영 schema 소유권을 바꾸지 않으면서 fresh Compose E2E를 재현하는 점이고, 단점은 local fixture가 운영 전체 schema의 대체물이 아니라는 점이다.

B 대안: base users·catalog·preference schema까지 애플리케이션 migration history에 포함한다. fresh DB의 일관성은 가장 높지만 기존 owner·데이터·전체 domain schema의 소유권을 바꾸는 큰 범위이며 G12-A의 의미를 변경한다.

C 대안: Compose는 infra-only로 유지하고 base schema 선행 조건·preflight만 문서화한다. 운영 경계는 보존하지만 현재 Compose에서 signup이 동작한다는 성공 기준은 충족하지 못한다.

결정 상태: 사용자 선택 G14-A 및 구현 진행 승인 기록 완료. 운영 base schema 소유권은 유지하고 Compose local bootstrap만 구현한다.

승인 후 검증 계획

아래 명령과 시나리오는 설계 승인 뒤 실제 파일·route·DB 계약에 맞게 고정한다.

  1. auth domain unit: email canonicalization, password KDF·비교, users unique create, JWT claim·algorithm·issuer·audience·TTL 검증.
  2. session unit/integration: 원문 미저장, hash 비교, cookie 정책, 만료·used·revoked 거절, 동시 refresh 중 하나만 소비, 재사용 시 전체 revoke.
  3. guard/controller integration: public/auth/user/admin route matrix, 401과 403, body/query의 user id 위조 실패, role demotion 결과, CSRF 실패.
  4. database migration: 기존 users row backfill, unique/index/FK/check, migration up과 되돌릴 수 없는 데이터 영향 확인.
  5. fresh Compose: G14-A bootstrap 경계를 적용하고 빈 volume에서 migration → signup → protected API → refresh → logout을 실제 HTTP로 재현.
  6. contracts: npm run contracts:all, npm run test:contracts, npm run typecheck:generated로 auth 실패·보안 scheme·응답 타입을 확인.
  7. 기존 게이트: npm run test:unit, npm run test:integration, npm run build, 필요 시 npm run test:smoke.

성공 기준은 단순히 “JWT 문자열이 발급됨”이 아니다. 보호된 실제 route가 올바른 principal과 role을 사용하고, 실패·재전송·동시성·로그 redaction까지 재현되어야 한다.

설계 이해·통제 점검 (design-control)

상태: 미실시. G14가 추가되어 기존 G1~G13 기준선은 재승인 대상이 되었다. G14의 bootstrap 경계를 선택하고 공유 이해를 확인한 뒤, prediction·invariant·boundary·failure recovery·verification coverage를 다시 점검한다. 답변 결과는 브라우저 안에만 남으며 Codex에 자동 전달된다고 가정하지 않는다.
