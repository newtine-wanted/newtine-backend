승인 설계 기준

기본 docker compose up --build가 PostgreSQL과 API를 지속 실행한다. batch는 databaseCheck one-shot 도구로 별도 실행한다. PostgreSQL은 고정된 postgres:18 local baseline과 named volume을 사용하며, 빈 volume에서 DB/user만 초기화한다. application table·schema sync·migration·seed·pgvector는 이번 범위가 아니다.

API container는 DB_HOST=db·API_HOST=0.0.0.0을 사용하고, host 실행은 DB_HOST=127.0.0.1을 사용한다. API와 DB port는 host loopback에만 publish한다. API runtime은 built JS·production dependencies·non-root 실행이며 container watch는 제공하지 않는다.

구현 상태 · 구현 완료

초기 로컬 Docker 구현은 승인된 파일 범위만 단일 worker가 수정했다. 당시에는 애플리케이션 TypeScript, package manifest, database options, entity·schema·migration, 기존 테스트와 계약 산출물을 변경하지 않았다. 이후 보안 hardening은 별도 승인 범위와 구현-control 문서에서 관리한다.

초기 후속 작업은 승인된 환경변수 경계 안에서 루트 .env를 로컬 전용으로 생성한 것이다. Compose 컨테이너 내부의 DB_HOST=db·API_HOST=0.0.0.0 매핑은 유지되고, 호스트 Node 실행을 위한 127.0.0.1 기본값은 .env에 남아 있다. API 컨테이너는 NODE_ENV=development·LOG_FORMAT=json·AUTH_COOKIE_SECURE=true를 local Compose에서 명시한다. DB transport 보안은 애플리케이션의 별도 mode/CA 환경변수로 강제하지 않고 DB provider·네트워크 설정의 책임으로 둔다.

설계 delta · runtime contract delta 없음

승인 baseline의 runtime topology·contract·state·data·failure policy와 다른 material delta는 없다. 실제 Docker 검증에서 발견한 build-stage CA 인증서 설치와 GOMAXPROCS=1 GOGC=50은 1.9GiB 로컬 빌드 자원에 맞춘 구현·검증 보완이며 runtime 동작이나 승인 범위를 바꾸지 않는다. 리뷰 후 API·batch의 전역 newtine-backend:local tag를 제거하고 Compose project-scoped service image로 전환했다. 두 서비스는 같은 Dockerfile에서 build되며, 이 변경은 image identity와 worktree 간 tag collision 경계만 조정하고 runtime contract·data policy는 바꾸지 않는다. 이번 후속에서는 .env.example의 호스트 개발 설정과 컨테이너 실행 설정을 분리하기 위해 API·batch·worker에 NODE_ENV=development·LOG_FORMAT=json을 고정하고, AUTH_COOKIE_SECURE=true는 유지했다. DB 연결 transport 보안은 별도 애플리케이션 환경변수로 강제하지 않는다. production dependency·보안 cookie 전제와 API contract·DB data policy는 바꾸지 않는다. 구현 중 behavior·contract·state·data·failure handling·verification strategy가 바뀌면 이 문서의 상태를 멈추고 설계 문서를 재승인 필요로 되돌린 뒤 별도 승인을 받는다.

IC-001 · 해결됨 초기 DB healthcheck가 Unix socket readiness를 볼 수 있었다. pg_isready -h 127.0.0.1 -p 5432로 수정했고, Compose에서 DB가 healthy가 된 뒤 API가 시작됨을 관찰했다. 재발 시 healthcheck host·port와 DB 로그를 먼저 확인한다. reviewer도 fixed로 판정했다.
IC-002 · 해결됨 profile batch가 API와 다른 stale image를 사용할 수 있었다. API·batch의 전역 newtine-backend:local tag를 제거해 Compose project-scoped service image로 전환했다. 두 서비스는 같은 Dockerfile에서 build되며 정상·실패 복구 batch 명령에 --build를 유지한다. batch exit 0을 확인했다. batch 실행 전 build를 유지하고, 같은 basename worktree를 병렬로 띄울 때는 Compose project name을 분리한다.
IC-003 · 해결됨 초기 host 문서의 NODE_OPTIONS=--env-file가 Node 24에서 허용되지 않았다. 직접 node --env-file=.env dist/... 실행으로 수정했다. host batch가 실제 select 1 후 exit 0이었다. API도 같은 env-file 방식으로 실행한다. reviewer clean verdict.
IC-004 · 해결됨 runtime image에 불필요한 optional platform compiler dependency가 포함될 수 있었다. runtime npm ci --omit=dev --omit=optional로 제한했고, production image build가 성공했다. 새 runtime native dependency 추가 시 omit 영향 재검토.
IC-005 · 해결됨 초기 Docker build가 CA 인증서 누락으로 Go module fetch에 실패했고, CA 보완 후 1.9GiB 환경에서 OOM이 발생했다. build stage에 ca-certificates를 설치하고 GOMAXPROCS=1 GOGC=50을 적용했다. 전체 API·batch image build가 성공했다. 첫 cold build는 약 353초였다. Docker Desktop 메모리와 build cache를 운영한다.
IC-006 · 해결됨 구현-control 문서가 구현 전·검증 대기 상태로 남아 있었다. 현재 as-built 구현, 이슈 trace, runtime evidence와 residual risk를 이 문서에 반영했다. 아래 구현 이해 점검 결과는 채팅으로 자동 전달되지 않으므로 별도 상태로 유지한다.
IC-007 · 해결됨 .env.example의 NODE_ENV=development를 local Compose가 사용하는데, devDependency인 pino-pretty가 빠진 image에서 pretty logger를 선택하면 bootstrap이 실패할 수 있다. Compose API·batch·worker를 NODE_ENV=development로 분류하고 LOG_FORMAT=json을 고정해 dependency-only runtime에서 JSON logger를 사용한다. AUTH_COOKIE_SECURE=true는 유지하고 DB transport 보안 설정은 provider·네트워크에 위임한다. docker compose config --quiet와 API environment 정적 검증, database options 테스트를 실행한다. 로컬 HTTP 인증 쿠키 동작은 별도 smoke에서 확인한다.

검증 공백

  • 애플리케이션 entity·schema·migration이 없는 초기 골격이므로 업무 table 생성·upgrade 동작은 검증하지 않았다.
  • 임시 PostgreSQL table sentinel로 named volume의 row 보존·명시적 reset은 검증했지만, application entity·schema·migration이 없어 실제 업무 데이터 upgrade 동작은 검증하지 않았다.
  • 운영·CI PostgreSQL major는 저장소에서 확인하지 않았으므로 postgres:18은 local baseline이다.
  • Docker Desktop 메모리 약 1.93GiB에서 cold native plugin build가 약 353초 걸렸다. cache가 없는 환경의 시간 편차는 남아 있다.

잔여 위험

  • DB healthcheck가 healthy여도 API 자격증명·업무 query·schema 호환성을 보장하지 않는다.
  • 기존 named volume에서는 PostgreSQL 초기화 env 변경이 재적용되지 않는다.
  • reset은 local data를 삭제할 수 있으므로 일반 down과 섞지 않는다.
  • PostgreSQL major 변경은 같은 volume에 image tag만 바꾸는 방식으로 처리하지 않는다.
  • local Compose는 NODE_ENV=development라도 AUTH_COOKIE_SECURE=true를 사용하므로, 실제 브라우저 로그인은 HTTPS 또는 loopback secure-cookie 동작을 별도 확인해야 한다. DB transport 보안은 DB provider·네트워크 설정과 배포 환경에서 별도로 확인해야 한다.
  • 현재 dependency install은 npm audit 기준 runtime 6건의 취약점(1 moderate·5 high)을 보고했다. dependency 갱신은 이번 승인 범위 밖이라 별도 보안 작업으로 남긴다.
