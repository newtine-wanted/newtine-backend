목표와 성공 조건

회원이 본인 계정의 탈퇴를 요청하면 개인 데이터와 세션을 정리하고, 삭제된 회원의 인증·새 쓰기·보고서 결과 저장을 막는다. 다른 회원과 공유 콘텐츠는 유지한다.

기존 데이터 계약의 삭제·보존 기본안과 T-16을 출발점으로 한다. 사용자가 G1-A(즉시 물리 삭제)와 G2-B(access token만 사용)를 선택했다. 성공한 삭제는 복구하지 않고, 같은 이메일 재가입은 새로운 UUID와 빈 개인 상태로 시작한다.

비범위: 관리자에 의한 타인 강제 삭제, 소셜 계정 해지, 탈퇴 사유 수집, 복구·재가입 금지 원장, 공유 이슈 삭제. 백업·외부 공급자 보존은 별도 운영 경계로 명시한다.

처리 흐름

  1. 요청 제한과 JWT guard를 통과한다. principal.userId만 사용한다.
  2. 최상위 TransactionManager.execute에서 users 행을 FOR UPDATE로 재조회한다. guard 통과 뒤 다른 탈퇴가 먼저 커밋했다면 401로 종료한다.
  3. users를 삭제한다. 검증된 FK CASCADE로 개인 데이터를 제거하고 보고서 사용량 FK를 NULL로 해제한다.
  4. 성공적으로 커밋된 뒤 refresh cookie를 만료시키고 204를 반환한다.
  5. 클라이언트는 access token·회원 개인 캐시·커서를 비우고 비회원 상태로 전환한다. 다른 기기는 다음 인증 요청에서 401을 받고 정리한다.

API 계약 제안

POST /auth/withdraw
Authorization: Bearer <accessToken>

204 No Content
Cache-Control: no-store
Set-Cookie: newtine_refresh=; Path=/auth; HttpOnly; SameSite=Lax; Max-Age=0; ...

기존 auth 명령형 POST 규칙에 맞춘다. 본문 없음(호환용 빈 객체 허용). body의 password·userId·email 등 추가 필드와 query parameter는 400. refresh cookie만으로는 탈퇴할 수 없다. 쿠키는 인증 수단이 아니며 동일 Path=/auth·Secure 정책으로 만료시킨다.

삭제 효과는 중복 적용되지 않지만 응답까지 항상 204로 재현하는 계약은 아니다. 첫 204 후 같은 토큰 재요청은 401이다. 삭제 커밋 뒤 응답이 유실된 경우에도 같은 재요청은 401이며, 장기 탈퇴 증명·멱등 응답을 위해 계정 식별자를 새로 보존하지 않는다.

브라우저에서 401을 받으면 기존 인증 정책에 따라 갱신/로그인 필요 여부를 처리한다. refresh 실패만으로도 삭제 성공을 단정할 수 없다. 204를 받지 못한 불명확한 요청은 “탈퇴 완료 확인 불가”로 처리한다. 이미 서버에서 삭제됐다면 재로그인은 실패하고 같은 이메일 재가입은 새 계정으로 처리된다.

스키마와 쓰기 경계

기존 migration을 수정하지 않고 새 migration을 추가·등록한다. user_region_preferences_user_fk를 users(id) ON DELETE CASCADE로 바꾸고, nullable feed_sessions.user_id에 같은 FK를 추가한다. user_id=NULL인 비회원 세션과 소유자 XOR 제약은 유지한다.

migration은 pg_constraint와 컬럼 정의로 실제 FK의 대상·삭제 동작·검증 상태를 확인한다. 기존 회원 피드에 users가 없는 고아 행이 있거나 기본 선호 테이블의 FK가 예상과 다르면 진단 후 중단한다. 고아 데이터 자동 삭제·비회원 변환은 하지 않는다. 운영 기본 스키마가 별도 소유이므로 필요한 정비 범위는 별도 승인 대상으로 올린다.

회원 피드 세션 생성은 회원을 먼저 잠그고 존재를 재확인하는 짧은 트랜잭션으로 감싼다. 없으면 401, 있으면 같은 트랜잭션에서 생성한다. 서비스/저장소 중 최상위 트랜잭션 소유자는 하나로 두어 중첩 트랜잭션 예외를 피한다. 삭제 이후 늦은 배치 저장은 세션 부재로 실패하며 재생성하지 않는다.

migration·삭제에 대한 lock_timeout/statement_timeout과 제약 검증을 포함한다. 탈퇴 트랜잭션의 초기 제안값은 각각 3초/10초이며 SQL 실행 제한이지 전체 HTTP 완료 시간 보장은 아니다. 격리 DB의 대용량 fixture에서 조정 필요성을 확인한다. rollback이나 migration down은 이미 삭제된 개인정보를 복구하지 않는다.

불변식과 완료의 의미

  1. 탈퇴 대상은 요청자가 제공한 ID가 아니라 JWT를 검증하고 DB에서 확인한 본인이다.
  2. 204 시점에 회원 및 열거된 개인 데이터는 주 DB에서 삭제됐다. 일부만 삭제된 성공 상태는 없다.
  3. 탈퇴 커밋 후 시작된 인증 조회는 기존 access JWT도 거절한다. 이전 JWT를 새로 가입한 계정과 연결하지 않는다.
  4. 삭제 후 새 refresh session·회원 피드·개인 행동·보고서 결과가 부활하지 않는다.
  5. 다른 회원, 비회원 피드, 공유 이슈·기사·분류·대상은 삭제하지 않는다.
  6. 이미 인증을 통과한 읽기 응답·이미 전송된 외부 AI 입력을 회수하거나 즉시 중지했다고 주장하지 않는다.
  7. 토큰만 가진 공격자가 탈퇴할 수 있다는 경계는 사용자 선택 G2-B의 대가다. 별도 비밀번호·확인 토큰을 추가하지 않는다.

동시성·인증·보고서 작업

트랜잭션의 공통 원칙은 회원 → 해당 기능의 종속 행이다. 로그인·refresh·탈퇴는 같은 회원의 users FOR UPDATE를 먼저 잡아 직렬화한다. refresh token hash로 owner ID를 잠금 없이 찾은 다음 회원을 잠그고, 세션을 다시 잠가 유효성을 재검증한다. 최초 조회 결과만 신뢰하지 않는다.

탈퇴 ↔ 피드 생성·저장 세션 생성은 현재 회원 잠금 없음. 배치 저장은 세션 행을 잠그고, 없으면 conflict. 회원 세션 생성은 user-first transaction 및 신규 FK로 보호. 배치 저장은 세션 부재 시 재생성 금지. guest 흐름에는 회원 lock을 추가하지 않음.
탈퇴 ↔ 보고서 신청 mikroOrmReport.repository.ts:70는 REPEATABLE READ로 입력 스냅샷을 만든 후 INSERT. 해당 transaction에서 사용자 FOR KEY SHARE를 먼저 획득한다. 삭제 선행이면 회원 없음으로 종료, 보고서 선행이면 생성 완료 후 탈퇴가 삭제. REPEATABLE READ의 40001은 제한된 전체 transaction 재시도(최대 기존 3회)로 처리하고 소진 시 503. 소유자 부재는 일반 FK 500으로 노출하지 않고 명시적 NOT_FOUND(404)로 매핑·계약 반영.
탈퇴 ↔ 보고서 재시도·claim·완료 retry·heartbeat·complete 등은 상태·attempt·lease 조건부 SQL. complete는 users JOIN 및 report 잠금 사용. 삭제 후 complete=false 테스트 존재. 삭제된 report를 INSERT/upsert하지 않는다. 이미 확보한 claim의 결과 저장은 0행/STALE_CLAIM으로 버린다. report를 잠근 뒤 user 잠금을 역순으로 추가하지 않는다.
탈퇴 ↔ AI 호출 시작 beginReport:16은 RUNNING·attempt를 검사하지만 lease token·user 잠금은 없음. 호출 직전 짧은 별도 transaction: user FOR KEY SHARE → report FOR SHARE → userId·status·attempt·lease token·lease 만료 검증 → usage RUNNING 삽입. 모두 끝나야 provider 호출 허용. 생성·의미 검증 두 호출에 각각 적용.
호출 허가 커밋과 실제 HTTP 전송 사이에도 시간차가 있다. 탈퇴 뒤 새 허가를 내주지는 않지만, 탈퇴 전에 이미 허가된 호출은 커밋 뒤 실제 전송될 수 있다. 204는 외부 처리 취소·과금 취소·이미 전송한 입력 회수를 보장하지 않는다. 이보다 강한 보장은 외부 호출 동안 장기 DB 잠금 또는 별도의 전체 worker 조정이 필요해 현재 설계에 포함하지 않는다.

사용량 처리: 탈퇴는 기존 FK의 weekly_report_id SET NULL을 사용한다. 탈퇴 transaction 안에서 사용량 상태를 먼저 갱신하는 방식을 추가하지 않는다. 진행 중 호출이 끝나면 usage ID로 확정 결과를 저장하고, worker 중단 등으로 남은 RUNNING은 기존 claim 복구가 lease 시간 이후 UNKNOWN으로 바꾼다. worker가 실행되지 않으면 이 정리도 지연되므로 운영에서 감지해야 한다.

현재 claim()은 오래된 사용량 정리와 report 갱신을 같은 transaction에서 실행해 usage → report 잠금 순서가 생길 수 있다. 오래된 terminal/연결 해제 usage 정리를 별도 짧은 transaction으로 분리하고, claim·만료 복구 transaction은 report → 해당 usage 순서를 지킨다. 새로운 usage gate도 user → report → usage를 사용한다. 외부 호출 중에는 어느 잠금도 유지하지 않는다.

로그인·refresh가 먼저 커밋하고 탈퇴 응답 뒤 그 로그인 응답이 도착하는 경우 쿠키가 브라우저에 다시 쓰일 수 있다. DB 세션은 삭제돼 사용할 수 없다. 클라이언트는 늦은 로그인/refresh 결과를 적용하지 않는 처리가 필요하며, 서버는 삭제 후 토큰이 다시 유효해진다고 보지 않는다.

검토 기록: 별도 읽기 전용 분석의 auth/report 결과를 통합했다. 동시 탈퇴 no-op 204 대안은 401 재시도 계약으로 통일했고, 탈퇴 직전 usage 상태 강제 변경 제안은 기존 종료·복구 경계를 재사용해 불필요한 상태 전이를 줄였다. 작업 전후 tracked implementation diff는 없었다.
