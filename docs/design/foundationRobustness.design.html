범위변경이해 점검

승인 범위

ROB-001~004와 FOUNDATION-R-001을 해결한다. 실제 업무 엔티티·DB 마이그레이션·PostgreSQL 성능 검증은 이번 범위 밖이다. 함께 영향을 받는 413 OpenAPI 계약과 실패 회귀 테스트를 갱신한다.

동작 계약

  1. 서버가 UUIDv7 요청 ID를 parser 앞에서 발급한다. 전달받은 ID로 덮어쓰지 않는다.
  2. parser 경계에서 잘못된 JSON은 안전한 400, 크기 초과는 413으로 변환한다. 신뢰된 parser 오류의 type/status 조합만 변환한다.
  3. 실패 응답은 title/status/detail/code 네 필드와 application/problem+json. 5xx 본문 상세는 은닉한다.
  4. 5xx 로그에는 요청 ID와 예외 name/message/stack 및 제한된 cause 경로를 기록한다. request body, HttpException response 객체, 임의 enumerable 속성은 직렬화하지 않는다.
  5. 도메인 정의는 own-key로 조회하고 미등록 코드는 INTERNAL_ERROR로 정규화한다.
  6. NODE_ENV=development 또는 test에만 개발 DB 기본값을 허용한다. 그 외에는 DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD가 필요하다. 모든 환경에서 빈 값과 잘못된 포트는 거절하며 값 자체는 오류에 출력하지 않는다. 설정 검증은 ORM 초기화 시 수행한다.

불변식·경계

임의 예외의 status를 신뢰하지 않는다. 외부 입력은 로그 payload로 남기지 않는다. 라이브러리 UUIDv7 생성과 단일 트랜잭션 정책은 유지한다. 진단용 예외 message/stack은 운영 로그 접근 통제 대상이며 애플리케이션 코드가 비밀값을 예외 메시지에 넣지 않아야 한다.

검증

필터 단위 테스트(5xx 로그·cause·미등록 코드), 설정 매트릭스, 실제 HTTP smoke(정상/validation/JSON 오류/413와 ID·로그 일치), contracts:check, typecheck, test, build, lint, format:check. DB 없는 실행 골격 검증을 실제 저장·rollback 검증이라고 부르지 않는다.

설계 이해 점검 · 미실시

핵심 실패 경계와 운영 설정을 아래 두 질문으로 확인한다. 값 선택은 설계 승인과 별개이며 로컬 결과를 Codex가 관찰했다고 간주하지 않는다. UUID·DB 영속성은 변경 범위가 아니므로 추가 퀴즈를 생략한다.

승인 기록

사용자의 “개선 ㄱ”는 제시된 다섯 문제의 수정 방향에 대한 명시적 실행 요청이다. 승인된 범위의 구현으로 진행하며 추가 설계 선택은 필요하지 않다. 이해 점검 결과는 미관찰이다.
