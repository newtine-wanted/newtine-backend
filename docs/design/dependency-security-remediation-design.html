의존성 보안 보완 설계

npm audit으로 확인된 취약 의존성을 공식 패치 버전으로 올리고 API 동작 변경 없이 리뷰 가능한 PR을 만든다.

작성일: 2026-09-14 · 갱신일: 2026-09-14 · 작업 참조: 보안 의존성 개선 및 PR 요청

목적(purpose)
npm 의존성 보안 advisory를 안전한 패치 버전으로 해소하고 검증 가능한 PR로 전달
사용자(audience)
백엔드 개발자와 PR 리뷰어
문제(problem)
multer 및 uuid 보안 advisory가 lockfile에 남아 있어 API 의존성 공급망 위험과 PR 검증 공백이 존재
핵심 흐름(core-flow)
audit 증거 확인 → 패치 범위 선택 → package manifest·lockfile 갱신 → 빌드·테스트·audit 검증 → PR
목표와 범위 확인 근거 설계 선택 불변식 검증 설계 통제 점검 승인 상태

목표와 범위

  • @nestjs/platform-express를 12.0.2로 올려 취약한 multer@2.2.0 경로를 공식 수정 버전의 multer@2.3.0으로 전환한다.
  • uuid의 최소 버전을 ^11.1.1로 올리고 lockfile도 갱신한다.
  • Nest 직접 의존성의 패치 버전 정렬 여부를 결정한다. 권고안은 common, core, platform-express, testing을 모두 12.0.2로 맞추는 것이다.
  • API route, DTO, DB schema, 런타임 파일 업로드 정책은 변경하지 않는다.
  • 검증 통과 후 codex/dependency-security-updates를 push하고 main 대상 PR을 만든다.
범위 경계: 현재 컨트롤러에는 multipart 업로드 사용이 없으므로 런타임 우회나 parser 설정 변경은 포함하지 않는다. 패치 버전·lockfile 보완으로 공급망 위험을 줄이고, 업로드 기능이 추가될 때 별도 제한 정책을 검토한다.

변경 흐름

실패 시 PR을 만들지 않고 실패 명령과 원인을 issue-register에 남긴다. npm audit fix --force로 범위를 넓히지 않고, 승인된 버전만 명시적으로 갱신한다.

가정: PR target은 저장소 기본 브랜치인 main, 검증이 통과하면 ready PR이다. 사용자가 draft를 원하면 PR 생성 전에 바꾼다.

불변식·실패 복구

  • OpenAPI route, 요청·응답 타입, DB schema, API host/port 동작은 dependency patch 외 변경으로 달라지지 않는다.
  • lockfile의 실제 해석 버전은 audit의 취약 범위 밖이어야 한다: multer > 2.2.0, uuid >= 11.1.1.
  • 패치 후 빌드·테스트·계약 생성이 실패하면 PR을 생성하지 않고 원인을 분류한다. 네트워크/registry 실패는 검증 불가로 기록한다.
  • 의존성 설치가 다른 semver 패키지까지 갱신하면 diff를 재검토하고, 승인 범위를 넘는 변경은 되돌린 뒤 재승인한다.

검증 계획

  1. npm ci로 clean install을 재현한다.
  2. npm audit --audit-level=moderate로 알려진 advisory가 0인지 확인한다.
  3. npm run format:check, npm run lint, npm run typecheck, npm run build를 실행한다.
  4. npm test와 npm run contracts:check로 런타임·계약 회귀를 확인한다.
  5. diff에서 package manifest·lockfile과 이 설계/구현 제어 문서 외의 변경, 의도하지 않은 transitive update, API 산출물 변화를 점검한다.

외부 registry가 필요한 audit/install은 실행 결과를 별도로 남기며, 보안 수정이 확인되지 않은 상태를 통과로 표현하지 않는다.
