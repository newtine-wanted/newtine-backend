구현(as-built)

  • libs/core/src/pipeline: 상태·상한·도메인 검증, 실행 접수/상태/수동 재시도 유즈케이스, repository port와 PostgreSQL adapter.
  • apps/api/src/pipeline: Nestia·Typia endpoint와 API 오류 매핑. 인증은 외부 의존성으로 남긴다.
  • apps/batch/src/pipeline: 단일 worker 조정, 네이버/OpenAI 어댑터, 단계별 실패 분류와 사용량 메타데이터.
  • 외부 adapter 실패는 PipelineException의 pipeline 의미 코드로 통일하고, retryable은 worker 내부 메타데이터로만 사용한다. provider HTTP/SDK 상세는 API·job 계약에 노출하지 않는다.
  • POST/GET/POST retry/POST interrupt /pipeline/runs와 generated SDK·E2E·OpenAPI를 계약 산출물에 반영했다. 운영자가 executionId로 종료를 확인한 뒤 중단 처리하고 재시도할 수 있다. CONTENT 재시도는 필수·최소 1건의 failedJobIds로 선택된 실패 job만 retry_scope/retry_job_ids에 기록하고 discovery를 건너뛰어 재확보한다. 임베딩 실패는 콘텐츠 성공을 되돌리지 않고 embeddingPendingCount로 표시한다.
  • libs/core/src/pipeline/migrations: MikroORM migration 클래스와 명시적 등록 순서로 온보딩·파이프라인 schema를 적용한다. npm run db:migrate 단일 runner를 사용하고, 본문·프롬프트·원시 응답 컬럼은 만들지 않는다.

영향받는 불변식과 잔여 위험

  • 자동 공개의 의도된 불변식은 검증 통과 → 동일 소유 attempt의 상세·근거·PUBLISHED·job 성공 원자 반영이다. transaction callback의 모든 raw query에 context를 전달하도록 수정했다. 실제 DB 경합 증거는 PIPE-REV-008이다.
  • 재시도는 expectedAttempt가 현재 상태와 일치할 때 한 번만 전환되어야 한다. retry·interrupt의 lock/update 모두 같은 transaction context로 실행하도록 수정했다.
  • 의도된 CONTENT 재시도는 discovery·후보 추출을 반복하지 않고 요청에 명시된 하나 이상의 실패 job만 처리한다. service와 두 repository가 누락 목록을 각각 방어하고, 선택 목록과 retry_job_ids snapshot을 동일하게 유지한다.
  • 등록 중복은 후보 문맥 조회와 분리된 transaction 최종 gate에서 정규화 제목을 재확인한다. URL canonicalization은 별도 hardening 항목(PIPE-REV-024)이다.
  • 외부 기사 URL은 Naver host allowlist·3-hop redirect·HTML content-type·2 MiB body cap으로 제한한다. 실제 egress 정책 검증은 운영 수용 단계에 남긴다(PIPE-REV-021).
  • 텍스트 공개 후 embedding은 별도 부작용이므로 commit 직후 crash 시 pending 관측이 누락될 수 있다(PIPE-REV-022).
  • 실제 Naver 본문 추출 품질, OpenAI 계정의 snapshot 접근성, pgvector 설치·migration 적용은 아직 운영 증거가 없다. JWT 미구현은 별도 승인된 범위 밖이다.

검증 증거와 공백

  • 개선 후 npm test: unit 13 suites/66 tests, integration 2 suites/8 tests 통과. 추가 focused retry 검증(npm run test:jest -- test/unit/pipelineValidation.test.ts test/unit/mikroOrmPipelineRepository.test.ts test/integration/pipelineLifecycle.test.ts)은 3 suites/27 tests를 통과했으며, CONTENT 누락 목록의 service·InMemory·MikroORM 방어, 선택 목록 재큐·snapshot, InMemory/SQL 오류 초기화 parity, DISCOVERY 선택 목록을 포함한다. git diff --check도 통과했다.
  • 개선 후 게이트: format check, lint, typecheck, build, contracts check와 API smoke를 모두 통과했다. smoke는 포트 바인딩 허용 환경에서 실행했다. generated E2E 함수 자체는 생성·typecheck 대상이며 실제 상태ful HTTP runner로 실행되지 않았다.
  • focused integration은 InMemoryPipelineRepository를 사용한다. PostgreSQL adapter의 migration 적용, 실제 lock/rollback, interrupt/save-success 경쟁, 동시 retry, partial unique-index 경쟁은 PIPE-REV-008로 남아 있다. InMemory의 saveJobFailure 상태 경계는 PIPE-REV-027로 정합화하고 회귀 테스트를 추가했다.
  • 정상 HTTP 표준 헤더를 포함한 POST /pipeline/runs validator는 compiled Nestia metadata factory 직접 호출로 통과를 확인했고, key 누락은 400을 확인했다. GET의 잘못된 UUIDv7 400 계약과 실제 Naver/OpenAI 자격증명 표본 실행은 미검증이다.
  • 따라서 PIPE-REV-029 계약 blocker는 해소되었고, 로컬 정적·단위 게이트도 통과했다. 다만 PIPE-REV-008의 실제 PostgreSQL 운영 수용 blocker와 실제 provider 표본 공백이 남아 자동 공개 배포 승인을 할 수 없다.

리뷰 판단: blocker 있음. 수직 흐름의 owner fence·검증 후 원자 공개·embedding pending 기록과 CONTENT 재시도 계약(PIPE-REV-029)은 정적·focused 검증상 일관되게 보완되었다. 실제 PostgreSQL migration/transaction 경쟁 검증(PIPE-REV-008)과 PIPE-REV-030~034는 운영 수용 전에 결정·보완해야 하며, 이 판단은 최종 출시 승인과 별개다.
